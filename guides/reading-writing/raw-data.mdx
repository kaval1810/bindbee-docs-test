Bindbee normalizes every record it syncs into a unified model, so an employee from Workday and an employee from BambooHR arrive in your application in exactly the same shape.

Raw data is the layer underneath. It is the payload Bindbee received from the third-party system before normalization, returned alongside the normalized fields on request.

You need it in three situations: confirming how a value was normalized, discovering a provider field the unified schema does not cover, and debugging a discrepancy a customer has reported. It is a diagnostic and discovery tool, not a data source to build on — [Using raw data safely](#using-raw-data-safely) explains why.

---

## Requesting raw data

Add `include_raw_data=true` to any list or retrieve request. It defaults to `false`.

```bash
curl -G https://api.bindbee.dev/api/hris/v1/employees \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>" \
  -d include_raw_data=true
```

The `raw_data` object appears on each record:

```json
{
  "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
  "remote_id": "123321",
  "first_name": "Jane",
  "employment_status": "ACTIVE",
  "marital_status": "SINGLE",
  "raw_data": {
    "employeeNumber": "000000168",
    "firstName": "Jane",
    "employmentStatus": "Active",
    "maritalStatus": "S",
    "customFields": {
      "badgeId": "B-4417"
    }
  }
}
```

Reading it against the normalized fields shows exactly what happened: `Active` became `ACTIVE`, `S` became `SINGLE`, and `badgeId` has no unified equivalent. The first two are [enum normalization](/guides/reading-writing/enum-values); the third is what custom fields exist for.

<Note>
  Raw data is available on the **88 data endpoints** across HRIS, ATS and LMS. It is not returned by the connector, integration, webhook, custom field or meta endpoints, since those describe Bindbee's own resources rather than synced third-party records.
</Note>

---

## What it contains

`raw_data` is an untyped JSON object. Bindbee makes no promises about its contents beyond it being what the provider returned.

* **Field names follow the provider, not Bindbee.** Expect `firstName`, `first_name`, `EmpFirstName`, or whatever that system uses.
* **The structure differs per connector.** A key that exists on one integration will not exist on another, and nesting depth varies.
* **It can change without notice.** Providers add, rename and remove fields on their own schedule.
* **It can be `null`.** Some records have no raw payload retained.

## Inspecting structure before you have a record

To see the shape of a provider's payload without pulling records, use the raw data endpoint. It is the fastest way to find the path to a field you want to map.

```bash
curl -G https://api.bindbee.dev/api/v1/custom-fields/raw-data \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -d category=HRIS \
  -d model=employee \
  -d connector_token=<CONNECTOR_TOKEN>
```

| Parameter | Required | Notes |
| --- | --- | --- |
| `category` | Yes | `HRIS`, `ATS` or `LMS` |
| `model` | Yes | The model slug, for example `employee` |
| `connector_token` | One of the two | Returns the latest synced row for that connector |
| `integration_slug` | One of the two | Returns the integration's canned sample payload |

Pass exactly one of `connector_token` or `integration_slug`. Providing both, or neither, returns a `422`.

With `connector_token` you get that connector's most recently synced row. **If the connector has never synced, the response falls back to the integration's canned sample** — enough to write a mapping against, but confirm the shape once real data lands. With `integration_slug` you get the sample directly, which is useful when building against an integration before any customer has connected it.

<Tip>
  Three ways to look at upstream data, and they are not interchangeable. Use this **endpoint** to find a field. Use `include_raw_data` with a small `page_size` to spot-check a mapping across records, or with an `ids` filter to audit one person. Use `include_custom_fields` for anything you consume in production.
</Tip>

## Using raw data safely

The rule is straightforward: **read raw data, do not build on it.**

Code that reaches into `raw_data` for a value works for the one connector you tested against and silently breaks for every other one, because the key it depends on does not exist there. It also breaks when that provider renames the field.

When you find a value your product genuinely needs, promote it to a [custom field](/guides/extending/custom-fields). You map it once with a JMESPath expression, per integration or per connector, and it then arrives on a stable key in the `custom_fields` object on every record.

| | Raw data | Custom fields |
| --- | --- | --- |
| Purpose | Inspection and discovery | Consuming provider-specific values in production |
| Key names | The provider's | Yours, chosen once and stable |
| Behaviour across connectors | Different everywhere | The same key on every connector you map |
| Safe to depend on | No | Yes |

Use raw data to find the value; use custom fields to consume it.

<Warning>
  `include_raw_data` increases response size, sometimes considerably, since it returns the full provider payload for every record in the page. Leave it off in production paths and turn it on when you are investigating something.
</Warning>
