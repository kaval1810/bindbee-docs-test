title: "Webhooks"
description: "Receive notifications when a connector syncs or when synced data changes, instead of polling the API."
icon: "webhook"
---

Webhooks let Bindbee push updates to you. When a sync starts, finishes or fails, and when records are created or updated, Bindbee sends a `POST` to a URL you control.

The reason to use them is efficiency. Without them you poll to find out whether anything changed, and most of those calls return nothing new. The data-change events go further than a "something happened" signal: they carry the IDs of the records that moved, so you can fetch exactly those instead of re-reading a full list.

**Neither kind of event carries the data itself.** A change event tells you something happened and gives you enough to go and read it — your handler's job is to fetch, not to consume a payload. That is deliberate: a record carried in a webhook is a snapshot from the moment the event fired and may be stale by the time your handler runs.

---

## Events

Five events are available. The dashboard shows the label in the left column; the payload carries the event string in the middle.

| Dashboard label | Event | Fires when |
| --- | --- | --- |
| Sync start | `connector_sync_started` | A sync job begins for a connector |
| Sync completed | `connector_synced` | A sync job finishes successfully |
| Sync error | `connector_sync_error` | A sync job fails |
| Employee model change | `employee_data_changed` | One or more employee records were created or updated |
| Data model change | `connector_data_modified` | One or more records in any supported model were created or updated |

<Tip>
  `connector_synced` is the event most integrations start with. It is the cleanest signal that a newly connected account has finished its initial sync and is ready to use in your product — see [Triggering a job on completion](/guides/reading-writing/syncing).
</Tip>

## Creating a webhook

Webhooks are configured in the dashboard, under **Configure → Webhooks**.

<Steps>
  <Step title="Enter your destination URL">
    Add the URL that should receive the notifications. Use **Test URL** to confirm your endpoint is reachable and accepting requests before you save.
  </Step>

  <Step title="Name the webhook">
    Give it something descriptive, for example `Employee data`. The name appears in delivery logs, which makes tracing a specific delivery easier later.
  </Step>

  <Step title="Choose the environment">
    Webhooks are environment-specific. A Production webhook never fires for a Development connector, and the reverse is also true — if you are testing and nothing arrives, check this first. See [Environments](/get-started/environments).
  </Step>

  <Step title="Select events and create">
    Tick the events you want. One webhook can subscribe to several, or you can create separate webhooks per event to route them to different handlers. Then press **Create webhook**.
  </Step>
</Steps>

## Payload structure

Every payload shares a common envelope. Four objects are always present, and one more appears on failures.

| Key | Present on | Contains |
| --- | --- | --- |
| `webhook` | All events | Which webhook fired and which event it was |
| `connector` | All events | The connector the event relates to |
| `sync` | All events | The sync job that triggered the event |
| `data` | All events | The event payload — its shape varies by event |
| `error` | `connector_sync_error` only | Details of the failure |

### `webhook`

```json
{
  "webhook_id": "10c9a6b1-4ea8-476e-bdb0-193001a94a8d",
  "url": "https://example.com/hooks/bindbee",
  "event": "connector_synced"
}
```

Read `webhook.event` to route the payload. Do not infer the event from the shape of `data`.

### `connector`

```json
{
  "id": "018f99e2-ed3a-7f4c-ae97-83d619bdf95c",
  "display_name": "BreatheHR",
  "integration_slug": "breathehr",
  "categories": ["HRIS"],
  "org_name": "Test Org",
  "origin_id": "user_123",
  "connector_status": "COMPLETE",
  "end_user_name": "John Doe",
  "end_user_email": "abc@xyz.com"
}
```

`origin_id` is the identifier you supplied when creating the connector, and it is usually the fastest way to map an incoming webhook back to a customer in your own database without storing Bindbee connector IDs.

`categories` is an array — a single connector can serve more than one category, for example `["LMS", "HRIS"]`.

### `sync`

```json
{
  "sync_id": "019f146e-8396-7c6d-aff3-c5760bf5eefe",
  "sync_type": "AUTOMATED",
  "sync_name": "#13"
}
```

| Field | Description |
| --- | --- |
| `sync_id` | Unique identifier of the sync job |
| `sync_type` | `AUTOMATED` for a scheduled sync, `MANUAL` for one you triggered — see [Forcing a resync](/guides/reading-writing/syncing#forcing-a-resync) |
| `sync_name` | The name assigned to the sync job, incrementing per run (`#1`, `#2`) |

`sync_id` is stable across every event from the same job, so you can correlate a `connector_sync_started` with the `connector_synced` that closes it. It also works as an idempotency key, since a retried delivery carries the same values.

### `error`

Included only on `connector_sync_error`:

```json
{
  "failed_at": "2026-07-07T11:21:35.837448+00:00",
  "message": "A runtime error occurred during the sync process. Bindbee team has been notified.",
  "detail": {}
}
```

`detail` is returned as `{}` when no additional information is available.

### `data`

This is the part that changes between events, so handle it per event rather than writing one parser for all five.

| Event | `data` shape |
| --- | --- |
| `connector_sync_started` | Object describing the sync, with `display_status: "Syncing"` |
| `connector_synced` | Object describing the sync, with `display_status: "Done"` |
| `connector_sync_error` | Object describing the sync, with `display_status: "Failed"` |
| `employee_data_changed` | Array of employee IDs |
| `connector_data_modified` | Object keyed by model name, each value an array of record IDs |

## Delivery and retries

| Property | Value |
| --- | --- |
| Method | `POST` |
| Timeout | 10 seconds per attempt |
| Maximum retries | Up to 4 |
| Retry window | Within 60 seconds |

Retries are triggered by request and network-layer failures — timeouts (connection, read, write, pool), connection errors, protocol errors, and proxy, decoding or redirect failures.

Because a retried delivery is indistinguishable from the original at the payload level and carries the same `sync_id` and `webhook_id`, **your handler must be idempotent.** Processing the same event twice should be a no-op.

<Warning>
  Your endpoint has 10 seconds to respond. Do not do the work inline: verify the signature, queue the payload, return a `2xx` immediately, then process asynchronously. Handlers that fetch records or write to a database before responding are the most common cause of timeouts, and a timeout costs you the retry budget.
</Warning>

## Securing your endpoint

Anyone who discovers your webhook URL can `POST` to it. Verify every incoming request before acting on it.

Bindbee signs each delivery and sends the result in the `X-Bindbee-Webhook-Signature` header. The signature is a **base64url-encoded HMAC-SHA256 of the raw request body**, keyed with your organisation's webhook signature key.

Your signature key is in the **Security** section of the Webhooks configuration page. It is unique to your organisation and can be regenerated if it is ever exposed.

<Warning>
  Compute the HMAC over the **raw request body**, exactly as received. If your framework parses the JSON and you re-serialise it, key order and whitespace can change and the signature will never match. Capture the raw bytes before parsing.
</Warning>

<CodeGroup>
```python Python
import base64, hashlib, hmac

signature_key = "YOUR_WEBHOOK_SIGNATURE_KEY"

received_signature = request.headers.get("X-Bindbee-Webhook-Signature")
if not received_signature:
    raise ValueError("Signature header missing; request may not be from Bindbee.")

# Raw body bytes, not a re-serialised parsed object
body_bytes = request.body if isinstance(request.body, bytes) else request.body.encode("utf-8")

hmac_digest = hmac.new(
    signature_key.encode("utf-8"),
    body_bytes,
    hashlib.sha256,
).digest()

expected_signature = base64.urlsafe_b64encode(hmac_digest).decode()
signature_valid = hmac.compare_digest(expected_signature, received_signature)
```

```javascript Node
const crypto = require("crypto");
const express = require("express");
const app = express();

// Capture the raw body before Express parses it
app.use(express.json({
  verify: (req, res, buf) => { req.rawBody = buf; },
}));

const webhookSecret = "YOUR_WEBHOOK_SIGNATURE_KEY";

app.post("/hooks/bindbee", (req, res) => {
  // Node lower-cases incoming header names
  const receivedSignature = req.headers["x-bindbee-webhook-signature"];
  if (!receivedSignature) return res.status(401).send("Missing signature");

  const expectedSignature = crypto
    .createHmac("sha256", webhookSecret)
    .update(req.rawBody)
    .digest("base64")
    .replace(/\+/g, "-")
    .replace(/\//g, "_");

  const a = Buffer.from(expectedSignature, "utf-8");
  const b = Buffer.from(receivedSignature, "utf-8");

  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    return res.status(401).send("Invalid signature");
  }

  // Respond first, process afterwards
  res.sendStatus(200);
  enqueue(req.body);
});
```

```ruby Ruby
require 'base64'
require 'openssl'

secret_key = 'YOUR_WEBHOOK_SIGNATURE_KEY'

received_signature = request.headers['X-Bindbee-Webhook-Signature']
raise 'Signature header missing; request may not be from Bindbee.' unless received_signature

# Read the raw body, and rewind so later code can read it too
request.body.rewind
request_body = request.body.read

hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new('sha256'), secret_key, request_body)
expected_signature = Base64.urlsafe_encode64(hmac_digest)

valid_signature = ActiveSupport::SecurityUtils.secure_compare(expected_signature, received_signature)
```
</CodeGroup>

## Monitoring deliveries

Delivery logs are on the [Webhooks tab](https://app.bindbee.dev/logs/webhooks) under Logs, and on each webhook's own page.

Three endpoints cover the same ground programmatically, which is what you want for alerting on delivery failures rather than discovering them by hand.

**List your webhooks**, for their IDs, names, URLs, enabled state and when each last fired:

```bash
curl -G https://api.bindbee.dev/api/v1/webhooks \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -d is_active=true
```

**List delivery attempts**, with filters:

```bash
curl -G https://api.bindbee.dev/api/v1/webhooks/logs \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -d errors_only=true \
  -d created_at_from=2026-08-01T00:00:00Z
```

| Parameter | Purpose |
| --- | --- |
| `webhook_id` | Deliveries for one webhook |
| `connector_id` | Deliveries triggered for one connector |
| `webhook_action` | Comma-separated event types, for example `connector_synced,employee_data_changed` |
| `response_code` | Comma-separated status codes, for example `200,403,503` |
| `created_at_from`, `created_at_to` | ISO 8601 bounds, interpreted as UTC when no offset is supplied |
| `errors_only` | When `true`, only deliveries whose response code was `400` or above |

**Get one delivery** by its log ID, for the full request and response detail including the status code your endpoint returned:

```bash
curl https://api.bindbee.dev/api/v1/webhooks/logs/<LOG_ID> \
  -H "Authorization: Bearer <BINDBEE_API_KEY>"
```

<Tip>
  Polling `GET /webhooks/logs?errors_only=true` on a schedule is a simple way to catch a silently broken endpoint. A webhook that stops being delivered is easy to miss, because nothing arrives to tell you.
</Tip>

<Note>
  These three endpoints have their own pagination bounds: `/webhooks` defaults to `20` with a maximum of `100`, and `/webhooks/logs` defaults to `25` with a maximum of `50`. Everything else on the API is `50` and `200` — see [Pagination](/api-reference/basics/pagination).
</Note>

## What webhooks cannot tell you

**That nothing happened.** Silence is ambiguous — no events could mean no changes, a delivery failure, or a connector that broke three weeks ago. Watch connector health separately, via [Monitor sync status](/guides/troubleshooting/sync-status).

**That you received everything.** Delivery is best-effort and the retry window is 60 seconds. A deploy that takes your endpoint down for two minutes loses those events permanently, with no error in your logs or Bindbee's.

**Which field changed.** An event says a record changed, not which attribute or what it was before.

**That a record was deleted.** Disappearance is a non-event. Only a scheduled read finds it.

{/* VERIFY: ordering - can events for one connector arrive out of sequence? Retry behaviour is documented; ordering is not, and it determines whether a handler can trust event order or must re-read state. */}

### Recovering a missed delivery

Do not try to recover the events. Take the earliest plausible start and latest plausible end of the outage — overlapping is free, a gap is not — then read current state with `modified_after` for each affected connector and model. If a record changed three times during the outage, current state is what you want anyway. See [Querying Data](/guides/reading-writing/querying-data).

One thing an incremental read will not surface: a connector that broke during the outage produces *no* new data, so check sync status per connector as well.

### When polling is the better instrument

You poll **Bindbee, not the source system**, so it costs nothing upstream. Polling every five minutes against a 24-hour sync produces 288 identical responses a day — time it off the schedule instead. Poll the connector list rather than the data endpoints, use `next_sync_start_time` to decide when to read, then read with `modified_after` for the connectors whose `last_sync_start_time` moved.

## Created versus modified records

Data-change events tell you a record was created **or** updated, without saying which. If your logic differs — a new hire versus a job-title edit, first-time enrolment versus a change to an existing one — you have to determine it yourself by comparing against your own stored copy.

<Warning>
  There is currently no created-versus-modified flag in the webhook payload.

  {/* VERIFY: this was raised with engineering in 2026 and a payload flag was discussed. If it shipped, make it the primary method and demote the comparison approach above. */}
</Warning>

**The first sync looks like everything was created.** The initial sync on a new connector loads the entire population, so every record is new to you. That is technically correct and rarely what you want — sending a welcome email to an entire workforce because a connector was just connected is a real failure mode.

Handle onboarding separately from steady state: process the first sync as a bulk import without triggering per-record workflows, then switch to event-driven handling. `sync.sync_name` increments per run, which is one way to recognise the first.
