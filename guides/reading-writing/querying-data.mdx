Filters run against Bindbee's copy, never against the source system. **What you can ask for is fixed by what Bindbee stored, and when you can ask is fixed by when it last synced** — which explains most of what follows.

## Narrowing a collection

Every filter is work Bindbee does instead of your application. At the maximum `page_size` of 200, a connector with 20,000 employees is a 100-page walk against a budget of [200 requests per minute](/api-reference/basics/rate-limits). Narrowing to the records you actually want makes it one request.

| Parameter | Matches | Takes |
| --- | --- | --- |
| `ids` | Bindbee record IDs | Several, comma-separated |
| `manager_id` | Employees reporting to a manager | Several |
| `company_id` | Employees at a company | Several |
| `groups` | Group membership | Several |
| `work_locations` | Work location | Several |
| `pay_group_id` | Pay group | Several |
| `employment_status` | Status — [see below](#employment-status) | One |
| `remote_id` | The source system's own ID | One |
| `employee_number` | HRIS employee number, not unique everywhere | One |
| `work_email` | Work email | One |
| `first_name`, `last_name` | Name | One |
| `modified_after` | Sync recency — [see below](#fetching-only-what-changed) | One |

Three things follow from filtering a stored copy rather than a live system:

**Matches are exact, and only ever inclusive.** `first_name=Jo` does not match `John`, and no parameter excludes. Fetch the statuses you want rather than excluding the ones you don't — a few inclusive requests still beat paging everything.

**Commas are `OR`; separate parameters are `AND`.** `groups=<A>,<B>&employment_status=ACTIVE` returns active employees who are in group A or group B.

**Not everything you can read, you can filter.** Custom fields come back in responses but are never filterable, so a custom field still leaves you filtering client-side. Where the source system supports a filter natively, [Passthrough](/guides/extending/passthrough) reaches it directly, at the cost of a provider-specific response shape.

```bash
curl --request GET \
  --url 'https://api.bindbee.dev/api/hris/v1/employees?groups=<GROUP_A>,<GROUP_B>&employment_status=ACTIVE&page_size=200' \
  --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
  --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
```

`expand` is not a filter either. It changes the shape of what comes back rather than which records do — `expand=manager[first_name,last_name]` saves a second request for a related record, but does not shorten the page walk.

## Employment status

The standard values are `ACTIVE` · `PENDING` · `INACTIVE` · `ACTIVE_EXTERNAL` · `INACTIVE_EXTERNAL` · `LEAVE` · `DECEASED` · `RETIRED` · `-`, and the parameter is not limited to them: any connector-specific status that appears in a response can also be filtered on. A value you can see is a value you can query.

**`-` means the source system supplied no status.** Treat it as unknown rather than inactive, and remember that filtering for any specific status excludes it — the usual reason a status query returns fewer records than expected.

**`_EXTERNAL` usually marks someone who is not a direct employee**, a contractor or contingent worker. Excluding those two values is the common fix for a headcount that reads higher than the customer expects, but the API assigns them no fixed meaning, so confirm what your connector puts there first.

<Warning>
  Which upstream value maps to which status varies by integration. Verify against one connector before relying on a status filter across all of them.
</Warning>

## Fetching only what changed

`modified_after` returns records **synced by Bindbee** after a timestamp — not records the source system changed after it. Two things follow:

**A resync makes everything look new.** Records re-synced during that run match the filter even when nothing changed upstream, so an incremental read can return the whole dataset. Processing has to be idempotent: an unchanged record must be safe to handle twice.

**Sync cadence is your real resolution.** An edit in the HRIS is invisible until the next sync picks it up, so a 24-hour cadence means up to 24 hours of latency however often you poll.

```bash
curl --request GET \
  --url 'https://api.bindbee.dev/api/hris/v1/employees?modified_after=2026-08-13T00:00:00Z&page_size=200' \
  --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
  --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
```

The watermark discipline is one rule in three parts: **take the timestamp before you read, reuse the identical string on every page, and store it only once the whole walk succeeds.** Taking it afterwards loses records synced mid-run; recomputing it per page corrupts the cursor's position; advancing it on failure loses whatever the failed run never returned. Send an explicit `Z` — with no offset the value is read as UTC anyway, but not visibly.

Rather than polling on a fixed schedule, run the read when the sync-completed event fires and pass your stored watermark. The event says data has landed; the filter says what is new — see [Trigger a job on completion](/guides/reading-writing/syncing).

## If this didn't work

<AccordionGroup>
  <Accordion title="A filter returns nothing though the records clearly exist">
    For `remote_id` and `employee_number`, confirm the value against `raw_data`. What the HRIS shows in its own UI is often not the identifier its API returns — see [Inspect raw data](/guides/reading-writing/raw-data).
  </Accordion>

  <Accordion title="The count doesn't match the customer's headcount">
    Usually a population-definition mismatch rather than missing data: contingent workers included, terminated employees retained, or one person holding several employment records. See [Record counts](/guides/troubleshooting/record-counts).
  </Accordion>

  <Accordion title="A related model didn't come back in an incremental read">
    `modified_after` is per model. An employee changing does not mark their employment or benefit records as synced, so filtering those separately misses related changes. Read them without the filter, or subscribe to data-change events for the model.
  </Accordion>

  <Accordion title="You need to know what changed, not just which records">
    The filter returns current state, not a diff. Compare against your own stored copy, or subscribe to the data-change events, which return the IDs of affected records per model.
  </Accordion>
</AccordionGroup>
