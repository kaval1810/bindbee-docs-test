Every list endpoint returns data Bindbee has already synced from the connected system. Three sets of query parameters control what comes back:

| Parameter | What it does |
|---|---|
| **`filters`** | Narrow the result set to the records you care about |
| **`expand`** | Return related objects inline instead of just their IDs |
| **`modified_after`** | Return only records updated since a point in time |

All three work alongside `cursor` and `page_size`, and can be combined in a single request.

The examples here use [Get Employees](/hris/employee/get-employees), but the same behaviour applies across HRIS, Payroll, ATS and LMS endpoints. The exact filter set differs per model, so check the reference page for the endpoint you are calling.

<Note>
Queries run against Bindbee's synced copy of the data, not against the third-party API in real time. Results reflect the last successful sync for that connector — see [Sync frequency](/api-reference/basics/sync-frequency).
</Note>

Every request needs your API key and the connector token for the end customer whose data you are reading:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

## Filters

### How filters work

Filters are query parameters on the list endpoint. A few rules apply everywhere:

- **Multiple filters combine with AND.** `employment_status=ACTIVE&company_id=<id>` returns active employees at that company only.
- **ID parameters accept comma-separated lists**, which behave as OR within that parameter. Do not put spaces after the commas.
- **Name and email filters are case-insensitive.**
- **Filters are inclusive only.** Nothing excludes — fetch the values you want rather than the ones you don't.
- **Filtering happens before pagination.** Page through a filtered result set with `cursor` exactly as you would an unfiltered one.

### Available filters on Get Employees

| Parameter | Type | Description | Example |
|---|---|---|---|
| `ids` | string | One or more Bindbee employee IDs | `01931edf-04b6-7391-8a5c-93ac4b395316` |
| `remote_id` | string | The third-party API ID of the matching object | `3235005483341316245` |
| `manager_id` | string | Return employees reporting to these managers | `01931edf-04b6-7391-8a5c-93ac4b395316` |
| `company_id` | string | Return employees at these companies | `01931edf-04c8-7649-a470-d85f6161bd1a` |
| `employee_number` | string | The employee number shown in the third-party UI | `000000168` |
| `first_name` | string | Case-insensitive match on first name | `Jane` |
| `last_name` | string | Case-insensitive match on last name | `Doe` |
| `work_email` | string | Case-insensitive match on work email | `jane.doe@acme.com` |
| `employment_status` | string | `ACTIVE`, `PENDING`, `INACTIVE`, `ACTIVE_EXTERNAL`, `INACTIVE_EXTERNAL`, `LEAVE`, `DECEASED`, `RETIRED` or `-` | `ACTIVE` |
| `groups` | string | Return employees belonging to these groups | `01931edf-04b6-7391-8a5c-93ac4b395316` |
| `work_locations` | string | Return employees at these work locations | `01931edf-04c8-7649-a470-d85f6161bd1a` |
| `pay_group_id` | string | Return employees in these pay groups | `01931edf-04b6-7391-8a5c-93ac4b395316` |

Two more parameters shape the payload rather than the result set. Both default to `false`:

| Parameter | Type | Description |
|---|---|---|
| `include_raw_data` | boolean | Include the original third-party payload Bindbee used to build the unified record |
| `include_custom_fields` | boolean | Include any [custom fields](/guides/extending/custom-fields) configured for the model |

<Note>
Custom fields are returned, never filtered on.
</Note>

`employment_status` is not a closed set — a connector's own status values are filterable too, and `-` marks a record the source gave no status for, so filtering for any specific status excludes those records. See [Enum values](/guides/reading-writing/enum-values).

### Examples

Active employees at one company:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?employment_status=ACTIVE&company_id=018af1fe-1250-772d-87c5-6f725a579e8a" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

Fetch a specific set of employees by ID in one call:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?ids=01931edf-04b6-7391-8a5c-93ac4b395316,01931edf-04c8-7649-a470-d85f6161bd1a" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

Look up an employee you only know by their identifier in the source system:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?remote_id=3235005483341316245" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

<Tip>
Use `id` for anything you store on your side. It is Bindbee's stable identifier and stays consistent across syncs. Use `remote_id` when you need to reconcile against a record your customer sees in their own HRIS or payroll UI — and confirm the value against `raw_data` first, since what the HRIS shows in its UI is often not the identifier its API returns.
</Tip>

## Expand

### How expand works

Relation fields on a unified model return as Bindbee IDs by default. On the Employee model that includes `manager`, `company`, `groups`, `work_locations`, `pay_group` and `payroll_run_calendar`. Getting a manager's name would normally mean a second call to Get Employee By Id.

`expand` removes that round trip by returning the related object inline.

**Syntax**

- Pass one or more relation names, comma separated, with **no spaces anywhere** in the value.
- Optionally restrict which fields come back for a relation by listing them in square brackets.

```
expand=manager
expand=manager[first_name,last_name]
expand=manager[first_name,last_name],company,pay_group
```

### Example

Default response, relations as IDs:

```json
{
  "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
  "first_name": "Kunal",
  "last_name": "Tyagi",
  "manager": "018aeaff-cc7c-7837-988a-965762bd63c1",
  "company": "018af1fe-1250-772d-87c5-6f725a579e8a"
}
```

The same request with `expand=manager[first_name,last_name],company`:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?expand=manager[first_name,last_name],company" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

```json
{
  "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
  "first_name": "Kunal",
  "last_name": "Tyagi",
  "manager": {
    "first_name": "Jane",
    "last_name": "Doe"
  },
  "company": {
    "id": "018af1fe-1250-772d-87c5-6f725a579e8a",
    "name": "Acme Inc"
  }
}
```

### Notes

- Field selection is the difference between a manageable payload and a very large one. If you only need a manager's name to render a row, ask for the name, not the whole employee record.
- If you still need the related record's identifier after selecting fields, include `id` in the bracket list.
- Expanding several relations at `page_size=200` produces large responses. Lower the page size if you see slow responses or timeouts.
- A relation that is null on the record stays null when expanded.

## modified_after

### How modified_after works

`modified_after` takes an ISO 8601 datetime and returns only objects whose `modified_at` value is later than it.

```
modified_after=2024-02-21T21:22:12.993Z
```

If you do not supply a timezone offset, the value is interpreted as UTC.

<Note>
`modified_at` is the datetime Bindbee last updated its copy of the record. It is not the third party's own "last updated" field. `modified_after` therefore answers "what has changed in Bindbee since I last looked", which is what you want for keeping your database in step.
</Note>

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?modified_after=2024-02-21T21:22:12.993Z" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

### The delta sync pattern

1. On first run, pull everything with no `modified_after`, paging through with `cursor`.
2. Record the highest `modified_at` you saw across all pages, in UTC.
3. On the next run, pass that value as `modified_after`.
4. Upsert the returned records into your store, keyed on `id`.
5. Update your stored watermark and repeat.

```python
params = {"page_size": 200}
if last_synced_at:
    params["modified_after"] = last_synced_at

while True:
    response = requests.get(
        "https://api.bindbee.dev/api/hris/v1/employees",
        params=params,
        headers=headers,
    ).json()

    for employee in response["items"]:
        upsert(employee)  # key on employee["id"]

    if not response["cursor"]:
        break
    params["cursor"] = response["cursor"]
```

### Things to watch

- **Match your polling to the sync frequency.** Bindbee syncs connectors once every 24 hours by default, and this is configurable. Polling far more often than the connector syncs mostly returns empty pages. For near real-time updates, use [webhooks](/guides/reading-writing/webhooks) instead of tight polling.
- **A resync makes everything look new.** Records re-synced during a full resync get a fresh `modified_at` even when nothing changed upstream, so an incremental read can return the entire dataset. Expected behaviour, not a bug.
- **Always upsert, never insert blindly.** The same record can appear in more than one window. Keying on `id` keeps this safe.
- **Store the watermark in UTC** and subtract a small buffer, for example one minute, before using it. That avoids dropping a record that landed between two pages of a long paginated run.
- **`modified_after` is per model.** An employee changing does not mark their employment or benefit records as modified, so filtering those separately misses related changes. Read them without the filter, or subscribe to data-change events for the model.
- **Combine it with filters.** `modified_after` plus `employment_status=ACTIVE` gives you only the active employees that changed, which is usually a much smaller set to process.

## Putting it together

Filters, `expand`, `modified_after` and pagination all compose in a single request:

```bash
curl -X GET "https://api.bindbee.dev/api/hris/v1/employees?\
employment_status=ACTIVE&\
modified_after=2024-02-21T21:22:12.993Z&\
expand=manager[first_name,last_name],work_locations&\
include_custom_fields=true&\
page_size=200" \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

That request returns active employees changed since the given timestamp, with each manager's name and work locations resolved inline and any configured custom fields attached, 200 records per page.
