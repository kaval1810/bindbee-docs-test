Filtering server-side cuts pages, latency, and rate-limit pressure. Filters combine with `AND` - every one you add narrows further.

<Info>
  **Before you start**

  - You know which field identifies the records you want.
</Info>

## Steps

<Steps>
  <Step title="Pick the filter">
    On employees:

    | Parameter | Matches | Notes |
    | --- | --- | --- |
    | `ids` | Bindbee record IDs | Comma-separated, no spaces |
    | `remote_id` | The source system's own ID | Single value |
    | `employee_number` | Employee number from the HRIS | Not unique on every system |
    | `work_email` | Work email | |
    | `first_name`, `last_name` | Name | |
    | `employment_status` | Status | See enum below |
    | `manager_id` | Employees reporting to a manager | Comma-separated |
    | `company_id` | Employees at a company | Comma-separated |
    | `groups` | Group membership | Comma-separated group IDs |
    | `work_locations` | Location | Comma-separated location IDs |
    | `pay_group_id` | Pay group | |
    | `modified_after` | Sync recency | See [Filter with modified_after](/guides/reading-writing/querying-data) |

    **Result:** A parameter that matches your intent.
  </Step>

  <Step title="Use the exact status values">
    `employment_status` accepts:

    `ACTIVE` · `PENDING` · `INACTIVE` · `ACTIVE_EXTERNAL` · `INACTIVE_EXTERNAL` · `LEAVE` · `DECEASED` · `RETIRED` · `-`

    The `_EXTERNAL` values matter when you want employees only. Contingent workers and contractors commonly carry an external status, and excluding them is the usual fix for a population count that's higher than the customer expects.

    `-` means the source system supplied no status - treat it as unknown rather than as inactive.

    **Result:** A population that matches what the customer counts.

    <Warning>
      Which upstream value maps to which status varies by integration. Verify against one connector before relying on a status filter across all of them.
    </Warning>
  </Step>

  <Step title="Combine filters">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?employment_status=ACTIVE&work_locations=<LOCATION_ID>&page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Comma-separate multiple values on one parameter for `OR` within that field; separate parameters combine with `AND`.

    **Result:** A narrowed result set.
  </Step>

  <Step title="Fetch a known set by ID">
    When you already hold IDs - from a webhook payload, for instance - request them directly rather than filtering a full page walk.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?ids=019f618e-c850-716d-a510-74639514abf6,019f618e-c88c-7328-9575-ab78958608d2' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    **Result:** Only those records, in one request.
  </Step>
</Steps>

## If this didn't work

<AccordionGroup>
  <Accordion title="A filter returns nothing though records clearly exist">
    Filters are exact matches, not partial. `first_name=Jo` won't match `John`.

    For `remote_id` and `employee_number`, confirm the value against `raw_data` - the value shown in the HRIS UI is often not the identifier its API returns. See [Inspect raw data](/guides/reading-writing/raw-data).
  </Accordion>

  <Accordion title="employment_status returns fewer records than expected">
    Records with no upstream status carry `-` and are excluded by any specific status filter. Query `-` separately to see how many fall into that bucket.
  </Accordion>

  <Accordion title="The count doesn't match the customer's headcount">
    Usually a population-definition mismatch rather than missing data: contingent workers included, terminated employees retained, or one person holding several employment records.

    See [Record counts](/guides/troubleshooting/record-counts).
  </Accordion>

  <Accordion title="You need to filter on a field with no parameter">
    Two options. If the value is in `raw_data`, map it as a [custom field](/guides/extending/custom-fields) - though custom fields are returned, not filtered on, so you'd still filter client-side.

    Where the source system supports the filter natively, [Passthrough](/guides/extending/passthrough) reaches it directly at the cost of a provider-specific response shape.
  </Accordion>

  <Accordion title="You want to exclude records rather than include them">
    Filters are inclusive only. Fetch the statuses you want rather than excluding the ones you don't - several inclusive requests still beat paging everything.
  </Accordion>
</AccordionGroup>

## Fetching only what changed

`modified_after` returns only records **synced by Bindbee** after a given timestamp. That distinction matters more than it first appears - read the next section before building on it.

<Info>
  **Before you start**

  - You can persist a timestamp between runs, per connector.
</Info>

### What the timestamp actually means

`modified_after` filters on when Bindbee synced the record, not when the source system changed it.

Two consequences:

**A full resync makes everything look new.** After a resync, records re-synced during that run match `modified_after` even if nothing changed upstream. Your incremental read returns the whole dataset. Make downstream processing idempotent - an unchanged record must be safe to reprocess.

**Sync cadence is your true resolution.** A record edited in the HRIS is invisible until the next sync picks it up, so a 24-hour cadence means up to 24 hours of latency regardless of how often you poll. Polling more often than the connector syncs adds load without adding freshness.

### Steps

<Steps>
  <Step title="Capture a timestamp before you read">
    Record the current UTC time *before* issuing the request, and store it only after the run completes successfully.

    Taking it afterwards opens a window where records synced mid-run are never returned.

    **Result:** A watermark per connector.
  </Step>

  <Step title="Pass it as ISO 8601">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?modified_after=2026-08-13T00:00:00Z&page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    With no timezone offset the value is interpreted as UTC. Send an explicit `Z` rather than relying on that.

    **Result:** Only records synced after that instant.
  </Step>

  <Step title="Page with the filter held constant">
    Compute the timestamp once, before the loop, and reuse the identical string on every page. Recomputing it per page corrupts the cursor's position - see [Pagination](/api-reference/basics/pagination).

    **Result:** A complete, non-overlapping set.
  </Step>

  <Step title="Advance the watermark only on success">
    Persist the new timestamp after the full page walk succeeds. On failure, keep the old one and let the next run re-read the overlap.

    **Result:** Failures cost duplicate work, never lost records.
  </Step>
</Steps>

### Pairing it with webhooks

Polling on a fixed schedule means either reading too early, while a sync is still running, or waiting longer than necessary.

The more reliable pattern is to run the incremental read when the sync-completed event fires, using `modified_after` with your stored watermark. The event tells you data has landed; the filter tells you what's new. See [Trigger a job on completion](/guides/reading-writing/syncing).

### If this didn't work

<AccordionGroup>
  <Accordion title="An incremental read returned the entire dataset">
    Almost always a resync - everything was re-synced, so everything matches. Expected behaviour, not a bug. This is why idempotent processing matters.
  </Accordion>

  <Accordion title="A record you know changed didn't come back">
    Check the sync ran after the change. Until the connector syncs, the change doesn't exist in Bindbee - see [Sync status](/guides/troubleshooting/sync-status).

    On a Development connector there's no schedule at all, so nothing is new until you trigger a sync.
  </Accordion>

  <Accordion title="You're reading a related model that didn't update">
    `modified_after` is per model. An employee changing doesn't mark their employment or benefit records as synced, so filtering those separately can miss related changes. Where you need related records, either read them without the filter or subscribe to data-change events for the model.
  </Accordion>

  <Accordion title="You need to know what changed, not just which records">
    The filter returns current state, not a diff. To act on specific changes, compare against your own stored copy, or subscribe to the data-change events, which return the IDs of affected records per model.
  </Accordion>
</AccordionGroup>
