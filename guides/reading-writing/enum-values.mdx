title: "Enum values"
description: "Why normalisation collapses source values into a fixed set, and what arrives when a value does not fit."

An employee your customer classifies as "Active PT" arrives as `ACTIVE`. A pay period they call "Semi-Monthly (2nd/16th)" arrives as `SEMIMONTHLY`.

**Nothing was lost, exactly. It was set aside** - and where it could not be mapped at all, it arrives untouched.

## The enum is a documented set, not a constraint

A unified enum exists so your code can branch on known values rather than on strings it has never seen. Source vocabularies are unbounded: customers define their own statuses, pay period names and classifications to encode things their business cares about - division, contract type, shift pattern, broker.

None of that is expressible in a fixed set. So the enum is a projection, and values with a clear equivalent map into it.

<Warning>
Values without an equivalent are **passed through verbatim.** More than thirty enum fields say so in their own description: *"If the value is not one of the defined enum values, the original value passed through will be returned."*

The fields are typed as plain strings, so **the enum list documents what you can expect, not what you can receive.** A switch that assumes the documented set will meet values outside it.
</Warning>

That is the single most important thing about enums here, and it changes how you write the handler: you are matching against known values with a real default branch, not exhausting a closed set.

## Two values that are part of the set

Some enums carry explicit fallback members, and they are not the same thing as a pass-through.

| Value | Means | What it points at |
| --- | --- | --- |
| `OTHER` | The source has its own "other" category and used it | A deliberate choice upstream, not a mapping gap |
| `-` | No usable value came from the source - absent, empty or unset | Source configuration or permissions |

Neither appears on every enum. Gender, ethnicity and marital status carry both; employment status carries `-` and no `OTHER`; benefit plan category carries `OTHER` and no `-`. Group type carries neither.

**So a field can return four different kinds of thing**: a documented value, `OTHER`, `-`, or an arbitrary string from the source system.

<Info>
A high proportion of `OTHER` or of pass-through values on one integration is worth investigating rather than accepting. It usually means a mapping gap affecting every customer on that system, not just the one who reported it.
</Info>

## The original is in raw data, if you ask for it

Whatever the source system sent survives unmodified - but `raw_data` is **not returned by default.** You need `include_raw_data=true`, and the same is true of custom fields.

That is the recovery path when the enum is too coarse. If the local vocabulary carries meaning you need - full-time versus part-time encoded in a status, contract type encoded in a classification - read it from the payload and promote it into a custom field, then request it with `include_custom_fields=true`.

What you should **not** do is branch on the raw string directly, whether you read it from `raw_data` or receive it as a pass-through. That is integration-specific handling, and it breaks the moment a customer edits their vocabulary.

## Enums can gain values

The documented set is fixed at a point in time, not permanently. Values are added as coverage broadens and as source systems introduce concepts the model does not yet carry.

A value that passes through verbatim today may become a mapped enum value later - which is a second reason the default branch matters.

## Why it works this way

The alternative is to pass every source string through untouched, and it fails on its own terms.

Your code would handle "Active", "ACTIVE", "Active FT", "A" and "Currently Employed" as five separate cases, all meaning employed, varying by integration *and* by customer within an integration.

That is precisely the per-integration branching a unified API exists to remove. Mapping to a fixed set means one comparison works for the common cases.

**Passing the remainder through, rather than forcing it into a bucket, is the honest half of that trade.** Coercing an unmappable status into `-` or `OTHER` would destroy information while looking like a clean result. Returning the original says plainly that the model did not cover this one, and leaves the value recoverable.

Keeping `OTHER` and `-` distinct follows the same logic: one says the source made a choice, the other says the source said nothing, and they have entirely different fixes.

## What this means for you

- **Always write the default branch.** The documented set is not the set of possible values.
- **Never default an unrecognised value to a meaningful one.** Defaulting an unknown employment status to inactive can deprovision a working employee.
- **Treat `OTHER` and pass-through values as signals**, particularly when they cluster on one integration.
- **`-` points at source configuration or permissions**, not at a mapping gap.
- **Promote local vocabulary into a custom field** if you need it, and request it explicitly. Do not branch on raw strings.
