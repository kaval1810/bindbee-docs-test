Bindbee normalizes categorical fields into a fixed set of values, so `FULL_TIME` means the same thing whether the data came from Workday, BambooHR or Gusto. Thirty-eight fields work this way, including `employment_status`, `employment_type`, `pay_frequency`, `request_type` and `benefit_plan_category`.

The accepted values for each field are listed on that endpoint's reference page, next to the field itself. This page covers the rules that apply to all of them.

---

## Enums are open on read

Every one of these fields carries the same contract, stated in its own description in the API spec: **if Bindbee cannot map a source value to one of the defined values, the original value is passed through unchanged.**

An enum field can therefore return a value that is not in its documented list. A customer with a custom leave type called `SABBATICAL_2024` will surface exactly that string in `request_type`. `request_type` and `employment_status` see this most often, since both are usually configurable per employer.

```javascript
// Fragile. Throws or silently mislabels on any unmapped value.
switch (timeOff.request_type) {
  case "VACATION": return "Vacation";
  case "SICK":     return "Sick leave";
}

// Safe. Known values map cleanly, everything else degrades gracefully.
const LABELS = { VACATION: "Vacation", SICK: "Sick leave" };
const label = LABELS[timeOff.request_type] ?? titleCase(timeOff.request_type);
```

<Warning>
Do not put a hard enum constraint on these columns in your database. Use a string column and validate in your application layer, or a passthrough value will fail the write.
</Warning>

## What a value can actually be

A single enum field can return four different kinds of thing, and they mean different things:

| You get | Means | Points at |
|---|---|---|
| A documented value | The source value mapped cleanly | Nothing — the normal case |
| `OTHER` | The source has its own "other" category and used it | A deliberate choice upstream, not a mapping gap |
| `-` | No usable value came from the source | Source configuration or permissions |
| An undocumented string | No equivalent existed, so the original passed through | A mapping gap, or a customer's own vocabulary |
| `null` | The field was absent from the source payload entirely | The model carries it; this source does not |

Neither sentinel appears on every field. **Nineteen fields define `-`** and **eight define `OTHER`** — six carry both. `employment_status` has `-` and no `OTHER`; `benefit_plan_category` has `OTHER` and no `-`.

Rather than tracking which field has which, treat `-` and `null` as the same "unknown" case in your UI and you will be right every time.

<Info>
A high proportion of `OTHER` or of pass-through values on one integration is worth investigating rather than accepting. It usually means a mapping gap affecting every customer on that system, not just the one who reported it.
</Info>

## Filtering by enum

Enum filters match the stored value exactly, so match the casing and punctuation from the reference page. Most values use underscores, but four break that convention: `NON-BINARY`, `THIRTEEN-MONTHLY`, `APPROVAL-SENT` and `SENT-MANUALLY`.

**Enum filters are typed as plain strings, not as closed sets.** An unrecognised value returns an empty result set rather than a validation error, so an empty page is not proof the customer has no matching data — check your spelling first.

That openness is deliberate on `employment_status`, whose parameter description says connector-specific values may be passed too. **A value you can see in a response is a value you can filter on**, including one that arrived by pass-through.

What will not work is expecting a normalized filter to catch unmapped records. If you need those, query without the enum filter and bucket the values yourself.

See [Querying Data](/guides/reading-writing/querying-data) for how enum filters combine with `expand`, `modified_after` and pagination.

## Enums can gain values

The documented set is fixed at a point in time, not permanently. Values are added as coverage broadens and as source systems introduce concepts the model does not yet carry.

A value that passes through verbatim today may become a mapped enum value later — which is a second reason the default branch in your handler matters, and a reason not to store the enum as a database constraint.

When the local vocabulary carries meaning you need, the durable answer is not to branch on the raw string. Read the original from [raw data](/guides/reading-writing/raw-data), then promote it into a [custom field](/guides/extending/custom-fields) so it arrives as a stable, named value.
