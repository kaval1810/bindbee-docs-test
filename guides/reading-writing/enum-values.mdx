Every HR, payroll, ATS and LMS system describes the same concept in its own words. One marks a full-time employee as `Full-Time`, another as `FT`, another as a numeric type code. Consuming each provider directly means branching logic for every one of them.

An **enum value** is Bindbee's answer to that. For a set of fields on the unified models, Bindbee defines a fixed vocabulary and maps each provider's value into it during sync. Your application reads `FULL_TIME` regardless of which connector is behind the request.

Enum fields are the normalized layer. The provider's own value stays available through `include_raw_data=true` or through [custom fields](/guides/extending/custom-fields).

---

## How enum values are defined

**38 fields** across the unified models carry a defined vocabulary, and they follow the same conventions.

| Convention | Detail |
| --- | --- |
| Data type | Always a JSON string, never an integer or boolean |
| Casing | `UPPER_SNAKE_CASE`, for example `PAID_TIME_OFF`, `SEMIMONTHLY`, `HEAD_OF_HOUSEHOLD` |
| Nullability | Enum fields are nullable. `null` means the provider did not supply the field at all |
| Scope | Vocabularies are defined per field, not globally. `Benefit.frequency` and `Compensation.pay_period` describe similar ideas but use different value sets |
| Discovery | The accepted values for a field are listed under `enum` in the API reference for that model |

For example, `employment_status` on the Employee model resolves to one of:

```
ACTIVE   PENDING   INACTIVE   ACTIVE_EXTERNAL   INACTIVE_EXTERNAL
LEAVE    DECEASED  RETIRED    -
```

### Naming exceptions worth knowing

Most values are underscore separated, but a few use hyphens or short forms. Match on the exact string rather than assuming the pattern:

* `NON-BINARY` — `gender`
* `THIRTEEN-MONTHLY` — `Compensation.pay_frequency` and `Benefit.frequency`
* `APPROVAL-SENT` and `SENT-MANUALLY` — ATS `Offer.status`
* `A`, `B`, `C`, `D`, `F`, `PASS`, `FAIL` — LMS `Completion.grade`

### The `-` value

Several vocabularies include `-` as a defined member — **19 fields** carry it. Treat `-` as "present but not classifiable" and `null` as "not provided at all".

## How normalization works

Enum mapping happens during sync, before the data reaches your API call.

1. Bindbee fetches the raw object from the third-party system.
2. The connector maps the provider's value onto the unified vocabulary for that field.
3. If no mapping exists for that value, Bindbee returns the provider's original value, unchanged.
4. If the provider did not return the field at all, Bindbee returns `null`.

### Unmapped values

Step 3 is the single most important behaviour on this page. Bindbee never drops or guesses a value it cannot classify, so an enum field can legitimately return a string that is not in the documented list. **Forty-eight field descriptions in the API spec say so explicitly**, in the same sentence: *"If the value is not one of the defined enum values, the original value passed through will be returned."*

<Warning>
  Do not treat enum fields as a closed set. Every enum field is typed as a string in the schema precisely because unmapped values are expected. Code that throws on an unrecognized value will break the first time a connector returns a provider-specific term.

  The same applies to your database: use a string column, not a hard enum constraint, or a passthrough value will fail the write.
</Warning>

```javascript
// Handle documented values explicitly, and return anything else as-is.
function labelForEmploymentType(value) {
  switch (value) {
    case "FULL_TIME":  return "Full time";
    case "PART_TIME":  return "Part time";
    case "CONTRACTOR": return "Contractor";
    case "INTERN":     return "Intern";
    case "FREELANCE":  return "Freelance";
    case "REGULAR":    return "Regular";
    case "FURLOUGHED": return "Furloughed";
    case "TERMINATED": return "Terminated";
    case "-":          return "Not specified";
    case null:
    case undefined:    return "Unknown";
    default:           return value; // unmapped value from the provider
  }
}
```

A reasonable pattern is to store the raw string, render documented values through your own label map, and log unrecognized values so you can decide whether they need product handling.

A high proportion of unmapped values on one integration usually means a mapping gap affecting every customer on that system, not just the one who reported it. Worth raising.

### Inspecting the original value

To see what the provider actually returned, add `include_raw_data=true` to any list or retrieve request. The `raw_data` object contains the untouched upstream payload alongside the normalized fields — see [Raw Data](/guides/reading-writing/raw-data).

```bash
curl -G https://api.bindbee.dev/api/hris/v1/employees \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>" \
  -d include_raw_data=true
```

```json
{
  "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
  "employment_status": "ACTIVE",
  "marital_status": "SINGLE",
  "raw_data": {
    "employmentStatus": "Active",
    "maritalStatus": "S"
  }
}
```

## Filtering by enum values

Several list endpoints accept an enum field as a query parameter, for example `employment_status` on `GET /api/hris/v1/employees`, `employment_type` on `GET /api/hris/v1/employments`, and `status` on `GET /api/hris/v1/time-off`.

These filters accept the standard values **and** any connector-specific value that appears in the response. If a connector returns `Seasonal` on `employment_type`, you can filter on `Seasonal`.

```bash
curl -G https://api.bindbee.dev/api/hris/v1/employees \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>" \
  -d employment_status=ACTIVE
```

<Note>
  Filter values are matched as returned, so `ACTIVE` and `Active` are not interchangeable. Use the exact string from the response payload. An unrecognized value returns an empty page rather than a validation error, so an empty result is not proof the customer has no matching data — check the spelling first.
</Note>

See [Reading data](/guides/reading-writing/reading-data) for how enum filters combine with `expand`, `modified_after` and pagination.

## Enums can gain values

The documented set is fixed at a point in time, not permanently. Values are added as coverage broadens and as source systems introduce concepts the model does not yet carry.

A value that passes through verbatim today may become a mapped enum value later — a second reason the default branch matters, and a second reason not to store the enum as a database constraint.

---

## Best practices

* **Treat every enum field as an open string.** Match on documented values, fall back to the raw string, and never throw on an unrecognized value.
* **Distinguish `null`, `-`, and an unmapped value.** They mean "not provided", "provided but not classifiable", and "provider specific" respectively, and they often warrant different behaviour in your UI.
* **Log unrecognized values.** They tell you which connectors are surfacing terms your product does not handle yet, and they are a good input for a custom field or a mapping request.
* **Use `include_raw_data=true` while building.** It is the fastest way to confirm how a specific connector's values are being normalized.
* **Do not assume shared vocabularies.** Fields that look alike, such as `pay_period` and `pay_frequency`, use different value sets.
