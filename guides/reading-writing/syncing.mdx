Bindbee does not proxy your requests to the third-party system in real time. It syncs data from each connected system on a schedule, normalizes it into the unified models, and stores it. **Your API calls read from that stored copy.**

That is what makes reads fast and predictable: they are not subject to the provider's rate limits or downtime, and every response arrives in the same shape whichever system is behind it. The trade is that data is only as current as the last completed sync.

## The initial sync

```mermaid
flowchart LR
    A["Customer<br/>authorises"] --> B["Initial sync<br/>reads return partial data"]
    B --> C["Complete<br/>data is trustworthy"]
    C --> D["Recurring sync<br/>every 24h by default"]
    D --> C
```

The initial sync starts the moment your end user completes authentication, however the connection was created — see [How to connect](/get-started/how-to-connect). Until it finishes, reads return `200` with partial data and nothing on the response says so.

You can watch its progress on the connector. Note that this endpoint scopes by a **query parameter**, not the usual header:

```bash
curl -G https://api.bindbee.dev/api/hris/v1/connectors \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -d connector_token=<CONNECTOR_TOKEN>
```

```json
{
  "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
  "integration_slug": "ukg-pro",
  "end_user": "Acme Corp.",
  "status": "COMPLETE",
  "sync_status": "Syncing",
  "last_sync_start_time": "2026-08-29T00:00:00Z",
  "next_sync_start_time": "2026-08-30T00:00:00Z"
}
```

Two status fields appear here and they answer different questions:

| Field | Values | Describes |
| --- | --- | --- |
| `status` | `COMPLETE`, `INCOMPLETE`, `RELINK_NEEDED` | The link status of the connector |
| `sync_status` | `Syncing`, `Done`, `Failed` | The status of the most recent sync job |

A connector can be `COMPLETE` and still hold no data, because the two are independent.

<Tip>
  Rather than polling the connector, subscribe to the `connector_synced` [webhook](/guides/reading-writing/webhooks). It fires when a sync job finishes successfully, which is the cleanest signal that a newly connected account is ready to use in your product.
</Tip>

## The recurring schedule

After the initial sync, a Production connector syncs again automatically, **once every 24 hours by default**. Nothing is required from you or your end user. The interval is configurable — see [Sync frequency](/api-reference/basics/sync-frequency) for the available cadences and how the start time is set.

`last_sync_start_time` is when the most recent job began; `next_sync_start_time` is when the next scheduled one will.

Every webhook payload carries a `sync` object identifying the job behind it, and `sync_type` is `AUTOMATED` for a scheduled run or `MANUAL` for one you triggered. That distinction is worth using: if you force a sync in response to a user action, you can match the resulting webhook back to that action rather than treating it as routine traffic. See [Events & payloads](/guides/reading-writing/webhooks).

<Note>
  Frequency bounds when data *changes*, not how often you can read. Call the API as often as you like within your [rate limits](/api-reference/basics/rate-limits) — the data simply will not differ between syncs.
</Note>

## Development connectors

Development connectors run the same initial sync as Production ones: it starts on authorisation and needs nothing from you. What they do not have is the **recurring** schedule that follows it. After that first run the data is frozen until you trigger a sync yourself.

This is the single most common source of "the data looks stale" during development. See [Environments](/get-started/environments) for everything else the two differ on.

## Forcing a resync

When you need data sooner than the next scheduled run — and always, in Development, after the first one:

```bash
curl -X POST https://api.bindbee.dev/api/embedded/v1/connectors/resync \
  -H "Authorization: Bearer <BINDBEE_API_KEY>" \
  -H "X-Connector-Token: <CONNECTOR_TOKEN>"
```

Unlike the connector list above, this endpoint scopes by header. To know when the data has landed, listen for `connector_synced` or poll `sync_status` until it returns to `Done`.

Reasonable moments to force one:

* Your end user just changed something in their HRIS and expects to see it in your product straight away.
* You completed a write and want the unified models to reflect it before the next scheduled run — writes reach the source system directly, so they are not readable until a sync picks them up.
* You changed a [custom field](/guides/extending/custom-fields) mapping and want it populated against existing records.
* You are investigating a discrepancy for one customer.

<Warning>
  Force sync is not a substitute for a higher sync frequency. Triggering it on every page load, or on a loop, puts avoidable load on the provider's API — the exact problem the sync model exists to solve. If you consistently need fresher data, change the cadence instead.
</Warning>

## Triggering a job on completion

Reading on a timer instead goes wrong in four ways: a paginated walk shifts under you mid-sync, counts come back short, a census extract is quietly incomplete, and a stalled connector looks identical to a quiet one.

Gate the work on `connector_synced` rather than a clock. The event names the connector and the sync job, so a handler can process exactly what finished — and pair it with `modified_after` to read only what that run touched, as in [Querying Data](/guides/reading-writing/querying-data).

For creating the subscription, the payload shape and delivery guarantees, see [Webhooks](/guides/reading-writing/webhooks).

## When a sync fails

A failed job sets `sync_status` to `Failed` and fires the `connector_sync_error` webhook, whose payload carries an `error` object with the failure time and a summary.

**Previously synced data stays readable throughout.** A failure means your copy is stale, not missing — which is also why a broken connector does not announce itself on your reads, and has to be watched separately. See [Monitor sync status](/guides/troubleshooting/sync-status) for what to alert on and how to diagnose a specific failure.

If `status` has become `RELINK_NEEDED`, the credentials themselves stopped working and your end user must reconnect before syncing resumes — see [Connections to relink](/guides/troubleshooting/connections-to-relink).
