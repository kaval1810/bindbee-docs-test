Passthrough sends a request to the source system's own API using the credentials already held on a connector. **Bindbee handles authentication and routing; everything else is that system's.**

It is the answer to "the unified model does not cover this", and it is worth being precise about what it costs, because it is easy to reach for and hard to back out of.

## What it gives you

Authentication is the genuinely hard part of talking to an HR system directly, and passthrough removes it entirely - no credential handling, no OAuth refresh, no per-system auth scheme, nothing sensitive stored on your side.

Your customer authorised once, and passthrough reuses that.

You get the source system's full API surface - every endpoint, every field, every operation that system supports, including ones the unified model has no equivalent for.

**It is not limited to JSON.** Requests go as `XML` or `MULTIPART`, responses come back as `XML`, `MULTIPART` or `BINARY`.

That matters because the systems most likely to need passthrough are the older enterprise platforms that speak SOAP and return files - precisely where unified coverage is thinnest.

## What you give up

**Normalisation.** The response is that system's shape. Your code parses it specifically, and a customer on a different system needs different code.

**Portability.** This is the real cost. A passthrough call works for one integration. Supporting the same capability across ten integrations means ten implementations, which is precisely the position a unified API exists to avoid.

**Scope and custom fields.** Neither applies. Passthrough returns whatever the endpoint returns, unfiltered by your scope configuration and without custom field mappings.

**Sync and storage.** The response is not stored, not synced, not available on later reads. Passthrough is a live call, subject to the source system's latency, rate limits and availability - if it is down, your call fails.

**Stability.** The source system's API can change without notice. A unified model change would be versioned and communicated; a passthrough integration breaks when the vendor decides it does.

<Warning>
Passthrough calls count against the **source system's** rate limits, which are typically far tighter than Bindbee's. A passthrough call in a per-user request path, or in a loop, will exhaust the customer's quota and can disrupt syncing for that connector.
</Warning>

## When it is the right choice

**A field or object with no unified equivalent**, where the need is genuinely specific to one system and one customer.

**A write the unified surface does not support** - updates, deletions, or models with no create endpoint.

**One-off or low-volume operations**, particularly administrative ones, where writing integration-specific code once is cheaper than waiting for coverage.

**Bridging a gap while coverage catches up**, with the intention of removing it later.

## When it is not

If the requirement is a field you need on every record, passthrough is the wrong instrument - a custom field brings the value into the unified model, syncs with everything else, and stays portable.

If you find yourself writing passthrough calls for several integrations to accomplish one capability, that is a signal to raise a coverage gap rather than to keep going. The second implementation is usually the point at which the unified path becomes cheaper.

## Why it works this way

**The escape hatch exists because the alternative is worse.** Without one, a team with a legitimate one-off need has two options: drop the requirement, or build a second integration alongside Bindbee - their own credential handling, their own OAuth refresh, their own storage of HR credentials.

Passthrough keeps the case inside the platform instead. Credentials stay where they are, the customer's authorisation still governs access, and no parallel integration appears.

**It is unnormalised on purpose.** A passthrough call visibly returns one system's shape, so the cost is obvious as you write it.

Smooth that over and it stops reading as an escape hatch and starts reading as a slightly rougher unified API - which is how it would accumulate usage until portability quietly stopped being true.

## What this means for you

- **Keep passthrough out of hot paths.** It is a live upstream call against tight rate limits.
- **Prefer a custom field** when the need is a value on every record.
- **Isolate passthrough code** behind an interface, so replacing it with unified support later is contained.
- **Treat the second integration-specific implementation as a signal** to raise a coverage gap.
- **Expect it to break without warning.** The source API is not under contract with you.

## Making a request

Passthrough forwards a request to the underlying source system using the connector's stored credentials. Bindbee handles authentication; everything else - path, body, response shape - is the provider's.

Use it for gaps, not as a default. Passthrough responses aren't unified, so every one you depend on is provider-specific code you maintain.

<Info>
  **Before you start**

  - You've confirmed the unified API doesn't cover this - see [Check write support](/guides/reading-writing/meta-apis).
  - You have the source system's own API documentation for the endpoint.
</Info>

### Steps

<Steps>
  <Step title="Find the provider's endpoint">
    Work from the source system's own documentation. You need the path, method, and body it expects - Bindbee doesn't validate or transform these.

    **Result:** A provider-specific request you can describe.
  </Step>

  <Step title="Send it through Passthrough">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/v1/passthrough' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>' \
      --header 'Content-Type: application/json' \
      --data '{
        "method": "GET",
        "path": "/v1/companies/current/paygroups",
        "headers": {}
      }'
    ```

    The base URL, authentication, and any token refresh are handled from the connector. `headers` is required even when empty - omitting it returns `422`. See [Make Passthrough Request](/api-reference/passthrough/make-passthrough-request) for the exact request shape.

    **Result:** The provider's raw response.
  </Step>

  <Step title="Handle the response as provider-specific">
    You get the source system's own response shape, not a unified model. Field names, casing, pagination, and error format are all theirs, and differ between integrations.

    Write handling per integration rather than trying to generalise across them.

    **Result:** Data your code understands.
  </Step>
</Steps>

### Where Passthrough genuinely earns its place

| Case | Why |
| --- | --- |
| Sourcing an `integration_params` value | Pay groups, statement types, and location codes often live only in provider configuration endpoints |
| Validating a code before a write | Confirming a deduction code exists beats a rejected payroll write |
| A write with no unified equivalent | Where the model isn't supported yet |
| A provider-native filter | Where the source system supports narrowing the unified API doesn't expose |

<Warning>
  Passthrough is not the answer to a field missing from a read. If the value is in the synced payload, map it as a [custom field](/guides/extending/custom-fields) - that keeps it in the unified response, works across connectors, and survives provider API changes. Passthrough is for things genuinely outside what Bindbee syncs.
</Warning>

### Writes through Passthrough are on you

Passthrough does not accept an idempotency key. A retried write goes straight through to the provider and creates a second record.

Where you're writing, build your own protection: check whether the record exists before creating it, or use whatever idempotency mechanism the provider offers natively. Don't retry blind.

### If this didn't work

<AccordionGroup>
  <Accordion title="404 from the provider">
    The path is wrong for this account. Provider paths vary by API version, region, and tenant - some embed a tenant or company identifier that differs per customer. Check the provider's docs for the version this integration authenticates against.
  </Accordion>

  <Accordion title="401 or 403 from the provider">
    The connector's credentials authenticate but lack access to that endpoint. Passthrough grants no more access than the connection has - see [Permission errors](/guides/troubleshooting/permission-errors).
  </Accordion>

  <Accordion title="The same request works on one connector and not another">
    Expected. Provider APIs vary by the customer's plan tier, enabled modules, and configuration. Passthrough code needs per-connector fallbacks in a way unified endpoints don't.
  </Accordion>

  <Accordion title="You're using Passthrough for something on every request">
    That's a signal the unified API should cover it. Raise it - a supported model or write is more maintainable than provider-specific code paths, and it's how coverage gets prioritised.
  </Accordion>

  <Accordion title="Provider rate limits">
    Passthrough consumes the customer's own quota with the provider, on top of Bindbee's [rate limit](/guides/api-basics/rate-limits). Heavy use can affect the connector's own syncs.
  </Accordion>
</AccordionGroup>
