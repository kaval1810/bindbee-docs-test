Something did not work. Before you can fix it you need to know whose failure it was — **yours, Bindbee's, or the source system's.** Those three arrive through different channels and look nothing like each other.

## Three origins, three channels

| Origin | How it reaches you | Where the detail is |
| --- | --- | --- |
| **Your request was wrong** | A `4xx` on the response | `detail` in the response body |
| **The source system refused** | Not on your response at all - it happens during a sync | [Connector logs](/guides/troubleshooting/logs), or a [sync-status webhook](/guides/reading-writing/webhooks) |
| **Nothing failed** | `200`, well-formed, data absent | Nowhere - it is [scope or permissions](/get-started/scoping) |

The middle row is the one that catches people. **A source-system failure does not surface on the request you just made.** Bindbee holds a synced copy, so an upstream refusal happened in the background — possibly hours earlier — and your read succeeds against whatever was last stored.

## Classify the status

Errors fall into three groups: fix the request, back off and retry, or act on the connection. Retrying everything, or failing on everything, causes the two most common integration problems.

| Status | Meaning | Retry? |
| --- | --- | --- |
| `401` | Missing, malformed, or wrong-environment API key | No - fix credentials |
| `403` | Valid credentials without access to this resource | No - see below |
| `404` | Resource doesn't exist for this connector | No |
| `422` | Validation failed - an invalid query or path parameter, or a write body the schema rejects | No - the body names the field |
| `429` | Rate limit exceeded | Yes, after `Retry-After` |
| `5xx` | Server-side | Yes, with backoff |

Retrying a `4xx` other than `429` will never succeed, and consumes the connector's rate limit while failing.

<Note>
  `422` is not a write-only code. A bad query parameter on a read returns `422`,
  not `400` - so a filter value the API rejects lands in the same branch as a
  malformed write body.
</Note>

## Read the response body, not just the status

Every error carries a `detail` field, and **its type depends on the status.** On `401`, `403`, `404` and `429` it is a string:

```json
{ "detail": "Rate limit exceeded" }
```

On `422` it is an array, one entry per rejected field — here, a `page_size` above the maximum of 200:

```json
{
  "detail": [
    {
      "loc": ["query", "page_size"],
      "msg": "Input should be less than or equal to 200",
      "type": "less_than_equal"
    }
  ]
}
```

`loc` is the path to the offending field and `msg` says what was expected. Together they usually identify the fault without further digging.

<Warning>
  The same key holds two different types. Code that treats `detail` as a string
  - logging it, matching on it, lower-casing it - works against every other
  status and then throws on the first `422`. Branch on the status before
  touching `detail`.
</Warning>

## The two causes of 403

A `403` means the credentials are valid but don't permit this resource. Two very different situations produce it:

- **A connector token used against the wrong API category** — an HRIS connector called on `/api/ats/v1/*`. That's a bug in your code.
- **A model whose writes are disabled for that integration** — see [Check write support](/guides/reading-writing/writing-data/meta-apis).

Neither is retryable, and neither is a source-system permission problem — those surface as sync failures or empty results rather than `403`. See [Permission errors](/guides/troubleshooting/permission-errors).

## Retry safely

**On `429`,** wait `Retry-After` seconds. Don't retry immediately, and don't use a fixed delay — the header is authoritative. Better still, watch `X-RateLimit-Remaining` on successful responses and slow down before you reach zero. The limit is [200 requests per minute per connector](/api-reference/basics/rate-limits), counted against the connector token rather than the API key, so parallelising across customers is fine; hammering one customer's connector is what trips it.

**On `5xx`,** retry with exponential backoff and jitter, capped at a few attempts. Jitter matters when many connectors fail together — without it, every client retries in lockstep.

```python Python
import random, time, requests

RETRY_ON = {429, 500, 502, 503, 504}

def request_with_retry(method, url, *, max_attempts=4, timeout=30, **kwargs):
    for attempt in range(max_attempts):
        # Without a timeout a hung connection never reaches the retry logic
        resp = requests.request(method, url, timeout=timeout, **kwargs)
        if resp.status_code not in RETRY_ON:
            return resp
        if attempt == max_attempts - 1:
            resp.raise_for_status()

        # 429 tells you how long to wait; 5xx does not, so back off
        retry_after = resp.headers.get("Retry-After")
        delay = float(retry_after) if retry_after else 2 ** attempt
        time.sleep(delay + random.uniform(0, 0.5))   # jitter
```

Log the status, response body, `X-RateLimit-Remaining`, connector ID and endpoint on every failure. A `403` without the endpoint is nearly undiagnosable later.

<Warning>
  Retrying a write is only safe with an idempotency key. A `5xx` can be returned
  after the record was already created upstream, so a retry without
  `X-Idempotency-Key` creates a duplicate in the customer's HRIS. Send the same
  key on the retry that you sent on the original request - see
  [Employee](/get-started/use-cases/create-an-employee).
</Warning>

## An empty result is not an error

The failure mode that costs most is a `200` with no records. Permission gaps, out-of-scope models and stalled syncs all present this way, and code that only branches on status treats it as "the customer has no employees".

Where a zero count is implausible, check sync status rather than assuming absence — see [Missing records](/guides/troubleshooting/missing-or-extra-records).

## Upstream failures keep the source system's own answer

When Bindbee's request to the HRIS fails, the record of it preserves the source system's response rather than a Bindbee interpretation: the upstream status, the endpoint called, and the response body unmodified.

Read that body first. It arrives in whatever format the HR system uses — BambooHR a structured problem document, Dayforce its own process-result codes inside a `403`, Workday SOAP faults. **None of it is normalised, and that is deliberate:** collapsing *"the Workday integration system user lacks Get_Workers permission on this security group"* into `PERMISSION_DENIED` would throw away the one sentence that tells an administrator what to change.

The same applies to writes, which fail for business reasons rather than structural ones — a time-off request rejected for insufficient balance, a hire rejected because a tenant requires a custom field, a payroll entry rejected because the period is closed. Bindbee cannot evaluate those in advance, so your user-facing messages for write failures cannot be fully generic.

<Warning>
An upstream `403` almost always means the authorising credentials lack a permission - not that Bindbee is unauthorised. **The fix is with your customer's HRIS administrator, not with your API keys.**
</Warning>

## Where background failures show up

A sync that fails partway through never reaches your response. Two surfaces record it:

- **[Logs](/guides/troubleshooting/logs)** — the per-request record: which endpoint, which status, what came back.
- **Issues** — the layer above. Where a log entry is one request, an issue is a failure Bindbee raised against a connector with a likely cause attached. See [Platform](/get-started/platform).

<Warning>
Both are Dashboard surfaces. **There is no issues endpoint and no connector logs endpoint**, so anything your own monitoring acts on has to come from sync-status webhooks or the connector's `status` - see [How connections work](/get-started/how-to-connect).
</Warning>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="401 with a key you're sure is correct">
    Environment mismatch - a Development key against a Production connector returns `401` rather than a clearer error. See [Authentication](/api-reference/basics/authentication).

    Also check the header includes the `Bearer ` prefix.
  </Accordion>

  <Accordion title="429 despite low request volume">
    The limit is per connector. Several of your services calling the same connector share one budget, and a page walk at `page_size=50` uses four times the requests of one at 200.
  </Accordion>

  <Accordion title="Intermittent 5xx on one integration only">
    May reflect the source system rather than Bindbee. Capture the connector ID and timestamps and report it - the pattern across connectors on the same integration is what identifies it.
  </Accordion>

  <Accordion title="422 on a write that matches the schema">
    The schema is the structural contract; the source system enforces rules beyond it - codes that must exist in their configuration, closed periods, approval states. See [Fetch a schema](/guides/reading-writing/writing-data/meta-apis).
  </Accordion>
</AccordionGroup>
