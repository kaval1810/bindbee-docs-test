"Missing" has five distinct causes, and they need different fixes. Work through them in this order - each is cheaper to check than the next.

<Info>
  **Before you start**

  - You have something identifying the record: a name, work email, employee number, or the source system's own ID.
</Info>

## Steps

<Steps>
  <Step title="Rule out your own filters">
    Fetch without filters and search the result before anything else.

    The usual culprits: an `employment_status` filter excluding a status you didn't expect, a `modified_after` watermark from a run that already consumed the record, or a page walk that terminated early. See [Pagination](/guides/api-basics/pagination).

    **Result:** You know whether the record is absent or just filtered out.
  </Step>

  <Step title="Check the sync ran after the record was created">
    A record created upstream after the last sync doesn't exist in Bindbee yet - see [Sync status](/guides/troubleshooting/sync-status).

    On a Development connector nothing syncs until you trigger it.

    **Result:** You know whether the data has had a chance to arrive.
  </Step>

  <Step title="Check whether the model synced">
    A run marked Partial loads some models and fails others. A model that failed returns nothing while everything else looks fine - see [Partial syncs](/guides/troubleshooting/partial-syncs).

    A model out of scope also returns nothing, with no error at all - see [Restrict what syncs](/get-started/scoping).

    **Result:** You know whether the model was loaded.
  </Step>

  <Step title="Check permission">
    Many platforms return a filtered set rather than an error when credentials lack access, so an entire category of records can be silently absent.

    The signature is a model returning consistently fewer records than expected, or a specific population missing - see [Permission errors](/guides/troubleshooting/permission-errors).

    **Result:** You know whether the source system is withholding the record.
  </Step>

  <Step title="Check whether it's excluded upstream">
    If everything above is clean, the record may not be returned by the source system's API at all.

    Common causes: the record sits outside the scope of the report or endpoint the integration reads; it's in a status the source excludes from its API; or it belongs to a legal entity, company, or population the connected credentials don't cover.

    Query the source system directly through [Passthrough](/guides/extending/passthrough) to confirm whether their API returns it at all. That single check separates a Bindbee problem from a source-system one.

    **Result:** A definitive answer about where the record stops.
  </Step>
</Steps>

## Records that were there and disappeared

Different problem, different causes.

**Terminated employees** are usually still returned with a terminal status rather than removed. If they've vanished entirely, the source may exclude terminated records from its API - that's an upstream behaviour, not a sync failure.

**Identifier changes.** If the source reissued the record's identifier, it may now be present under a different Bindbee `id` and look like a disappearance plus a new arrival - see [Unexpected records](/guides/troubleshooting/missing-or-extra-records).

**File-based connectors.** Where the integration reads files rather than an API, each delivery is a point-in-time snapshot. A record absent from the latest file may mean it was removed upstream, or that the file was generated differently - a report definition change, a filter, a partial export. Confirm which before treating absence as a deletion.

## If this didn't work

<AccordionGroup>
  <Accordion title="The record appears in raw_data but not the unified response">
    It synced but didn't map to a unified record - usually a required field the unified model needs is absent upstream. Report it with the connector ID and the raw payload.
  </Accordion>

  <Accordion title="It appears for one connector and not another at the same company">
    Connectors are independent, and credentials often differ in the populations they cover - different legal entities, companies, or permission scopes.
  </Accordion>

  <Accordion title="It's missing from a related model only">
    Models sync independently. An employee can exist while their employment, benefit, or dependent records don't - because that model failed, is out of scope, or genuinely has no record upstream.
  </Accordion>

  <Accordion title="Counts are close but not exact">
    That's reconciliation rather than a missing record, and usually a population-definition difference. See [Record counts](/guides/troubleshooting/record-counts).
  </Accordion>
</AccordionGroup>

## Unexpected or duplicate records

Most apparent duplicates aren't duplicates. Work out which of these you have before trying to fix it - the remedies are different and the wrong one makes things worse.

<Info>
  **Before you start**

  - You have the Bindbee `id` of each record involved. Two records with the same `id` is a different problem from two records for the same person.
</Info>

### Steps

<Steps>
  <Step title="Check whether it's two employments, not two employees">
    An employee is a person; an employment is a job. One person legitimately has several employments - a rehire, a transfer, a promotion, or two concurrent roles.

    Systems that terminate-and-recreate on transfer produce several employment records for one continuous tenure. If you're joining employees to employments and rendering the result, one person appears once per employment.

    Fetch employees alone and count. If the duplication disappears, this is your answer - and the fix is selecting the right employment rather than deduplicating people. See [Reading employees](/guides/data-models/employee-and-org).

    **Result:** You know whether you have one person or two records.
  </Step>

  <Step title="Compare the identifiers">
    For two employee records that look like the same person, compare `id`, `remote_id`, and `employee_number` across both.

    | Pattern | Meaning |
    | --- | --- |
    | Different `remote_id` | Two distinct records upstream - the duplication is in the source system |
    | Same `remote_id`, different `id` | Identity drift on the Bindbee side - report it |
    | Same `employee_number`, different `remote_id` | Employee numbers aren't unique on this platform; don't key on them |

    **Result:** You know which side the duplication is on.
  </Step>

  <Step title="Check the raw payload">
    Fetch `raw_data` for both records - see [Inspect raw data](/guides/reading-writing/raw-data).

    Two genuinely distinct upstream records means the source system holds two, and the fix belongs in the customer's HRIS. This is common after a merger, a payroll migration, or a rehire processed as a new person.

    **Result:** Confirmation of what the source actually returns.
  </Step>

  <Step title="Check whether you created it">
    If you write to this connector, a duplicate may be yours - a retried write without a consistent idempotency key creates a second record.

    Check the creation timestamps against your own write logs. See [Employee](/get-started/use-cases/create-an-employee).

    **Result:** You know whether the duplicate originated with you.
  </Step>
</Steps>

### Records you didn't expect at all

| Symptom | Usual cause |
| --- | --- |
| More people than the customer's headcount | Contingent workers and contractors, commonly `ACTIVE_EXTERNAL` |
| Former employees | Terminated records persist with a terminal status; filter on `employment_status` |
| People from another business unit | The credentials cover more legal entities or companies than expected - filter on `company_id` |
| Records with almost no fields populated | Partially provisioned upstream, or a sync that loaded the employee but not related models |
| Test or system accounts | Present in the source system; filter them out on a stable attribute |

### Preventing the version you cause yourself

**Key on the Bindbee `id`.** Not `remote_id`, not `employee_number`. Some source systems reissue their identifiers on rehire, transfer, or record merge - keying on them creates duplicates in *your* system when the upstream ID changes.

**Send idempotency keys on writes**, derived from your own record identity rather than randomly.

**Don't delete and recreate connectors.** That discards record identities and produces an entirely new set of IDs, which looks like every record was duplicated - see [Rename or delete](/get-started/platform).

### If this didn't work

<AccordionGroup>
  <Accordion title="The same remote_id appears under two Bindbee IDs">
    That shouldn't happen within one connector. Check both records belong to the same connector - IDs are per connector, so the same person across two connectors legitimately has two. If it's one connector, report it with both IDs.
  </Accordion>

  <Accordion title="Duplicates appeared after a resync">
    A resync shouldn't create duplicates; it refreshes existing records. If it did, the upstream identifier likely changed during the window, so the record was treated as new. Compare `remote_id` values before and after.
  </Accordion>

  <Accordion title="A rehired employee appears twice">
    Depends on the source system. Some reuse the original record; others create a new one. Where they create a new one, both are genuine upstream records and the customer's HR team owns the merge.
  </Accordion>

  <Accordion title="Duplicates only in your system, not in reads">
    Your ingestion is creating them - usually keying on a mutable identifier, or reprocessing without idempotency. A resync makes every record match an incremental filter, which is when this surfaces.
  </Accordion>
</AccordionGroup>
