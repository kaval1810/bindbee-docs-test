Every request between Bindbee and a source system is recorded. **When something is wrong but nothing in your own application errored, look here** — a sync fails in the background and never reaches your response.

## Where to find them

Open **Logs** in the dashboard for the whole account, or open a single connector for just that customer. The second is almost always faster.

## What an entry holds

| Field | Holds |
| --- | --- |
| **Direction** | `READ` or `WRITE` |
| **Connector** | Which customer's connection the request belongs to |
| **Endpoint** | The path called, on Bindbee or on the source system |
| **Status** | The response code, and the error code where there is one |
| **Request & response** | The full bodies. Open an entry to expand them |

<Warning>
  **Read the upstream response body first.** When Bindbee's request to the HRIS fails, the log keeps the source system's own answer rather than a Bindbee summary of it. That body usually names the exact permission or field at fault. See [Errors & issues](/guides/troubleshooting/errors-and-issues).
</Warning>

## Find an answer

| Question | Where to look |
| --- | --- |
| Why is this connector not returning benefits? | `READ` entries for the benefits endpoint. A `403` means permissions; no entry at all means scope |
| Why did my write fail? | The `WRITE` entry, then the source system's response body. Writes fail for business reasons |
| Did the sync run at all? | No entries in the window, checked against [Sync status](/guides/troubleshooting/sync-status) |
| Which model broke a partial sync? | The first upstream error in the run. See [Partial syncs](/guides/troubleshooting/sync-status#diagnose-a-partial-sync) |

## Connector logs are dashboard-only

There is no API for them. Anything your own monitoring acts on has to come from sync webhooks or the connector's `status` and `sync_status` fields — the same constraint that applies to Issues.

**Webhook delivery logs are a different thing.** They record Bindbee's attempts to reach *your* endpoint, so they answer why your handler did not fire, not why data is wrong. Unlike connector logs, they do have an API: [List Webhook Logs](/api-reference/webhooks/list-webhook-logs) and [Get Webhook Log Detail](/api-reference/webhooks/get-webhook-log-detail).

## What logs cannot tell you

- **Why a field is empty.** A `200` with the field absent leaves no error to find. That is scope, permissions, or the unified model not carrying it — see [Scoping](/get-started/scoping).
- **That a record was deleted upstream.** A disappearance produces no request, so no entry.
- **How far back they go.** The retention window is not published, so treat logs as a tool for recent debugging rather than an audit trail.
