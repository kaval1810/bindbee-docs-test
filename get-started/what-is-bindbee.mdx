---
title: "What is Bindbee?"
description: "One API and one data model for reading and writing HR, payroll, ATS and LMS data across the systems your customers already run."
---

Your customers keep their people data in whatever system they already bought - BambooHR, ADP, Workday, Paycom, or a smaller payroll provider. Your product needs the same employee record out of all of them.

Bindbee sits between those systems and yours. You integrate once, against one API and one data model. Each customer connects their own system, and their data reaches your code in the same shape no matter where it came from.

## Reading and writing

Most integrations start by reading: Bindbee pulls from the source system,
normalizes it, and serves it through the unified API.

Bindbee writes back too. Write coverage grows model by model, so check the API
reference for what's supported today.

Every integration runs through the same five stages, in this order.

| | Stage | What happens |
| --- | --- | --- |
| **1** | **Scope** | You declare which models and fields you want. |
| **2** | **Connect** | Your customer authorizes their HR system, creating a connector. |
| **3** | **Sync** | Bindbee pulls from the source and normalizes it. |
| **4** | **Read** | You call the unified API and get normalized records back. |
| **5** | **Stay current** | Webhooks notify your app the moment something changes. |

The tutorial walks all five against a test account, before you point anything at
a real customer.

## What Bindbee is not

- **Not a system of record.** Bindbee reads from and writes to your customer's HR system. It does not replace it, and it does not run payroll.
- **Bounded by the source.** If a field doesn't exist in the source system, or the customer's admin didn't grant access to it, it won't appear in the unified model — and it's absent rather than an error.
