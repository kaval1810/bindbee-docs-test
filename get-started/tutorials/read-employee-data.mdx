This is the payoff: one request, both tokens, real records.

**By the end of this lesson** you will be reading unified employee records in your own code, paging through them and filtering by what changed.

## Context

You now hold both tokens - the Development API key from [lesson 1](/get-started/tutorials/set-up-your-environment) and the connector token from [lesson 3](/get-started/tutorials/connect-a-test-account). Every request below carries both.

## Step 1 - Fetch employees

`include_raw_data=true` asks for the original source-system payload alongside the normalized record. It is off by default; [lesson 6](/get-started/tutorials/add-a-custom-field) needs it, so turn it on now.

<CodeGroup>

```bash cURL
curl -G https://api.bindbee.dev/api/hris/v1/employees \
  --header "Authorization: Bearer $BINDBEE_API_KEY" \
  --header "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "include_raw_data=true" \
  --data-urlencode "page_size=10"
```

```python Python
import os, requests

resp = requests.get(
    "https://api.bindbee.dev/api/hris/v1/employees",
    headers={
        "Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}",
        "X-Connector-Token": os.environ["CONNECTOR_TOKEN"],
    },
    params={"include_raw_data": True, "page_size": 10},
)
resp.raise_for_status()
for employee in resp.json()["items"]:
    print(employee["display_full_name"], employee["work_email"])
```

```javascript Node
const url = new URL("https://api.bindbee.dev/api/hris/v1/employees");
url.searchParams.set("include_raw_data", "true");
url.searchParams.set("page_size", "10");

const res = await fetch(url, {
  headers: {
    Authorization: `Bearer ${process.env.BINDBEE_API_KEY}`,
    "X-Connector-Token": process.env.CONNECTOR_TOKEN,
  },
});

if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);

const { items } = await res.json();
for (const employee of items) {
  console.log(employee.display_full_name, employee.work_email);
}
```

## Step 2 - Read the response envelope

Every list response has the same three top-level keys.

| Key | Meaning |
| --- | --- |
| `items` | The records |
| `cursor` | Pass back as `?cursor=` for the next page |
| `page_size` | How many records this page holds |

Two identifiers appear on every record, and confusing them causes real bugs:

- **`id`** - Bindbee's identifier. Stable, consistent in shape across every system. Store this one.
- **`remote_id`** - the source system's own identifier. Useful for reconciliation and support conversations, but its format varies by system.

**Result:** you know which field to key your own records against.

## Step 3 - Page through results

```bash
curl "https://api.bindbee.dev/api/hris/v1/employees?page_size=200&cursor=YOUR_CURSOR" \
  --header "Authorization: Bearer $BINDBEE_API_KEY" \
  --header "X-Connector-Token: $CONNECTOR_TOKEN"
```

`page_size` defaults to 50 and maxes out at 200. Keep requesting until a page returns no cursor. See [Pagination](/api-reference/basics/pagination).

**Result:** every record in the tenant, not just the first page.

## Step 4 - Fetch only what changed

After the first full pull, most integrations only want deltas.

```bash
curl "https://api.bindbee.dev/api/hris/v1/employees?modified_after=2026-08-01T00:00:00Z" \
  --header "Authorization: Bearer $BINDBEE_API_KEY" \
  --header "X-Connector-Token: $CONNECTOR_TOKEN"
```

`modified_after` filters on when Bindbee last synced the record, not when the source system changed it.

**Result:** a smaller response containing only recently synced records.

## What you just did

You read normalized data that will keep the same shape regardless of which system is on the other end.

Notice the `raw_data` object on every record - the original payload from the source system, before normalization. You are not meant to read your product's data out of it, since its shape changes by system and version, which is exactly what the unified model protects you from. It has one job: showing you what the source system actually sent, so you can find values the unified model does not carry.

That is lesson 6.

## If this didn't work

<AccordionGroup>
  <Accordion title="Empty items array">
    Almost always no completed sync. Development connectors do not sync
    automatically - go back to [lesson 4](/get-started/tutorials/run-your-first-sync).
  </Accordion>

  <Accordion title="401 or 403">
    `401` means the API key is wrong. `403` usually means `X-Connector-Token` is
    missing or belongs to a different environment.
  </Accordion>

  <Accordion title="Records are there, but a field you expected is missing">
    Check in this order: is the field in [scope](/get-started/tutorials/scope-your-data);
    did the source system grant permission for it; does the unified model carry
    it at all. Look in `raw_data` - if the value is there, it is the third case
    and lesson 6 solves it. If it is not there either, it is one of the first two.
  </Accordion>

  <Accordion title="Data looks stale">
    In development, data is only as fresh as your last manual resync.
  </Accordion>
</AccordionGroup>
