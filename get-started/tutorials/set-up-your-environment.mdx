Bindbee has two [environments](/how-to/environments/development), each with its own API key. Requests for a specific customer's data carry a second token as well, the `connector_token`. Mixing these up is the most common early mistake.

**By the end of this lesson** you will have a working development API key and know which token belongs on which request. About 10 minutes.

## Context

### Development and production

| | Development | Production |
| --- | --- | --- |
| Connectors | Separate | Separate |
| Logs and webhook deliveries | Separate | Separate |
| Scope configuration | **Shared** | **Shared** |
| Custom field configuration | **Shared** | **Shared** |
| Syncs | Manual trigger only | Automatic |

The shared rows matter more than they look. Scope and custom fields configured in development carry over to production. Connectors and their data do not.

**Everything in this tutorial happens in Development.**

### The two tokens

Every Bindbee request carries your API key. Requests that touch a specific customer's data carry a second token as well.

| Token | Header | Identifies | Where it comes from |
| --- | --- | --- | --- |
| API key | `Authorization: Bearer …` | Your organization | Settings → API Keys |
| Connector token | `X-Connector-Token` | One customer's linked system | Lesson 3 |

A useful mental model: the API key says *who is asking*, the connector token says *whose data*. Any endpoint returning employee, payroll, candidate, or course records needs both. You do not have a connector token yet - that is expected.

## Step 1 - Create and store your development API key

Go to **Settings → [API Keys](https://app.bindbee.dev/settings/keys)**. Development and Production each have their own block with their own keys - find the **Development** block, then generate a key.

<img
  src="https://images.unifyx.dev/documentation_images/development-key.png"
  alt="The API Keys screen in the Bindbee Dashboard, showing the Development block"
  className="block"
/>

```bash
export BINDBEE_API_KEY="your_development_api_key"
```

<Warning>
  Keys are shown once. If you lose it, regenerate from the same screen -
  regenerating invalidates the old key, so update anything already using it.
</Warning>

**Result:** you have a development API key, set in your shell for the rest of the tutorial.

## Step 2 - Confirm the key works

List the integrations Bindbee supports. This endpoint needs nothing but your API key, and it returns actual content - so a `200` here proves the key works and nothing else is in the way.

```bash
curl -i https://api.bindbee.dev/api/v1/lookup/integrations \
  --header "Authorization: Bearer $BINDBEE_API_KEY"
```

**Result:** a `200` and a list of integrations. Your key is valid.

Do this before debugging anything else for the rest of the tutorial - it separates "bad key" from "bad request" in one call.

<Note>
  Connector and record endpoints are **category-scoped**:
  `/api/hris/v1/connectors` returns HRIS connectors only, and the ATS and LMS
  equivalents are `/api/ats/v1/connectors` and `/api/lms/v1/connectors`. There is
  no combined endpoint across categories. Leaving the category segment out - 
  `/api/v1/connectors` - is a `404`, and it is the most common wrong guess.
</Note>

## What you just did

You now have one of Bindbee's two keys. Every request from here needs the `Authorization` header. Requests for customer records also need `X-Connector-Token` - you'll get that in lesson 3.

For the full rules on what each endpoint needs, see [Authenticate a request](/how-to/authenticate).

## If this didn't work

<AccordionGroup>
  <Accordion title="401 Unauthorized">
    The key is wrong, expired, or the `Bearer ` prefix is missing. The space
    after `Bearer` is required.
  </Accordion>

  <Accordion title="200, but later requests return connectors you don't recognize - or none at all">
    You are almost certainly holding the other environment's key. Development and
    production keys read entirely separate sets of connectors, and neither falls
    back to the other. Confirm you generated the key from the **Development**
    block, and regenerate from there if not.
  </Accordion>

  <Accordion title="404 Not Found">
    Check the category segment in the path. Connector endpoints are scoped per
    category - `/api/hris/v1/connectors`, not `/api/v1/connectors`.
  </Accordion>

  <Accordion title="403 on an endpoint that returns records">
    Endpoints returning customer data need `X-Connector-Token` as well. That
    comes in lesson 3.
  </Accordion>
</AccordionGroup>
