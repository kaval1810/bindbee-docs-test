By the end of this page you will have employee records arriving in your own code, in Bindbee's unified schema — the same shape whether the source is BambooHR, Workday or ADP.

Four steps, all in the **Development** environment. No real customer data is touched.

<Info>
  **You need** access to the [Bindbee Dashboard](https://app.bindbee.dev), provisioned during onboarding. If you cannot sign in, email [support@bindbee.dev](mailto:support@bindbee.dev).
</Info>

## 1. Get your development API key

Go to **Settings → [API Key](https://app.bindbee.dev/settings/keys)**. Both keys already exist — copy the **Development Key**.

<Frame caption="Settings → API Key. Production and Development are separate keys, and neither works against the other's connectors.">
  <img src="/images/quickstart/api-keys.png" alt="The API Key settings page, showing a Production Key block and a Development Key block, each with a masked value and a Regenerate Key button" />
</Frame>

Check it works. This endpoint needs nothing but the key, so a `200` proves it is valid before you add a second credential:

```bash
curl -i https://api.bindbee.dev/api/v1/lookup/integrations \
  --header "Authorization: Bearer <BINDBEE_API_KEY>"
```

<Note>
  **Regenerate Key** replaces the key immediately and invalidates the old one. Use it if a key leaks, not to obtain your first one.
</Note>

## 2. Create a test connector

A connector is one customer's authorised link to one system. In Development you create them yourself rather than waiting for a customer.

Go to **Connectors**, switch to the **Development** tab, and choose **+ Test Connector**.

<Frame caption="Connectors → Development. The Dashboard states the constraint that step 3 exists to handle.">
  <img src="/images/quickstart/connectors-development.png" alt="The Connectors page on the Development tab, noting that development connectors do not sync automatically, with a Test Connector button" />
</Frame>

Name the customer something recognisable — `Quickstart Test Co` — then pick category **HRIS** and an integration.

<Warning>
  **Screenshot needed** — the **+ Test Connector** dialog with category and integration selected. Save to `images/quickstart/test-connector-dialog.png` and replace this callout with a `<Frame>`.
</Warning>

You get a connector with status `INCOMPLETE` and a Magic Link.

**Open the link. This is exactly what your customer sees** — the same hosted page an HR administrator will use in production. Complete every step; several systems have a final confirmation screen that is easy to close early.

<Note>
  What that flow asks for depends on the integration. Some complete against a demo tenant; others want credentials for a real account in that system, and provisioning one can take a day. If yours does, start that signup now — steps 1 and 3 need only the Dashboard.

You now hold both credentials, and they answer different questions.

| Token | Header | Identifies |
| --- | --- | --- |
| API key | `Authorization: Bearer …` | Your organisation — *who is asking* |
| Connector token | `X-Connector-Token` | One customer's system — *whose data* |

Every request from here carries both — see [Authentication](/guides/api-basics/authentication) for which endpoints need only the key.

## 3. Run the first sync

<Warning>
  **Development connectors do not sync automatically.** Skip this and step 4 returns an empty list that looks exactly like a bug. It is the most common thing to get stuck on.
</Warning>

Open the connector and choose **Force Sync**, or call:

```bash
curl -X POST https://api.bindbee.dev/api/embedded/v1/connectors/resync \
  --header "Authorization: Bearer <BINDBEE_API_KEY>" \
  --header "X-Connector-Token: <CONNECTOR_TOKEN>"
```

Watch it in the Dashboard, or poll the connector list:

```bash
curl -G https://api.bindbee.dev/api/hris/v1/connectors \
  --header "Authorization: Bearer <BINDBEE_API_KEY>"
```

Two fields answer different questions, and both matter well beyond this page:

| Field | Values | Answers |
| --- | --- | --- |
| `status` | `INCOMPLETE`, `COMPLETE`, `RELINK_NEEDED` | Are the credentials good? |
| `sync_status` | `Syncing`, `Done`, `Failed` | Did the last run succeed? |

**A connector can be `COMPLETE` and hold no data.** Wait for `sync_status` to reach `Done`.

<Note>
  Triggering syncs by hand is a Development behaviour. Production connectors run on a schedule — see [Sync frequency](/guides/api-basics/sync-frequency).
</Note>

## 4. Read employee data

<CodeGroup>

```bash cURL
curl -G https://api.bindbee.dev/api/hris/v1/employees \
  --header "Authorization: Bearer <BINDBEE_API_KEY>" \
  --header "X-Connector-Token: <CONNECTOR_TOKEN>" \
  --data-urlencode "page_size=10"
```

```python Python
import os, requests

resp = requests.get(
    "https://api.bindbee.dev/api/hris/v1/employees",
    headers={
        "Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}",
        "X-Connector-Token": os.environ["CONNECTOR_TOKEN"],
    },
    params={"page_size": 10},
)
resp.raise_for_status()
for employee in resp.json()["items"]:
    print(employee["first_name"], employee["last_name"], employee["work_email"])
```

```javascript Node
const url = new URL("https://api.bindbee.dev/api/hris/v1/employees");
url.searchParams.set("page_size", "10");

const res = await fetch(url, {
  headers: {
    Authorization: `Bearer ${process.env.BINDBEE_API_KEY}`,
    "X-Connector-Token": process.env.CONNECTOR_TOKEN,
  },
});

if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);

const { items } = await res.json();
for (const employee of items) {
  console.log(employee.first_name, employee.last_name, employee.work_email);
}
```

</CodeGroup>

```json
{
  "cursor": "MDE4YjE4ZWYtYzk5Yy03YTg2LTk5NDYtN2I3YzlkNTQzM2U1",
  "page_size": 10,
  "items": [
    {
      "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
      "remote_id": "123321",
      "modified_at": "2026-07-16T00:00:00Z",
      "first_name": "Kunal",
      "last_name": "Tyagi",
      "work_email": "kunal@example.com",
      "department": "Engineering",
      "employment_status": "ACTIVE"
    }
  ]
}
```

**Each object in `items` is a unified model.** `first_name`, `work_email` and `employment_status` mean the same thing and arrive in the same shape whichever HRIS produced them — that normalisation is the whole product. Point this same code at a connector on a different system and it keeps working.

Two identifiers appear on every record, and confusing them causes real bugs. **`id`** is Bindbee's — stable, same shape everywhere, the one to store. **`remote_id`** is the source system's own, useful for reconciliation but varying in format by system.

<Note>
  An empty `items` array almost always means the sync hasn't finished. Go back to step 3 and check `sync_status`.
</Note>

Keep passing `cursor` back until it returns `null` — see [Pagination](/guides/api-basics/pagination). Paging a large population is the first thing to meet the [rate limit](/guides/api-basics/rate-limits), so raise `page_size` rather than looping faster.

## That's the whole loop

Every Bindbee integration is built from the four steps you just ran:

**Authorised a customer's system** without handling their credentials → **synced their data** into Bindbee's copy → **read it back normalised**, through code that doesn't know which HRIS it came from.

Production is the same four steps with a Production key. What changes: connectors sync on a schedule instead of on demand, and your customers open the Magic Link themselves rather than you.

## If this didn't work

<AccordionGroup>
  <Accordion title="Empty items array">
    Almost always no completed sync. Development connectors do not sync automatically — go back to step 3.
  </Accordion>

  <Accordion title="401 Unauthorized">
    The key is wrong, or missing the `Bearer ` prefix — the space after it is required. A Development key against a Production connector also returns `401`.
  </Accordion>

  <Accordion title="403 Forbidden">
    `X-Connector-Token` is missing, or belongs to a different environment or API category.
  </Accordion>

  <Accordion title="404 Not Found">
    Check the category segment — `/api/hris/v1/connectors`, not `/api/v1/connectors`.
  </Accordion>

  <Accordion title="The connector never leaves INCOMPLETE">
    Authorisation wasn't finished. Several systems have a final confirmation screen that closes without completing. Reopen the Magic Link and walk it to the end.
  </Accordion>

  <Accordion title="A field you expected is missing">
    Check in order: is the field in [scope](/get-started/scoping); did the source system grant permission for it; does the unified model carry it at all. If the value appears in `raw_data`, it is the third — see [Custom fields](/guides/extending/custom-fields).
  </Accordion>
</AccordionGroup>
