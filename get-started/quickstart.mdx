## Prerequisites

- A Bindbee account, provisioned during onboarding — there is no self-serve signup. Without one, email [support@bindbee.dev](mailto:support@bindbee.dev).
- Your **Development API key**, from [app.bindbee.dev/settings/keys](https://app.bindbee.dev/settings/keys).

</Step>

<Step title="Wait for the first sync">

Authorisation starts the initial sync — a full read of every model in scope. On a small test tenant it takes a couple of minutes.

<Warning>
  **Reads before it finishes return `200` with partial or empty results.** Nothing on the response tells the two apart — an employee list still filling looks exactly like a customer with no employees.
</Warning>

Open the connector and watch the **Sync** panel. Wait until the run's **Status** reads **Synced**.

The same value over the API is `sync_status`, and it reads `Done` rather than `Synced`. It is a separate field from `status`, and the two answer different questions:

| API field | Answers | Dashboard | Watch for |
| --- | --- | --- | --- |
| `status` | Are the credentials good? | The connector's own state | `RELINK_NEEDED` |
| `sync_status` | Did the last run succeed? | The **Status** column in the Sync panel | `Failed` |

A connector can be `COMPLETE` and still hold no data.

<Note>
  **That first sync is the only automatic one in Development.** Every refresh after it is one you trigger — press **Force Sync**, or call [Force sync a connector](/api-reference/connectors/resync-connector). Production connectors run on a schedule instead; see [Sync frequency](/api-reference/basics/sync-frequency).
</Note>

</Step>

<Step title="Make your first API call">

Send a `GET` to the Employees endpoint:

```bash
curl https://api.bindbee.dev/api/hris/v1/employees \
  -H "Authorization: Bearer YOUR_DEV_API_KEY" \
  -H "X-Connector-Token: YOUR_CONNECTOR_TOKEN"
```

</Step>

</Steps>

That is the whole Employee model — **40 fields**, the same 40 whether the source is BambooHR, Workday, ADP or any other supported system. `first_name`, `work_email` and `employment_status` mean the same thing everywhere.

Every record carries two identifiers. **`id`** is Bindbee's — stable, same shape everywhere, the one to store; `remote_id` is the source system's own, useful for reconciliation.

Three things to read off it before you build against it:

- **A `null` is not a gap in the model.** It means the source system did not supply that field for that person, or the connector's credentials cannot reach it. The key is still there.
- **`raw_data` and `custom_fields` stay `null` until you ask.** Add `include_raw_data=true` or `include_custom_fields=true` — see [Raw data](/guides/reading-writing/raw-data) and [Custom fields](/guides/extending/custom-fields).
- **Related records arrive as IDs, not nested objects.** `company`, `manager`, `groups`, `work_locations` and `pay_group` are Bindbee IDs you resolve with a second call, or inline with `expand`.

## What just happened

1. You created a **connector** — one authorised connection to one source system.
2. You **synced** it, pulling that system's data into Bindbee's copy.
3. You called the **Unified API** with your API key and the connector token, and got normalised data back.

That is the core of every Bindbee integration. Production differs in two ways: connectors sync on a schedule rather than on demand, and your end users authorise them through Magic Link instead of you entering credentials — see [How to connect](/get-started/how-to-connect).
