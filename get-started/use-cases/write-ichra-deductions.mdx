The round trip behind most benefits products: read the enrolment, work out the amount, write it to payroll, confirm it landed.

## What you'll use

**Models** - [employee](/hris/employee/get-employees), [benefit](/hris/benefits/get-benefits), [employer benefit](/hris/employer-benefits/get-employer-benefits), [employee payroll run](/hris/employee-payroll-runs/get-employee-payroll-runs), [payroll run calendar](/hris/payroll-run-calendar/get-payroll-run-calendars), [payroll code](/hris/payroll-codes/get-payroll-codes)

**Events** - `connector_synced`, `connector_data_modified`

<Info>
  **Before you start**

  - You have the customer's plan-to-code mapping, for connectors that don't supply one.
  - You know the customer's payroll cut-off. It isn't readable through the API.
</Info>

## Steps

<Steps>
  <Step title="Confirm the integration supports payroll writes">
    Write support varies by integration - see [Check write support](/guides/reading-writing/writing-data/meta-apis). Where writes aren't supported, [Passthrough](/guides/extending/passthrough) is the fallback, at the cost of a provider-specific shape.

    **Result:** Confirmation this round trip is possible here.
  </Step>

  <Step title="Read the enrolment and its plan">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/benefits?employee_id=<EMPLOYEE_ID>&page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Take the plan year from the benefit's effective dates, never from the payroll date - a deduction paid in January can belong to the prior plan year. See [Reading benefits](/guides/data-models/benefits).

    **Result:** The election and the period it belongs to.
  </Step>

  <Step title="Resolve the deduction code">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/payroll-codes?page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    **Read the plan first.** The employer benefit carries `payroll_codes` and `deduction_code`. Use those rather than a hand-maintained mapping, and keep your own only for connectors that leave them empty.

    ```python
    codes = employer_benefit.get("payroll_codes") or []
    if not codes:                                        # not populated on this connector
        code = customer_mapping[connector_id][plan_id]   # fall back to onboarding config
        if code not in {c["code"] for c in payroll_codes}:
            raise MappingStale(plan_id, code)            # fail loudly, don't guess
    ```

    A wrong code posts a real deduction against the wrong plan, and it shows up as a payroll discrepancy weeks later rather than an API error. The payroll code model is **BETA**, so pin what you depend on.

    **Result:** A code that exists in this customer's payroll configuration.
  </Step>

  <Step title="Find the next open pay period">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/payroll-run-calendars?page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    The calendar tells you when runs are scheduled, not when payroll closes for processing. That deadline is the customer's operational schedule - agree it separately.

    **Result:** The period you're targeting, and how long you have.
  </Step>

  <Step title="Fetch the write schema">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs/meta/post' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Build the body from this rather than hardcoding it. Read the `required` array on every nested object, and use `enumInformation` instead of guessing from value names - see [Fetch a schema](/guides/reading-writing/writing-data/meta-apis).

    **Result:** The exact body this integration accepts.
  </Step>

  <Step title="Write the deduction with an idempotency key">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>' \
      --header 'X-Idempotency-Key: <STABLE_KEY>' \
      --header 'Content-Type: application/json' \
      --data '{ ... }'
    ```

    Derive the key from employee, plan and period - not a random value or a timestamp. A retry must reuse the same key, or you post the deduction twice against real pay. See [Employee payroll run](/get-started/use-cases/write-payroll-deductions).

    **Result:** One deduction line, however many times you retry.
  </Step>

  <Step title="Confirm it landed in the right period">
    A `2xx` means the source system accepted the write, not that it's visible yet. Read it back after the next sync.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs?employee_id=<EMPLOYEE_ID>&check_date_from=2026-09-01&check_date_to=2026-09-30' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Check the period, not just that it exists - a write submitted after cut-off can be silently applied to the following run. See [Reading payroll](/guides/data-models/payroll).

    **Result:** Confirmation the deduction is in the run you intended.
  </Step>
</Steps>

<Note>
  Sync latency sits between the election and your write, so the usable window before cut-off is shorter than it looks. Where timing is tight, [force a resync](/guides/reading-writing/syncing) rather than waiting for the schedule.
</Note>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="The write returned 501">
    The Meta schema isn't published for this integration and model. That isn't the same as the write being unsupported - see [Meta APIs](/guides/reading-writing/writing-data/meta-apis#which-operations-have-a-schema).
  </Accordion>

  <Accordion title="The write returned 422 though the body matches the schema">
    The schema is the structural contract; the payroll system enforces more on top - codes that must already exist, closed periods, approval states. The `detail` array names the field it rejected - see [Errors & issues](/guides/troubleshooting/errors-and-issues).
  </Accordion>

  <Accordion title="The deduction landed in the wrong period">
    Submitted after the customer's cut-off. Treat it as a catch-up adjustment in the following period rather than a retroactive edit.
  </Accordion>

  <Accordion title="The deduction appears twice">
    A retry without a consistent `X-Idempotency-Key`, or the same change submitted through two paths. Correct it in the payroll system, then fix the key derivation.
  </Accordion>

  <Accordion title="The deduction is against the wrong plan">
    A stale plan-to-code mapping. Validate the code against the current payroll codes before every write.
  </Accordion>
</AccordionGroup>
