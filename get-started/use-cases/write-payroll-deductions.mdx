This is the write behind benefits deductions - an ICHRA allowance, an HSA contribution, a voluntary premium reaching payroll as a line item. It's also the write with the least room for error, because it changes what people are paid.

<Info>
  **Before you start**

  - You've confirmed the integration supports this write - see [Check write support](/guides/reading-writing/writing-data/meta-apis).
  - You have the deduction or earning codes defined in the customer's payroll system.
</Info>

## Steps

<Steps>
  <Step title="Fetch the schema">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs/meta/post' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Expect array fields for earnings, deductions and taxes, each with its own `required` array under `items`. Expect `integration_params` to be required too - payroll writes almost always need a platform-specific reference.

    **Result:** The contract for this integration.
  </Step>

  <Step title="Source the codes from the customer's configuration">
    Deduction and earning codes are defined per customer. A code that works for one customer on a platform won't work for another.

    <Warning>
      There is no reliable automatic mapping from a benefit plan to a payroll deduction code. Get it wrong and you post a deduction against the wrong plan - which surfaces as a payroll discrepancy, not an API error.

      Confirm the mapping with the customer and store it against the connector.
    </Warning>

    **Result:** Codes that exist in this customer's payroll configuration.
  </Step>

  <Step title="Build the arrays">
    ```json
    {
      "employee": "019f618e-c850-716d-a510-74639514abf6",
      "earnings": [
        { "earning_code": "REG", "amount": 4500 }
      ],
      "deductions": [
        { "deduction_code": "HSA_EE", "employee_deduction": 150 }
      ],
      "integration_params": {
        "pay_statement_type_id": "<PLATFORM_VALUE>"
      }
    }
    ```

    Use the field names from the schema, and send amounts in the currency and precision it specifies - some platforms expect minor units.

    **Result:** A body matching the contract.
  </Step>

  <Step title="Send with an idempotency key">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>' \
      --header 'X-Idempotency-Key: <UNIQUE_KEY>' \
      --header 'Content-Type: application/json' \
      --data @payroll-run.json
    ```

    Derive the key from the employee and the pay period - something like `payroll-{employee_id}-{period_end}`. A duplicate write doubles a deduction, and the person affected finds out on payday.

    **Result:** The payroll data is written.
  </Step>

  <Step title="Verify against the pay period">
    Read the run back and confirm it landed in the period you intended - see [Get Employee Payroll Runs](/hris/employee-payroll-runs/get-employee-payroll-runs).

    Payroll systems close periods. A write submitted after close may be rejected, or silently applied to the next open period, which is worse.

    **Result:** Confirmation the amounts are in the right period.
  </Step>
</Steps>

<Note>
  The customer's cut-off isn't visible through the API. When a change misses it, the fix is usually a catch-up adjustment in the next period, not a retroactive edit - design for that.
</Note>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="A deduction code is rejected">
    The code doesn't exist in this customer's configuration, or isn't valid for this employee's pay group. Check their payroll setup rather than reusing a code from another customer.
  </Accordion>

  <Accordion title="The write succeeded but the amount is wrong">
    Check the precision the schema expects. A value sent in dollars where minor units were expected is off by 100x and still passes validation.
  </Accordion>

  <Accordion title="The write was rejected because the period is closed">
    Expected after the customer's cut-off. Queue the change for the next open period and reconcile it as an adjustment.
  </Accordion>

  <Accordion title="A deduction was applied twice">
    A retry without a consistent idempotency key - see [Idempotency](/guides/reading-writing/writing-data/idempotency) - or the same change submitted through two paths. Correct it in the payroll system, then fix the key derivation.
  </Accordion>

  <Accordion title="You need to map plan years to payroll periods">
    Payroll runs carry payment dates, not plan years. Cross-reference the payment date against the benefit's coverage period - see [Reading benefits](/guides/data-models/benefits).
  </Accordion>
</AccordionGroup>
