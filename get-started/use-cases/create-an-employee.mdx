Creating an employee writes a person into the customer's system of record. It's the highest-consequence write Bindbee offers - a duplicate is visible to HR and awkward to unwind.

<Info>
  **Before you start**

  - You've confirmed the integration supports this write - see [Check write support](/guides/reading-writing/writing-data/meta-apis#supported-operations).
  - You can generate a stable idempotency key per person.
</Info>

## Steps

<Steps>
  <Step title="Fetch the schema">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees/meta/post' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Employee creation varies more between platforms than any other write, so never hardcode the field list.

    **Result:** The contract for this integration.
  </Step>

  <Step title="Assemble the body from the schema">
    Work through the `required` array on the root object, then on each nested object you include.

    ```json
    {
      "first_name": "Ada",
      "last_name": "Lovelace",
      "work_email": "ada@example.com",
      "start_date": "2026-09-01",
      "home_location": {
        "street_1": "12 Analytical Way",
        "city": "London",
        "country": "GB"
      }
    }
    ```

    A nested object that's optional at the top level still enforces its own required fields once you send it. A half-filled address is often rejected where leaving it out entirely would have been fine.

    **Result:** A body conforming to the schema.
  </Step>

  <Step title="Supply integration_params">
    Most platforms need their own references - an employment type ID, a pay group, a legal entity, a location code. These come from the customer's HRIS configuration, not from Bindbee.

    Where you can't get them from a Bindbee read, query the source system's configuration endpoints via [Passthrough](/guides/extending/passthrough).

    **Result:** The platform-specific values the write needs.
  </Step>

  <Step title="Send with an idempotency key">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/hris/v1/employees' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>' \
      --header 'X-Idempotency-Key: <UNIQUE_KEY>' \
      --header 'Content-Type: application/json' \
      --data @employee.json
    ```

    <Warning>
      Derive the key from your own record for this person - not a random value, and not a timestamp. A retry must reuse the same key, or you create a second employee. Most source systems will happily accept two people with identical names and emails.
    </Warning>

    **Result:** The employee is created upstream.
  </Step>

  <Step title="Store the returned identity">
    Persist the returned Bindbee `id` against your own record.

    Don't key on the employee number or `remote_id` - some systems assign these asynchronously, so they can be missing right after creation, and some reissue them later. See [Reading employees](/guides/data-models/employee-and-org).

    **Result:** A stable reference for later operations.
  </Step>
</Steps>

<Note>
  An employee is a person; an employment is a job. Rehires and transfers are not new employees - creating one duplicates the person instead of adding an employment. Check for an existing record by a stable upstream identifier first.
</Note>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Validation fails on a field the schema marks optional">
    Check the nested objects. A field that's optional on the root can be required inside an object you included, and the error often names the leaf field without its path.
  </Accordion>

  <Accordion title="An integration_params value is rejected">
    These reference configuration that must already exist in the customer's HRIS. A plausible-looking pay group or location code that isn't defined in their instance will be rejected. Confirm the value against their setup rather than constructing it.
  </Accordion>

  <Accordion title="The employee was created twice">
    A retry without a consistent idempotency key. Merge or remove the duplicate in the source system - Bindbee doesn't own the record once created - then fix the key derivation.
  </Accordion>

  <Accordion title="The employee doesn't appear in reads">
    Reads serve synced data, so a new employee appears after the next sync. [Force a resync](/guides/reading-writing/syncing) to confirm sooner.
  </Accordion>

  <Accordion title="The write returns 403">
    Creating employees usually needs broader permission than reading them. The credentials can authenticate and read fine while lacking write access - see [Permission errors](/guides/troubleshooting/permission-errors).
  </Accordion>
</AccordionGroup>
