Data reaches Bindbee one of two ways. An **API connector** means Bindbee calls the vendor's API. An **SFTP connector** means the customer's system exports a file on a schedule and drop on Bindbee dropper to reads it - used where the vendor has no usable API, charges for one, or leaves out the models your customer needs.

## The two connection types

| | API connector | SFTP connector |
| --- | --- | --- |
| How data arrives | Bindbee calls the vendor's API | The customer's system exports a file |
| Schedule | Bindbee's sync schedule | The customer's export schedule |
| Forcing a resync | Fetches fresh data | Re-reads the same file until new file upload |
| A record that stops appearing | Nothing happens | Marked no longer active |
| Coverage | What the vendor's API exposes | What the export was set up to include |
| Writes | Often supported | Generally not |

[Integrations](/get-started/integrations) lists the type per integration. Slugs ending in `_sftp` are file-based, but **the suffix is not a reliable test on its own** - variants like `workday_raas` and `paychex_flock` carry no marker.

---

## API connectors

Bindbee calls the vendor's API on its own schedule. **How the customer authorises depends on the integration** - most offer OAuth, where they sign in and approve access; others need an API key, token or certificate they generate first; some offer both.

**The choice changes nothing about the data** - only what breaks later. A token expires on its own, a key breaks when it's rotated, and either way the fix is a [relink](/guides/troubleshooting/connections-to-relink).

## SFTP connectors

The customer's system exports a file and Bindbee reads it. Your customer sets the delivery up themselves, following [Set up an SFTP connection](https://help.bindbee.dev/set-up-an-sftp-connection). **Everything below applies only to these connectors.**

### Each file is a full snapshot

An API can be asked "what changed since Tuesday". A file cannot be asked anything - it arrives, and it contains whatever it contains. So Bindbee reads each delivery as the complete picture at that moment, compares it with what it already holds, and updates.

**There are no change events and no deltas.**

### A missing record is treated as a leaver

**If someone is missing from the file, Bindbee reads that as "they should not be here"** and marks them no longer active. The record is not deleted.

That rule exists because most HR exports list current employees and drop leavers - there is no termination row to read. Without it, **terminations would never come through at all**, and former employees would look active indefinitely, keeping benefits or access they should have lost.

<Warning>
A file that is cut short, filtered, or only half-written marks a lot of employees inactive at once. If the customer changes their export, limits it to one division, or sends a file that failed partway through, **it looks exactly like a mass termination.**
</Warning>

That is the cost of the trade, and **it favours the loud, recoverable failure over the silent one** - a wave of inactive employees is noticed within hours, while a leaver who never became inactive may never be noticed at all.

These files also rarely give a termination date for someone who has simply stopped being listed, so the end date is a guess, not a reported value.

### The customer controls the schedule and the columns

Data is only as fresh as the last file, and **Bindbee cannot ask for a new one** - forcing a resync just re-reads the file already there. A delivery that quietly stops looks like frozen data: no error, no failed sync, just records that stop moving.

The file also carries only the columns the export was set up to produce. Anything outside it is not merely empty - **it cannot be fetched at all**, and widening coverage means the customer changing their export.

---

## Summary

- **Watch how recent the last file is**, not whether the sync succeeded. An SFTP connector can look healthy and be weeks stale.
- **Treat a large simultaneous status change as suspect.** Real terminations rarely happen at once; broken exports always do.
- **Don't use an inferred end date** where a legally accurate termination date is required.
- **On an API connector, broken credentials mean a relink**, not a new connector - the auth method never changes the data you get.
