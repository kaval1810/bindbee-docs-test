Four things carry every integration, and they happen in that order. You set **scope** once - the models and fields Bindbee may request. Your customer authorises their system, which creates a **connector**. That connector **syncs**, pulling the scoped data and normalizing it. When something looks wrong, **logs** show the exact request and response behind it.

The Dashboard is where you watch all four.

<Info>
  Ready to build instead? The [Quickstart](/get-started/quickstart) takes you from an empty environment to employee data in your own code.
</Info>

## Magic Link

Where you create a hosted authorisation link for a named customer and watch it complete. Select the integration, set `origin_id` to your own customer identifier, and send the link to whoever administers their HRIS.

See [How to connect](/get-started/how-to-connect) for this and the two other routes.

## Connectors

A connector is one customer's authorised link to one third-party system - **one connector per customer, per system.** Find them under **Connectors**, with separate **Development** and **Production** tabs.

<img
  src="https://images.unifyx.dev/documentation_images/connector.png"
  alt="The Connectors list in the Bindbee Dashboard"
  className="block"
/>

From a connector you can open its issues and its logs, both the fastest route to why a sync misbehaved.

<Note>
  Filter to **Active Connectors** before counting. Incomplete connectors - where the end user opened the link but never finished authorising - sit in the same list, and are the usual reason a count looks wrong.
</Note>

### Moving a connector between environments

A connector's environment is fixed at creation, but it can be moved afterwards without the end user reconnecting. Authorisation and record history survive, so **the IDs your system has stored stay valid** - which is why moving beats deleting and recreating.

It is not self-serve: send the connector list and the target environment to support. Two things change once it lands:

- **The API key.** Environment isolation is enforced on the key, so calls for moved connectors must use the target environment's. A stale key returns `401`, which is the first symptom of a service you missed. Webhooks are environment-specific too.
- **Sync behaviour.** Moving to Development stops automatic syncs; moving to Production starts them on the 24-hour cadence.

### Renaming or deleting a connector

**Renaming** changes the display name shown in the dashboard and returned as `connector.display_name`. Nothing in the API is keyed on it, and it is a support request rather than a dashboard control - so don't rely on the display name to tell connectors apart. `origin_id` is what actually resolves a connector to your customer record.

**Deleting** discards the connector's synced data *and the record identities built from it*. Reconnecting the same customer afterwards produces a new connector with new IDs, so every employee, employment and benefit ID you stored becomes a dangling reference.

| Situation | Delete? |
| --- | --- |
| An incomplete connector the end user abandoned | Yes |
| A duplicate created by mistake, never used | Yes |
| A customer that has genuinely churned | Yes |
| A test connection in Production that's being billed | No - move it to Development |
| Credentials expired | No - [relink it](/guides/troubleshooting/connections-to-relink) |
| Sync failing or data looks wrong | No - [resync](/guides/reading-writing/syncing) |

See [Delete Connector](/api-reference/connectors/delete-connector) for the endpoint.

## Logs
