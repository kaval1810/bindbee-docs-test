You called an endpoint, got a 200, and the field you needed came back empty - or the whole model came back as an empty list. Nothing failed. There is no error to look up.

This is almost always one of three filters doing its job. Data has to survive all three to reach you, and only one of them is yours to control.

## Three filters, in order

Every record Bindbee returns has passed through three independent gates. They apply in this order, and each one narrows what the next one sees.

**Integration coverage.** Not every source system exposes every model. If an HRIS has no concept of pay groups, or exposes benefits only through a report you cannot reach programmatically, that model does not exist for that integration. This is a property of the source system and its API, not a setting.

**Scope configuration.** You choose which categories, models, and fields Bindbee syncs for your organisation. Anything you have not enabled is never fetched. Scope is configured once and applies across your environments - a change in development is a change in production.

**Source-system permissions.** The credentials your customer's admin authorised carry a set of permissions. Bindbee can only read what those credentials can read. A connector authorised by an admin with restricted role permissions returns less than the same integration authorised by a full administrator.

A field arrives only if the integration exposes it, your scope includes it, and the credentials permit it.

## Why a missing permission looks like empty data

When credentials lack permission for a field or model, the source system does not usually say so. It returns a response with that data absent, or returns a 403 on one endpoint while every other endpoint succeeds. Bindbee syncs what it received.

The result is that a permission problem and a genuinely empty field look identical from your side. An employee with no compensation record and an employee whose compensation you are not permitted to read both return the same shape.

<Info>
This is the single most common cause of "the data is in the HRIS but not in the API." Before assuming a coverage gap, check whether the connector's credentials were authorised with sufficient permissions. The connector's logs will show a 403 on the specific endpoint if the source system reported one.
</Info>

The exception is when a source system fails the whole request rather than trimming the response. Then you get a sync error rather than silence, and the connector surfaces the upstream status code and message.

## Scope is a contract, not a filter on responses

It is tempting to think of scope as a filter applied to data Bindbee already holds. It is not. Data outside your scope is never fetched and never stored.

Two consequences follow. First, narrowing scope does not just hide data - it stops collecting it, which reduces sync time and the volume of PII you hold. Second, widening scope does not immediately reveal data that was previously hidden, because that data was never there. Newly enabled models are populated on the next sync.

## Why it works this way

Silent omission is a deliberate choice, and it is the less obvious of the two options.

The alternative is to fail loudly - return an error whenever any part of a request could not be satisfied. That produces a system where a single missing permission on one field breaks reads for every field, across every employee, for that connector. One customer's restrictive IT policy would take down your whole integration for them.

Partial success keeps the integration running on whatever the credentials do permit, and pushes the diagnosis to the point where someone can act on it - the connector's logs, and the permission setup your customer's admin controls. The cost is that absence is ambiguous, which is why the diagnosis has to start with the credentials rather than with the data.

Scope exists for a different reason. Unified APIs make it trivially easy to request far more personal data than a use case needs, and the default of "sync everything" is both a compliance liability and a performance cost. Making scope an explicit, up-front decision means the narrow default is the easy one.

## What this means for you

- **An empty field is a permissions question first, a coverage question second.** Check the connector's authorising credentials before assuming the integration does not support the field.
- **Scope changes are organisation-wide and cross-environment.** Enabling a model in development enables it in production. Plan scope before connecting production customers.
- **Narrow scope deliberately.** Every model you do not enable is data you do not sync, do not store, and do not have to justify holding.
- **Coverage varies by integration, not just by category.** Two HRIS connectors under the same scope configuration will not return the same models.
