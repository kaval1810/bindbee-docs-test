Reading is symmetrical: every integration returns the same employee shape. Writing is not. What a source system requires to create an employee differs by system, and within a system it differs by tenant, because customers configure their own mandatory fields.

A fixed request schema cannot express that. So for writes, Bindbee tells you what the schema is at the moment you ask, for the connector you are asking about.

## Ask before you write

A meta endpoint returns the request schema for a create operation on a specific connector: which fields exist, which are required, and where the value set is constrained, what the permitted values are.

That last part matters more than it sounds. Many required fields are not free text but references into the customer's own configuration - a location identifier, a pay group, an employment type defined in their tenant. You cannot know those values in advance, and they differ between two customers on the same system.

<Info>
The practical pattern is to fetch the schema, render a form or validate against it, then submit. Hardcoding a request body that worked for one customer is the most common way to build a write integration that breaks on the second customer.
</Info>

Meta endpoints currently exist for create employee, create employee payroll run, create time off, create timesheet entry, and create candidate.

## Where there is no meta endpoint

Most write operations do not have one. The ATS creates in particular are largely uncovered.

For those, the request shape comes from the API reference, and the per-integration variation you would have learned from a schema has to be discovered another way - by attempting the write and reading the failure. This is unsatisfying and it is the current state.

## Integration-specific parameters

Some writes need values that exist in one source system and nowhere else - a pay adjustment code, a system-specific flag governing how the record is processed.

These travel in a dedicated parameters object rather than being added to the unified body. The separation is deliberate: the unified fields stay portable across integrations, and the escape hatch is visibly an escape hatch. Code passing integration-specific parameters is code that knows which integration it is talking to, and it should be obvious in the request that this is the case.

## Why it works this way

Publishing one fixed schema per model would be simpler to document and simpler to code against, and it would be wrong for a substantial share of customers.

The alternative to runtime discovery is the intersection: require only the fields every integration requires, and hope the rest are optional. They are not. A tenant that has made cost centre mandatory will reject a create that omits it, and no amount of schema design on Bindbee's side changes that. You would learn the requirement from a 400, which is what runtime discovery exists to avoid.

The other option is the union - accept every field any system might want and pass through what applies. That produces a schema too large to be useful and gives no signal about what is actually required for the customer in front of you.

Asking the connector puts the answer where the truth is. The cost is an extra call and a more dynamic integration than a static schema would give you. In return, a write built against the schema works for a tenant configured in ways you never anticipated, which is most of them.

## What this means for you

- **Fetch the schema per connector**, not once per integration. Requirements vary by tenant.
- **Render forms from the schema** rather than hardcoding fields.
- **Do not reuse a working request body across customers** without checking it against their schema.
- **Keep integration-specific parameters out of the unified body.** They belong in the dedicated object.
- **Where no meta endpoint exists**, expect to discover requirements from failures, and log them.
