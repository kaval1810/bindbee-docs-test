Four things carry every integration, and they happen in that order. You set **scope** once - the models and fields Bindbee may request. Your customer authorizes their system, which creates a **connector**. That connector **syncs**, pulling the scoped data and normalizing it. When something looks wrong, **logs** show the exact request and response behind it.

The Dashboard is where you watch all four. This page is the tour; each section links to the guide that goes deeper.

<Info>
  Ready to build instead? The [Quickstart](/get-started/quickstart) takes you from an empty environment to employee data in your own code - you do not need this page first.
</Info>

## Dashboard

What you land on after signing in, and where you manage every integration from one place: how many API requests have been made, which of your customers is on which connector, and whether any connector currently has a problem.

From here you can reach Logs, the list of open Issues, and every connector you have created.

## Connectors

A connector is one customer's authorized link to one third-party system. Each is specific to a single integration and carries the credentials and state needed to move data between the two - **one connector per customer, per system.**

Find them under **Connectors**, with separate **Development** and **Production** tabs. From a connector you can open its issues and its logs, both the fastest route to why a sync misbehaved.

<img
  src="https://images.unifyx.dev/documentation_images/connector.png"

## Scoping

Scope is the list of models and fields Bindbee requests from a connected system. Set it once under **Configure → Scoping**, and it applies to every connector you create afterwards.

A field outside scope is never requested, so it never syncs and is absent from responses - not `null`, simply not there. Narrowing scope also narrows what your customer's admin has to grant.

<Info>
  Scope is **shared across environments**. What you configure in Development applies in Production too.
</Info>

Scope is only one of three reasons a field can go missing - see [What data you get](/explanation/scope-and-permissions) for the other two.

## Logs

Real-time visibility into request and response data, so you can see exactly what happened for a connector. Open **Logs**, or reach one connector's logs from its own page.

Each entry shows the direction - `READ` or `WRITE` - along with the request and the response. When a response is an error, the error code is shown alongside it. Open any entry for full detail.

When a sync misbehaves this is the first place to look: the source system's own error is usually more specific than the status Bindbee shows.

## Issues

Bindbee's error tracking. When something fails on a connector - a sync, an authorization, a request to the source system - it is raised as an issue rather than left for you to find in the logs.

Each issue records what failed and, where Bindbee can determine it, the likely resolution. Every issue carries the request and response behind it, so you and the Bindbee team look at the same evidence when you escalate.

Issues tell you *that* something broke and usually *why*. Fixing it happens elsewhere:

| The issue points at | Where it is fixed |
| --- | --- |
| Expired or revoked source credentials | Re-authorize the connector - see [Update credentials](/how-to/connections/update-credentials) |
| A model failing to sync | Logs has the request and the source system's own error |
| A field never arriving | Check Scoping first, then permissions in the source system |
| Errors your own code has to handle | [Handle API errors](/how-to/setup/handle-api-errors) |

## Custom Fields

Custom fields carry values the unified model does not, taken from the source system's own payload and returned alongside the normalized record. Find them under **Custom Fields**.

Creating one is two steps, separate on purpose - the field is what your code reads, the mapping is where its value comes from.

**Create the field** with **New Field**. Names must be unique and `snake_case`, because the name is the key your code reads off the `custom_fields` object.

**Configure the mapping**, choosing the level:

| Mapping level | Applies to | Use when |
| --- | --- | --- |
| **Integration** | Every connector for that integration | The source system names the field consistently |
| **Connector** | One selected connector | A single customer configured it differently |

<Warning>
  A mapping that does not match the payload does not raise an error. It resolves to `INVALID_JSON_PATH`, which arrives as the field's **value**. Preview an expression before saving it.
</Warning>

Custom field configuration is shared across environments, like scope. See [Map a custom field](/how-to/data-model/map-a-custom-field-from-the-dashboard) to do it, or [How custom fields work](/explanation/how-custom-fields-work) for the model behind it.

## Webhooks

How Bindbee tells your application that a sync finished or a record changed, instead of your application polling. Find them under **Configure → Webhooks**.

| Field | What it does |
| --- | --- |
| **Destination URL** | Where deliveries are sent. **Test URL** confirms Bindbee can reach it before you save |
| **Webhook Name** | Your own label, for finding it later |
| **Webhook Type** | Which environment's connectors this covers - Development, Production, or both |
| **Events** | Which events trigger a delivery, chosen by checkbox |

The **Security** section on the same page holds your organization's signature key. Every delivery is signed with it, and your handler should verify that signature before acting on the payload.

<Warning>
  The Dashboard labels events in prose, but the payload carries the event string - `connector_synced`, not "Sync completed". Match on the string, and note that event strings use **underscores**, never hyphens. Matching the wrong form fails quietly: your handler simply never runs.
</Warning>

See [Webhooks](/webhooks/overview) to set one up, and [Webhook Events & Payloads](/webhooks/events) for every event and payload shape.

## How your customers connect

In production your customers authorize their own systems. A [Magic Link](/how-to/connections/generate-a-magic-link) is a secure URL that runs the whole flow in their browser with no front-end code on your side; [embedding the flow](/how-to/connections/embed-the-connection-flow) puts it inside your own product instead.
