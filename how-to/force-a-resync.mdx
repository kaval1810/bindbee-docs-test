```bash
curl -X POST "https://api.bindbee.dev/api/embedded/v1/connectors/resync" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN"
```

The API reference tells you how. This page tells you when.

## When to resync

| Situation | Resync? | Why |
| --- | --- | --- |
| User clicked "Sync now" | **Yes** | Explicit intent; they are waiting |
| You just wrote data back and want to read it | **Yes** | Writes aren't visible until a sync |
| Development connector — you need any data at all | **Yes** | Dev connectors never sync automatically |
| Customer says "I fixed permissions in the HRIS" | **Yes** | Confirms the fix without waiting a day |
| Right after `RELINK_NEEDED` was resolved | **Yes** | Verifies the new credentials work |
| On a cron/schedule | **No** | Production already syncs automatically |
| Before every read | **No** | Syncs are not instant; you'd read stale data anyway |
| Data looks stale | **No** — diagnose first | Check `status` and `last_sync_start_time` |
| Data looks wrong | **No** | A resync re-runs the same mapping and produces the same result |
| To make data fresher than the schedule | **No** | See below |

<Warning>
  **Resyncing does not bypass the vendor's rate limits.** Frequent resyncs can
  get your customer's connector throttled or temporarily blocked upstream —
  making their data *less* current, not more.
</Warning>

<Warning>
  On **SFTP connectors**, a resync re-processes the most recently delivered file.
  It does not fetch new data. If the customer's export runs weekly, resyncing
  daily achieves nothing. See [SFTP vs API](/explanation/sftp-vs-api).
</Warning>

## Doing it properly

A resync is asynchronous. Triggering it is the beginning, not the end.

<Steps>
  <Step title="Trigger">
    `POST /api/embedded/v1/connectors/resync` with the API key and connector
    token.
  </Step>
  <Step title="Reflect it in the UI immediately">
    Set your local state to `syncing` so the user gets instant feedback. Do not
    wait for the first poll.
  </Step>
  <Step title="Track progress">
    Poll `GET /api/{category}/v1/connectors` and read `sync_progress` (0–100),
    or wait for the `connector_synced` webhook.
  </Step>
  <Step title="Re-read when done">
    Once `sync_status` is `Done`, run your normal
    [`modified_after` read](/how-to/filter-with-modified-after).
  </Step>
</Steps>

```python
def trigger_and_wait(connector_token, timeout_s=1800, interval_s=15):
    requests.post(
        f"{BASE}/api/embedded/v1/connectors/resync",
        headers=auth_headers(connector_token),
        timeout=30,
    ).raise_for_status()

    deadline = time.monotonic() + timeout_s
    while time.monotonic() < deadline:
        connector = find_connector(connector_token)
        if connector["sync_status"] == "Done":
            return connector
        if connector["sync_status"] == "Failed":
            raise SyncFailed(connector)
        time.sleep(interval_s)

    raise SyncTimeout(connector_token)
```

<Tip>
  Set the user's expectation from `avg_sync_duration` on the connector — the
  measured average for *that* connection. "This usually takes about 15 minutes"
  beats an indefinite spinner.
</Tip>

## Guard the button

A user-triggered resync means a button, and a button means someone will click it repeatedly.

```python
MIN_INTERVAL = timedelta(minutes=30)

def can_resync(connector, last_manual_resync):
    if connector["sync_status"] == "Syncing":
        return False, "A sync is already running."
    if last_manual_resync and datetime.now(timezone.utc) - last_manual_resync < MIN_INTERVAL:
        return False, "Recently synced. Try again in a little while."
    if connector["status"] == "RELINK_NEEDED":
        return False, "Reconnect your HR system first."
    return True, None
```

Three rules worth enforcing:

1. **Disable while `sync_status` is `Syncing`.**
2. **Cooldown of at least 15–30 minutes** between manual resyncs per connector.
3. **Block on `RELINK_NEEDED`** — the sync will fail; offer reconnect instead.

<Warning>
  Never resync from a page-load handler, a health check, or a retry loop. This is
  the fastest route to a throttled connector, and the symptom — degraded data —
  looks nothing like the cause.
</Warning>

## Resync vs relink

Frequently confused, entirely different:

| | Resync | Relink |
| --- | --- | --- |
| Fixes | Stale data | Broken credentials |
| Who does it | You, via API | The customer, via the connect flow |
| Use when | `status: COMPLETE` | `status: RELINK_NEEDED` |
| Effect | New sync job | New credentials on the same connector |

<Warning>
  Resyncing a `RELINK_NEEDED` connector fails — the credentials are the problem.
  It also produces a `Failed` sync that can pollute your alerting. Check
  `status` before triggering.
</Warning>

Relinking updates the existing connector: the `connector_token` you stored keeps working, and you do not need to re-exchange tokens.

## After writing data back

The most legitimate use.

```python
create_time_off(connector_token, body)     # POST succeeded

trigger_resync(connector_token)            # make it readable sooner
# then re-read once sync_status == "Done"
```

<Warning>
  A `2xx` from a write means the **source system** accepted it. The record is not
  readable from Bindbee's unified API until a sync brings it back. Show the write
  optimistically in your own UI and let the sync reconcile — don't block the user
  on a round trip.
</Warning>
