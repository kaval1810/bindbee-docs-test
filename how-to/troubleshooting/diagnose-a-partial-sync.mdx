---
title: "Diagnose a Partial Sync"
description: "Work out which model failed during a sync that completed only in part, and what to do about it."
---

A partial sync means some models loaded and others didn't. The connector is authenticated and running - the failure is scoped to specific models, so the fix is different from a total failure.

<Info>
  **Before you start**

  - You've confirmed the run is marked Partial in the connector's sync history - see [Monitor Sync Status](/how-to/troubleshooting/monitor-sync-status). Partial is a dashboard label; `sync_status` does not carry it.
</Info>

## Steps

<Steps>
  <Step title="Identify which models failed">
    Open the sync run and read the per-model breakdown. Note every model that reports an error, and the record count on the ones that succeeded.

    **Result:** A list of failed models. That list is the diagnosis - the cause is usually shared across all of them.
  </Step>

  <Step title="Classify the failure">
    Match the failed set against these patterns.

    | Pattern | Likely cause | Where to go |
    | --- | --- | --- |
    | One model family fails, e.g. all payroll or all benefits | The credentials lack permission for that area of the source API | [Resolve a Permission Error](/how-to/troubleshooting/resolve-a-permission-error) |
    | A model fails only on large populations | Upstream request size or timeout limits | Step 3 |
    | Different models fail on different runs | Transient upstream errors or rate limiting at the source | Step 4 |
    | Every model fails | Not a partial sync - treat it as a failed sync | [Detect a Connection That Needs Relinking](/how-to/reliability/detect-a-connection-that-needs-relinking) |

    **Result:** You know whether this needs a configuration change on the customer's side, a retry, or an escalation.
  </Step>

  <Step title="Retry the sync">
    For transient and size-related failures, trigger a fresh run rather than waiting for the next scheduled one.

    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/embedded/v1/connectors/resync' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    See [Force a Resync](/how-to/sync-control/force-a-resync).

    **Result:** A new run starts. If the same models fail again with the same error, it isn't transient - go back to step 2.

    <Warning>
      Resync; do not delete and recreate. Deleting a connector discards its sync history and the record identities built from it, which changes the IDs your system has already stored.
    </Warning>
  </Step>

  <Step title="Check whether the succeeded models are internally consistent">
    A partial sync can leave related models out of step - employees loaded but employments didn't, or benefits loaded but dependents didn't. Reads against the succeeded models will look complete while the relationships between them are incomplete.

    Treat the connector's data as provisional until a run completes cleanly, and gate downstream processing on the sync-completed event rather than a clock. See [Trigger a Job When a Sync Completes](/how-to/sync-control/trigger-a-job-on-sync-complete).

    **Result:** Downstream systems don't act on a half-loaded dataset.
  </Step>
</Steps>

## If this didn't work

<AccordionGroup>
  <Accordion title="The same model fails on every run with a permission-style error">
    This needs a change in the source system, not in Bindbee. Identify the required permission and have the customer's administrator grant it, then resync. Per-system instructions live in the [help centre](https://help.bindbee.dev).
  </Accordion>

  <Accordion title="A model fails only for large customers">
    Some source systems impose response-size or processing limits that only bite above a certain population. Filtering the extract on the source side to confirm the limit is the cause is a useful diagnostic - if a filtered run succeeds and an unfiltered one fails within seconds, the failure is a size or definition problem rather than a timeout.

    Report this with the connector ID and the failing model; extract handling is adjusted per integration.
  </Accordion>

  <Accordion title="Records loaded but fields are empty">
    That isn't a partial sync. The model loaded; the fields weren't populated or aren't exposed at the current permission level. See [Trace a Missing Record](/how-to/troubleshooting/trace-a-missing-record) and [Inspect the Raw Upstream Payload](/how-to/data-model/inspect-the-raw-upstream-payload).
  </Accordion>

  <Accordion title="The partial sync coincides with a spike in your own API calls">
    Sync failures and read failures are separate. If your reads are returning `429`, that's the [rate limit](/api-reference/basics/rate-limits) on the connector token and unrelated to the sync.
  </Accordion>
</AccordionGroup>
