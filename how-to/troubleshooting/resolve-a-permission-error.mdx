---
title: "Resolve a Source-System Permission Error"
sidebarTitle: "Permission errors"
description: "Map a sync failure or missing field back to the specific permission the end user's HRIS credentials are missing."
---

Most sync failures that aren't credential expiry are permission failures in the source system. Bindbee can only read what the connected credentials are allowed to read, and many HRIS platforms return an empty result rather than an error when permission is missing - so a permission problem often presents as missing data.

<Info>
  **Before you start**

  - You have the connector ID and the name of the affected model or field.
  - You have a route to the customer's HRIS administrator. Every fix on this page happens in their system, not in Bindbee.
</Info>

## Steps

<Steps>
  <Step title="Confirm the symptom is permission-shaped">
    Match what you're seeing against these signatures.

    | Symptom | Permission-related? |
    | --- | --- |
    | An authorization or access-denied message in the sync error | Yes |
    | One model family fails while others succeed | Usually |
    | A model returns zero records but the source system shows data | Usually |
    | A field is null for every record but populated in the HRIS UI | Often - field-level permission |
    | Failures that come and go across runs | Sometimes - intermittent permission or token scope |
    | Every model fails at once | No - credential expiry, see [Connections needing relink](/how-to/reliability/detect-a-connection-that-needs-relinking) |

    **Result:** You've separated permission failures from authentication failures. They look similar and need different fixes.
  </Step>

  <Step title="Identify what's being requested">
    Open **Logs** for the connector and find the failing request. The log shows the request, the response, and the error code where the response failed.

    **Result:** You know which upstream resource was refused, which is what the administrator needs to grant access to.
  </Step>

  <Step title="Determine the permission from the failing model">
    Translate the failing model into the access the source system needs to expose.

    | Failing model | Access typically required |
    | --- | --- |
    | `employee`, `employment` | Read access to worker or personnel records |
    | Date of birth, national ID, `bank_info` | Sensitive personal data access - commonly a separate grant from general employee read |
    | `compensation`, `payroll_run`, `employee_payroll_run` | Payroll module access, often licensed separately |
    | `benefit`, `dependent`, `benefit_coverage` | Benefits module access |
    | `time_off`, `time_off_balance`, `timesheet_entry` | Time and attendance module access |
    | Cost centre, department, custom groupings | Access to the specific field group or report definition |

    **Result:** A concrete ask for the administrator rather than "the integration isn't working".

    <Note>
      Sensitive fields are the most common single cause. Date of birth and cost centre in particular are frequently gated behind a permission that general employee read does not include, so the connector authenticates cleanly and returns records with those fields null.
    </Note>
  </Step>

  <Step title="Send the customer the setup instructions">
    Per-system click paths, with screenshots, live in the [help centre](https://help.bindbee.dev). Send the administrator the guide for their platform rather than describing the steps yourself - the guides are white-labelled and safe to forward to your customers.

    **Result:** The administrator has instructions specific to their HRIS.
  </Step>

  <Step title="Resync after the permission is granted">
    Permission changes do not apply retroactively to already-synced data. Trigger a fresh run so the newly readable fields are pulled.

    See [Force Resync a Connector](/api-reference/connectors/resync-connector).

    **Result:** The next sync includes the previously refused models or fields.
  </Step>
</Steps>

## If this didn't work

<AccordionGroup>
  <Accordion title="The administrator says the permission is already granted">
    Check the permission is on the account the connector authenticated as, not on the administrator's own account. Integration users and service accounts are commonly provisioned with a narrower role than the person configuring them.

    Some platforms also require the integration user to be reactivated, or a token reissued, before a permission change takes effect. If the credentials were issued before the change, [update them](/how-to/reliability/detect-a-connection-that-needs-relinking).
  </Accordion>

  <Accordion title="The failure appears on some runs but not others">
    Intermittent permission errors usually indicate token scope changing between refreshes, or a source system applying limits under load rather than refusing outright. Capture the connector ID and the timestamps of both a succeeding and a failing run before escalating - the contrast is what makes it diagnosable.
  </Accordion>

  <Accordion title="Records return but a specific field is still null">
    Confirm the field is genuinely absent upstream rather than unmapped on the Bindbee side. Fetch the raw payload - see [Inspect raw data](/how-to/reading-data/include-raw-data-and-custom-fields).

    If the value is present in `raw_data` but not in the unified response, it's a mapping question, not a permission one, and you can surface it as a [custom field](/explanation/how-custom-fields-work).
  </Accordion>

  <Accordion title="The source system uses IP allow-listing">
    Some platforms restrict API access by source IP in addition to credentials, which presents as an authorization failure with correct credentials. Ask support for the current egress IP ranges to pass to the customer's administrator.

  </Accordion>

  <Accordion title="The integration connects over SFTP rather than an API">
    File-based connectors fail differently - access is governed by SFTP credentials and by which files the source system is configured to drop, not by API scopes. A missing field usually means the file layout doesn't include it, which needs a report or template change on the customer's side.
