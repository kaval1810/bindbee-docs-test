---
title: "Trace a Missing Record"
description: "Work out why a record that exists in the customer's HRIS isn't coming back from Bindbee."
---

"Missing" has five distinct causes, and they need different fixes. Work through them in this order - each is cheaper to check than the next.

<Info>
  **Before you start**

  - You have something identifying the record: a name, work email, employee number, or the source system's own ID.
</Info>

## Steps

<Steps>
  <Step title="Rule out your own filters">
    Fetch without filters and search the result before anything else.

    The usual culprits: an `employment_status` filter excluding a status you didn't expect, a `modified_after` watermark from a run that already consumed the record, or a page walk that terminated early. See [Paginate Through Results](/how-to/reading-data/paginate-through-results).

    **Result:** You know whether the record is absent or just filtered out.
  </Step>

  <Step title="Check the sync ran after the record was created">
    A record created upstream after the last sync doesn't exist in Bindbee yet - see [Monitor Sync Status](/how-to/troubleshooting/monitor-sync-status).

    On a Development connector nothing syncs until you trigger it.

    **Result:** You know whether the data has had a chance to arrive.
  </Step>

  <Step title="Check whether the model synced">
    A run marked Partial loads some models and fails others. A model that failed returns nothing while everything else looks fine - see [Diagnose a Partial Sync](/how-to/troubleshooting/diagnose-a-partial-sync).

    A model out of scope also returns nothing, with no error at all - see [Restrict Which Models and Fields Sync](/how-to/data-model/restrict-models-and-fields).

    **Result:** You know whether the model was loaded.
  </Step>

  <Step title="Check permission">
    Many platforms return a filtered set rather than an error when credentials lack access, so an entire category of records can be silently absent.

    The signature is a model returning consistently fewer records than expected, or a specific population missing - see [Resolve a Source-System Permission Error](/how-to/troubleshooting/resolve-a-permission-error).

    **Result:** You know whether the source system is withholding the record.
  </Step>

  <Step title="Check whether it's excluded upstream">
    If everything above is clean, the record may not be returned by the source system's API at all.

    Common causes: the record sits outside the scope of the report or endpoint the integration reads; it's in a status the source excludes from its API; or it belongs to a legal entity, company, or population the connected credentials don't cover.

    Query the source system directly through [Passthrough](/how-to/data-model/make-a-passthrough-request) to confirm whether their API returns it at all. That single check separates a Bindbee problem from a source-system one.

    **Result:** A definitive answer about where the record stops.
  </Step>
</Steps>

## Records that were there and disappeared

Different problem, different causes.

**Terminated employees** are usually still returned with a terminal status rather than removed. If they've vanished entirely, the source may exclude terminated records from its API - that's an upstream behaviour, not a sync failure.

**Identifier changes.** If the source reissued the record's identifier, it may now be present under a different Bindbee `id` and look like a disappearance plus a new arrival - see [Trace an Unexpected or Duplicate Record](/how-to/troubleshooting/trace-an-unexpected-record).

**File-based connectors.** Where the integration reads files rather than an API, each delivery is a point-in-time snapshot. A record absent from the latest file may mean it was removed upstream, or that the file was generated differently - a report definition change, a filter, a partial export. Confirm which before treating absence as a deletion.

## If this didn't work

<AccordionGroup>
  <Accordion title="The record appears in raw_data but not the unified response">
    It synced but didn't map to a unified record - usually a required field the unified model needs is absent upstream. Report it with the connector ID and the raw payload.
  </Accordion>

  <Accordion title="It appears for one connector and not another at the same company">
    Connectors are independent, and credentials often differ in the populations they cover - different legal entities, companies, or permission scopes.
  </Accordion>

  <Accordion title="It's missing from a related model only">
    Models sync independently. An employee can exist while their employment, benefit, or dependent records don't - because that model failed, is out of scope, or genuinely has no record upstream.
  </Accordion>

  <Accordion title="Counts are close but not exact">
    That's reconciliation rather than a missing record, and usually a population-definition difference. See [Reconcile Record Counts Against the Source](/how-to/troubleshooting/reconcile-record-counts).
  </Accordion>
</AccordionGroup>
