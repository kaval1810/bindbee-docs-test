---
title: "Filter and Narrow a Collection"
sidebarTitle: "Filtering"
description: "Use query parameters to fetch a targeted subset instead of paging the full dataset and discarding records."
---

Filtering server-side cuts pages, latency, and rate-limit pressure. Filters combine with `AND` - every one you add narrows further.

<Info>
  **Before you start**

  - You know which field identifies the records you want.
</Info>

## Steps

<Steps>
  <Step title="Pick the filter">
    On employees:

    | Parameter | Matches | Notes |
    | --- | --- | --- |
    | `ids` | Bindbee record IDs | Comma-separated, no spaces |
    | `remote_id` | The source system's own ID | Single value |
    | `employee_number` | Employee number from the HRIS | Not unique on every system |
    | `work_email` | Work email | |
    | `first_name`, `last_name` | Name | |
    | `employment_status` | Status | See enum below |
    | `manager_id` | Employees reporting to a manager | Comma-separated |
    | `company_id` | Employees at a company | Comma-separated |
    | `groups` | Group membership | Comma-separated group IDs |
    | `work_locations` | Location | Comma-separated location IDs |
    | `pay_group_id` | Pay group | |
    | `modified_after` | Sync recency | See [Filter with modified_after](/how-to/reading-data/filter-with-modified-after) |

    **Result:** A parameter that matches your intent.
  </Step>

  <Step title="Use the exact status values">
    `employment_status` accepts:

    `ACTIVE` · `PENDING` · `INACTIVE` · `ACTIVE_EXTERNAL` · `INACTIVE_EXTERNAL` · `LEAVE` · `DECEASED` · `RETIRED` · `-`

    The `_EXTERNAL` values matter when you want employees only. Contingent workers and contractors commonly carry an external status, and excluding them is the usual fix for a population count that's higher than the customer expects.

    `-` means the source system supplied no status - treat it as unknown rather than as inactive.

    **Result:** A population that matches what the customer counts.

    <Warning>
      Which upstream value maps to which status varies by integration. Verify against one connector before relying on a status filter across all of them.
    </Warning>
  </Step>

  <Step title="Combine filters">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?employment_status=ACTIVE&work_locations=<LOCATION_ID>&page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Comma-separate multiple values on one parameter for `OR` within that field; separate parameters combine with `AND`.

    **Result:** A narrowed result set.
  </Step>

  <Step title="Fetch a known set by ID">
    When you already hold IDs - from a webhook payload, for instance - request them directly rather than filtering a full page walk.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?ids=019f618e-c850-716d-a510-74639514abf6,019f618e-c88c-7328-9575-ab78958608d2' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    **Result:** Only those records, in one request.
  </Step>
</Steps>

## If this didn't work

<AccordionGroup>
  <Accordion title="A filter returns nothing though records clearly exist">
    Filters are exact matches, not partial. `first_name=Jo` won't match `John`.

    For `remote_id` and `employee_number`, confirm the value against `raw_data` - the value shown in the HRIS UI is often not the identifier its API returns. See [Inspect raw data](/how-to/data-model/inspect-the-raw-upstream-payload).
  </Accordion>

  <Accordion title="employment_status returns fewer records than expected">
    Records with no upstream status carry `-` and are excluded by any specific status filter. Query `-` separately to see how many fall into that bucket.
  </Accordion>

  <Accordion title="The count doesn't match the customer's headcount">
    Usually a population-definition mismatch rather than missing data: contingent workers included, terminated employees retained, or one person holding several employment records.

    See [Record counts](/how-to/troubleshooting/reconcile-record-counts).
  </Accordion>

  <Accordion title="You need to filter on a field with no parameter">
    Two options. If the value is in `raw_data`, map it as a [custom field](/how-to/data-model/map-a-custom-field-from-the-dashboard) - though custom fields are returned, not filtered on, so you'd still filter client-side.

    Where the source system supports the filter natively, [Passthrough](/how-to/data-model/make-a-passthrough-request) reaches it directly at the cost of a provider-specific response shape.
  </Accordion>

  <Accordion title="You want to exclude records rather than include them">
    Filters are inclusive only. Fetch the statuses you want rather than excluding the ones you don't - several inclusive requests still beat paging everything.
  </Accordion>
</AccordionGroup>
