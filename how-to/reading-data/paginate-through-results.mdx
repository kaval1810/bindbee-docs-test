Every collection endpoint is paginated with `cursor` and `page_size`. Follow the cursor until it stops coming back.

<Info>
  **Before you start**

  - You can make an authenticated request - see [Authentication](/api-reference/basics/authentication).
</Info>

## Steps

<Steps>
  <Step title="Request the first page">
    Set `page_size`. The default is 50 and the maximum is 200 - a value above 200 is rejected rather than clamped.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    **Result:** A response containing `items`, `page_size`, and a `cursor`.

    ```json
    {
      "cursor": "MDE4YjE4ZWYtYzk5Yy03YTg2LTk5NDYtN2I3YzlkNTQzM2U1",
      "page_size": 200,
      "items": [ ... ]
    }
    ```
  </Step>

  <Step title="Follow the cursor">
    Pass the returned `cursor` back on the next request, keeping every other parameter identical.

    **Result:** The next page.

    <Warning>
      Filters must stay the same across pages. Changing `employment_status`, `modified_after`, or any other filter mid-walk invalidates the cursor's position and produces gaps or repeats.
    </Warning>
  </Step>

  <Step title="Loop until the cursor is exhausted">
    <CodeGroup>
      ```python Python
      import time, requests

      def fetch_all(path, params, api_key, connector_token):
          headers = {
              "Authorization": f"Bearer {api_key}",
              "X-Connector-Token": connector_token,
          }
          params = {**params, "page_size": 200}
          cursor, records = None, []

          while True:
              if cursor:
                  params["cursor"] = cursor
              r = requests.get(f"https://api.bindbee.dev{path}",
                               params=params, headers=headers, timeout=30)

              if r.status_code == 429:
                  # Wait, then retry the same cursor - don't advance
                  time.sleep(float(r.headers.get("Retry-After", 1)))
                  continue

              r.raise_for_status()
              body = r.json()
              records.extend(body["items"])
              cursor = body.get("cursor")
              if not cursor:
                  return records
      ```

      ```javascript Node
      async function fetchAll(path, params, apiKey, connectorToken) {
        const records = [];
        let cursor = null;

        while (true) {
          const qs = new URLSearchParams({ ...params, page_size: "200" });
          if (cursor) qs.set("cursor", cursor);

          const res = await fetch(`https://api.bindbee.dev${path}?${qs}`, {
            headers: {
              Authorization: `Bearer ${apiKey}`,
              "X-Connector-Token": connectorToken,
            },
            signal: AbortSignal.timeout(30_000),
          });

          if (res.status === 429) {
            // Wait, then retry the same cursor - don't advance
            const wait = Number(res.headers.get("Retry-After") ?? 1);
            await new Promise((r) => setTimeout(r, wait * 1000));
            continue;
          }
          if (!res.ok) throw new Error(`${res.status}`);

          const body = await res.json();
          records.push(...body.items);
          cursor = body.cursor;
          if (!cursor) return records;
        }
      }
      ```
    </CodeGroup>

    Stop when `cursor` is absent or null. Don't stop on a short page - a page returning fewer than `page_size` records is not reliably the last one.

    **Result:** The full collection.
  </Step>
</Steps>

## Reducing how much you page

Two things cut page count more than tuning `page_size`.

Filter server-side rather than fetching everything and discarding - see [Filtering](/how-to/reading-data/filter-and-narrow-a-collection). And on scheduled runs, fetch only what changed - see [Filter with modified_after](/how-to/reading-data/filter-with-modified-after).

## If this didn't work

<AccordionGroup>
  <Accordion title="Records are missing or repeated across pages">
    Check every parameter is byte-identical between requests. The most common cause is recomputing a timestamp filter per page - compute it once before the loop.

    A sync running mid-walk also shifts the underlying data. Page against a stable dataset by gating the run on the sync-completed event - see [Trigger a job on completion](/how-to/sync-control/trigger-a-job-on-sync-complete).
  </Accordion>

  <Accordion title="The loop never terminates">
    The exit condition must be the absence of a cursor. Terminating on an empty `items` array or a short page will either loop forever or stop early.
  </Accordion>

  <Accordion title="429 partway through">
    Rate limits are 200 requests per minute per connector token. Honour `Retry-After` and resume from the cursor you were on - see [Errors & issues](/explanation/errors-issues-and-limits).

    Different connectors have independent limits, so paging several customers in parallel is fine; paging one customer harder is not.
  </Accordion>

  <Accordion title="Pages are slow with expanded relations">
    `expand` and `include_raw_data` increase response size substantially at `page_size=200`. Drop `page_size` when using them.
  </Accordion>
</AccordionGroup>
