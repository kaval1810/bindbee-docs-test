You have a synced connector. This tutorial turns it into a directory sync you could actually ship.

**You will build:** a full initial import, then an incremental refresh.

Every request below needs both headers:

```http
Authorization: Bearer YOUR_BINDBEE_API_KEY
X-Connector-Token: END_USER_CONNECTOR_TOKEN
```

---

## Step 1 - Read one page

```bash
curl "https://api.bindbee.dev/api/hris/v1/employees?page_size=50" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN"
```

Every list endpoint returns the same envelope:

```json
{
  "cursor": "MDE4YjE4ZWYtYzk5Yy03YTg2LTk5NDYtN2I3YzlkNTQzM2U1",
  "page_size": 50,
  "items": [ ... ]
}
```

| Field | Meaning |
| --- | --- |
| `items` | The records on this page |
| `page_size` | How many were returned |
| `cursor` | Pass as `?cursor=` to get the next page. `null` means you are done |

`page_size` defaults to `50` and maxes out at `200`.

---

## Step 2 - Page through everything

The loop terminates when `cursor` comes back `null`. Do not try to guess a page count - there isn't one.

<CodeGroup>

```python Python
import os, requests

BASE = "https://api.bindbee.dev"
HEADERS = {
    "Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}",
    "X-Connector-Token": os.environ["CONNECTOR_TOKEN"],
}

def iter_employees(**filters):
    cursor = None
    while True:
        params = {"page_size": 200, **filters}
        if cursor:
            params["cursor"] = cursor
        resp = requests.get(f"{BASE}/api/hris/v1/employees",
                            headers=HEADERS, params=params, timeout=30)
        resp.raise_for_status()
        body = resp.json()
        yield from body["items"]
        cursor = body.get("cursor")
        if not cursor:
            return

for employee in iter_employees(employment_status="ACTIVE"):
    upsert(employee)
```

```javascript Node
const BASE = "https://api.bindbee.dev";
const headers = {
  Authorization: `Bearer ${process.env.BINDBEE_API_KEY}`,
  "X-Connector-Token": process.env.CONNECTOR_TOKEN,
};

async function* iterEmployees(filters = {}) {
  let cursor = null;
  do {
    const qs = new URLSearchParams({ page_size: "200", ...filters });
    if (cursor) qs.set("cursor", cursor);

    const res = await fetch(`${BASE}/api/hris/v1/employees?${qs}`, { headers });
    if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);

    const body = await res.json();
    yield* body.items;
    cursor = body.cursor;
  } while (cursor);
}

for await (const employee of iterEmployees({ employment_status: "ACTIVE" })) {
  await upsert(employee);
}
```

</CodeGroup>

<Warning>
  You get **200 requests per minute per connector**. At `page_size=200` that is
  40,000 records a minute, so pagination alone will rarely hit it - but if you
  fan out across many connectors in parallel, handle `429` with the `Retry-After`
  header. See [Rate Limits](/api-reference/basics/rate-limits).
</Warning>

## Step 3 - Filter server-side

Filter in the query string rather than pulling everything and discarding it.

| Parameter | Use |
| --- | --- |
| `employment_status` | `ACTIVE`, `INACTIVE`, `PENDING`, `LEAVE`, `TERMINATED`-equivalents |
| `company_id` | Employees at one company (multi-entity customers) |
| `manager_id` | Direct reports of a manager |
| `groups` | Employees in given groups - comma-separated IDs |
| `pay_group_id` | Employees in a pay group |
| `employee_number` | Look up by the customer-facing employee number |
| `remote_id` | Look up by the source system's own ID |
| `ids` | Fetch specific Bindbee IDs - comma-separated |
| `modified_after` | Only records Bindbee synced after this time |

```bash
# Active employees at one company
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "employment_status=ACTIVE" \
  --data-urlencode "company_id=01931edf-1a22-7f00-9b4e-2c9b7d1e5f04"
```

<Tip>
  Comma-separated ID parameters take **no spaces**:
  `ids=01931edf-04b6-...,01931edf-04c8-...`
</Tip>

## Step 4 - Expand relations instead of N+1

By default, relations come back as IDs:

```json
{
  "id": "01931edf-04b6-7391-8a5c-93ac4b395316",
  "display_full_name": "Jane Doe",
  "manager": "01931edf-04c8-7649-a470-d85f6161bd1a",
  "company": "01931edf-1a22-7f00-9b4e-2c9b7d1e5f04",
  "pay_group": "01931edf-2b33-7a11-8c5d-3d0c8e2f6a15"
}
```

Fetching each of those separately is an N+1 across the network. Use `expand`:

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "expand=manager,company"
```

`expand` takes comma-separated relation names with no spaces. You can restrict which fields come back on the expanded object using square brackets:

```
expand=manager[first_name,last_name,work_email],company
```

## Step 5 - Read only what changed

Re-importing the whole directory on every run is wasteful. `modified_after` returns only records Bindbee touched after a given ISO 8601 timestamp.

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "modified_after=2026-07-21T00:00:00.000Z"
```

<Warning>
  `modified_after` filters on **when Bindbee synced the record**, not when the
  HRIS changed it. A sync that rewrites an unchanged record still moves
  `modified_at`, so this filter is *inclusive* - you may receive records whose
  business fields are identical. Make your write path idempotent.

  Full explanation: [Filtering with `modified_after`](/how-to/filter-with-modified-after).
</Warning>

The dependable pattern: store the timestamp of your last successful import, pass it as `modified_after` next time, and upsert by `id`.

```python
last_run = load_watermark()          # e.g. "2026-07-21T00:00:00.000Z"
started  = utcnow_iso()

for employee in iter_employees(modified_after=last_run):
    upsert(employee)                 # keyed on employee["id"]

save_watermark(started)              # only after the whole run succeeds
```

<Tip>
  Save the watermark from *before* the run started, and only after the run
  completes. If you save the end time, records changed mid-run are missed
  forever.
</Tip>

## Step 6 - Get raw data when you need to debug

When a unified field is `null` and you want to know whether the source system had the value at all, ask for the upstream payload:

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "include_raw_data=true"
```

If the value is present in `raw_data` but absent from the unified field, that is a mapping question - and usually a [custom field](/how-to/map-custom-fields). If it is absent from `raw_data` too, the source system did not return it.

Add `include_custom_fields=true` to get your mapped custom fields in the response.

<Note>
  Both flags increase response size significantly. Use them for debugging and
  targeted reads, not for your bulk import loop.
</Note>
