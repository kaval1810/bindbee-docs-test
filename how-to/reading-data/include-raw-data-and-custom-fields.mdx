Both are omitted by default. Each is a query parameter you opt into per request.

<Info>
  **Before you start**

  - For custom fields, at least one field is mapped and resolves on this connector - see [Map from the dashboard](/explanation/how-custom-fields-work).
</Info>

## Steps

<Steps>
  <Step title="Add the parameter">
    | Parameter | Adds |
    | --- | --- |
    | `include_custom_fields=true` | A `custom_fields` object per record |
    | `include_raw_data=true` | A `raw_data` object per record, untransformed |

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employees?include_custom_fields=true&page_size=200' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Both are available on collection and single-record endpoints across models.

    **Result:** The extra keys inline.
  </Step>

  <Step title="Read custom fields by name">
    ```json
    {
      "id": "019f618e-c850-716d-a510-74639514abf6",
      "first_name": "Ada",
      "custom_fields": {
        "cost_center_name": "Engineering-NA",
        "guardian_mobile": "+1-555-123-4567"
      }
    }
    ```

    Only fields with a mapping that resolves on this connector appear. A field mapped for one connector and not another is absent rather than null on the second.

    **Result:** Your mapped values alongside unified fields.
  </Step>

  <Step title="Lower page_size when including raw data">
    `raw_data` carries the source system's full payload per record, which is frequently larger than the unified record itself. At `page_size=200` responses become slow and heavy.

    Drop to 25-50 when including it, or filter to specific records instead.

    **Result:** Responses that return in reasonable time.
  </Step>
</Steps>

## Which to use when

| Goal | Use |
| --- | --- |
| Consume a value in production | `include_custom_fields` |
| Find a field to map | The [raw-data endpoint](/how-to/reading-data/include-raw-data-and-custom-fields), not this parameter |
| Spot-check a mapping across many records | `include_raw_data`, with a small `page_size` |
| Audit what the source returns for one person | `include_raw_data` with an `ids` filter |

<Warning>
  `include_raw_data=true` is a debugging tool. Leaving it on in production inflates every response, slows every page, and means your code depends on provider-specific shapes that change without notice - which is exactly what the unified model exists to avoid.

  If you need a raw value routinely, map it as a custom field instead.
</Warning>

## If this didn't work

<AccordionGroup>
  <Accordion title="custom_fields is missing entirely">
    Confirm `include_custom_fields=true` is on the request. If it is, no mapped field resolves on this connector - check with the configuration endpoint, see [Scope a mapping](/explanation/how-custom-fields-work).
  </Accordion>

  <Accordion title="A field's value is INVALID_JSON_PATH">
    The mapping's expression doesn't resolve against this connector's payload. An invalid path returns this string rather than raising an error - see [Test an expression](/explanation/how-custom-fields-work).
  </Accordion>

  <Accordion title="A custom field is null for some records">
    Usually correct - not every record has every value. Confirm by checking `raw_data` for a record where you expect it.
  </Accordion>

  <Accordion title="Responses became slow after adding raw data">
    Expected. Lower `page_size`, or use the raw-data endpoint for a single record instead of paging everything with raw data attached.
  </Accordion>

  <Accordion title="You want raw data for one employee only">
    Combine with a filter: `?ids=<EMPLOYEE_ID>&include_raw_data=true`. That's far cheaper than paging the collection.
  </Accordion>
</AccordionGroup>

## Inspecting the upstream payload

When a value exists in the HRIS but not in the unified response, it is almost always present in the raw upstream payload. Inspect that payload to find the exact path, then map it.

<Info>
  **Before you start**

  - You know the model the field should belong to - `employee`, `employment`, `benefit`, and so on.
  - The connector has completed at least one sync, or you accept the integration's canned sample instead.
</Info>

### Steps

<Steps>
  <Step title="Fetch the raw payload">
    Call the raw-data endpoint with the category and model slug. Pass `connector_token` to see this connector's most recent synced row, or `integration_slug` to see a generic sample for the integration.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/v1/custom-fields/raw-data?category=HRIS&model=employee&connector_token=<CONNECTOR_TOKEN>' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>'
    ```

    **Result:** The untransformed JSON the source system returned for one record.

    <Tip>
      If the connector has never synced, the endpoint falls back to the integration's canned sample. That's enough to write a mapping against, but confirm the shape once real data lands.
    </Tip>
  </Step>

  <Step title="Locate the field">
    Search the payload for the value you expect. Match on the value, not the field name - source systems rarely name things the way their UI does.

    **Result:** You have a JSON path, for example `personalInfo.birthDate` or `customFieldGroup[0].value`.
  </Step>

  <Step title="Write a JMESPath expression">
    Convert the location into a [JMESPath](https://jmespath.org/) expression.

    | What you see | Expression |
    | --- | --- |
    | `{"personalInfo": {"birthDate": "1991-03-16"}}` | `personalInfo.birthDate` |
    | `{"fields": [{"name": "Cost Center", "value": "ENG-NA"}]}` | `fields[?name=='Cost Center'].value \| [0]` |
    | `{"customField4611": "REG"}` | `customField4611` |

    **Result:** An expression that resolves to a single value.
  </Step>

  <Step title="Confirm it resolves">
    Dry-run the expression before saving it, using the dashboard's preview control or the preview endpoint. See [Test an expression](/explanation/how-custom-fields-work).

    **Result:** The preview returns your value rather than `null`.
  </Step>
</Steps>

### Map what you found

Finding the path doesn't surface the field - a mapping does. Create it from the dashboard for one-off changes, or via the API when the configuration needs to be versioned or replicated across environments.

### If this didn't work

<AccordionGroup>
  <Accordion title="The field isn't in the payload at all">
    Two likely causes.

    The field may not be in scope for this connector. Some models and fields are excluded from sync by configuration - see [Restrict what syncs](/explanation/scope-and-permissions).

    Or the source system may not expose it on this endpoint. Several HRIS platforms return different field sets to different API surfaces, and permission level changes what's returned - see [Permission errors](/how-to/troubleshooting/resolve-a-permission-error). If the field is genuinely absent from the API, the source system's own configuration usually has to change first.
  </Accordion>

  <Accordion title="The payload looks different from another connector on the same integration">
    Expected. Payload shape varies with the source system's configuration, plan tier, and enabled modules, so two connectors on the same integration can differ.

    Map at connector level for these, and reserve integration-level mappings for fields that are genuinely consistent. See [Scope a mapping](/explanation/how-custom-fields-work).
  </Accordion>

  <Accordion title="The value appears in raw data but the mapped field returns INVALID_JSON_PATH">
    The expression didn't resolve. Bindbee returns `"INVALID_JSON_PATH"` in place of the value rather than raising an error, so this surfaces at read time rather than at save time.

    Most often it's an array that needs an index or a filter, or a quoting error inside a filter expression.
  </Accordion>

  <Accordion title="You need the raw payload in the API response instead">
    Add `include_raw_data=true` to a unified endpoint to get `raw_data` inline per record. That's useful for spot checks across many records; the raw-data endpoint above is better for discovering structure on one.
  </Accordion>
</AccordionGroup>
