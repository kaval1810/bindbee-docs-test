---
title: "Move a Connector Between Environments"
sidebarTitle: "Move a Connector"
description: "Switch an existing connector between Development and Production without recreating it or asking the end user to reconnect."
---

A connector created in the wrong environment - or a test connection that should stop being billed, or a pilot that's ready to go live - can be switched without recreating it. The authorised connection is retained, so the end user does not reconnect.

<Warning>
  This switch is not self-serve. There is no control for it in the dashboard - request it through your support channel with the list of connectors to move.
</Warning>

<Info>
  **Before you start**

  - You have the connector names or IDs to move, and the target environment.
  - You can update the API key your services use for those connectors.
</Info>

## Steps

<Steps>
  <Step title="List the connectors to move">
    Filter to **Active Connectors** on the Connectors tab and identify the ones to switch - see [Connectors](/platform/overview). Incomplete connectors - where the end user opened the Magic Link but never finished authorising - show alongside active ones and are a common source of miscounting.

    It's usually faster to name the connectors that should *stay* in Production and have everything else moved, rather than enumerating a long list to move.

    **Result:** An unambiguous list.
  </Step>

  <Step title="Request the switch">
    Send the list and the target environment to your support channel.

    **Result:** Support confirms once the switch is done.
  </Step>

  <Step title="Swap the API key in your services">
    The connection is retained, but the environment's key is not. After the move, calls for those connectors must use the target environment's key.

    A Production key against a moved-to-Development connector returns `401`. Update every service, scheduled job, and stored configuration that references those connectors.

    **Result:** Your calls authenticate against the new environment.

    <Note>
      Webhooks are environment-specific too. A connector moved to Development stops firing your Production webhooks. If you rely on sync events for these connectors, create the equivalent Development webhook - see [Create a Webhook](/webhooks/overview).
    </Note>
  </Step>

  <Step title="Adjust for the new sync behaviour">
    Moving **to Development**: automatic syncs stop. Trigger them manually or via API - see [Sync a Development Connector](/how-to/sync-control/sync-a-development-connector).

    Moving **to Production**: automatic syncs begin on the default 24-hour cadence.

    **Result:** You know whether data now refreshes on its own.
  </Step>

  <Step title="Verify">
    Call an endpoint for one moved connector with the new key, and check the connector's sync history in the target environment.

    **Result:** A `200` with expected data, and the connector visible in the target environment.
  </Step>
</Steps>

## What you just did

You changed the connector's environment while preserving its authorisation and its record history. Because record identities survive the move, the IDs your system has stored remain valid - which is why moving beats deleting and recreating.

## If this didn't work

<AccordionGroup>
  <Accordion title="Calls started returning 401 right after the move">
    Expected if a service is still using the old environment's key. Environment isolation is enforced on the key, so this is the first symptom of a missed service. See [Authenticate a Request](/how-to/setup/authenticate-a-request).
  </Accordion>

  <Accordion title="Data stopped refreshing after moving to Development">
    Development connectors do not sync automatically. Trigger a sync when you need current data - see [Force a Resync](/how-to/sync-control/force-a-resync).
  </Accordion>

  <Accordion title="Some connectors appear not to have moved">
    Check the Connectors tab filter. Incomplete connectors are frequently mistaken for ones that were missed. Filter to **Active Connectors** and re-check before reporting it.
  </Accordion>

  <Accordion title="You need to move a live customer without interrupting them">
    The end user is not involved and does not reconnect. The interruption risk is entirely on your side - the window between the switch and your services picking up the new key. Deploy the key change first where you can, or schedule the move outside your processing window.
  </Accordion>
</AccordionGroup>
