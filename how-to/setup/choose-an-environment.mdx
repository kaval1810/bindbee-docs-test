title: "Choose an Environment"

---

Development and Production are fully isolated. Keys, connectors, data, and webhooks in one are invisible to the other. Choosing the wrong one is recoverable, but not self-serve - so it's worth getting right at connection time.

<Info>
  **Before you start**

  - You know whether this connection carries real customer data.
</Info>

## Steps

<Steps>
  <Step title="Decide from the connection's purpose">
    | Use Development when | Use Production when |
    | --- | --- |
    | Testing an integration before go-live | A paying customer's live connection |
    | A sandbox or demo tenant of an HRIS | Data feeds anything customer-facing |
    | Internal test accounts, however realistic | You need syncs to run unattended |
    | Validating field mappings | |

    The deciding question is whether anything downstream depends on the data being current without someone triggering it.

    **Result:** You know which environment this connection belongs in.
  </Step>

  <Step title="Use the matching API key">
    Generate the key for that environment from **Settings → API Keys** and copy it immediately - a key is shown once. Development keys reach Development data only; Production keys reach Production data only. A mismatched key returns `401`, not a clearer error.

    **Result:** Your client is configured for the right environment.
  </Step>

  <Step title="Account for the behaviour differences">
    | | Development | Production |
    | --- | --- | --- |
    | Automatic sync | No - trigger manually or via API | Yes, every 24 hours by default |
    | Connector limit | Unlimited | Counted |
    | Billing | Not billed | Billed per connector |
    | Key sharing | Safe to share within the team | Treat as a production secret |
    | Webhooks | Development webhooks only | Production webhooks only |

    **Result:** You won't be surprised by stale data in Development or by connector counts in Production.

    <Warning>
      Production connectors are counted and billed automatically. Test connections left in Production get billed as live ones - the most common cause of an unexpected connector count is testing done against a Production key.
    </Warning>
  </Step>

  <Step title="Create the connection">
    Generate a Magic Link while the dashboard is in the chosen environment - see [Magic Link](/explanation/magic-link). The environment is fixed at creation.

    **Result:** The connector exists in the intended environment.
  </Step>
</Steps>

## If this didn't work

<AccordionGroup>
  <Accordion title="A connector is in the wrong environment">
    It can be moved without recreating it or asking the end user to reconnect, but the switch isn't self-serve today. See [Move between environments](/how-to/setup/move-a-connector-between-environments).
  </Accordion>

  <Accordion title="A Development connector is returning stale data">
    Working as designed - Development connectors don't sync on a schedule. See [Development connectors](/how-to/sync-control/sync-a-development-connector).
  </Accordion>

  <Accordion title="Your connector count is higher than the connections you recognise">
    Incomplete connectors - ones where the end user opened the Magic Link but never finished authorising - appear alongside active ones. Filter to **Active Connectors** on the Connectors tab before counting - see [Connectors](/platform/overview), which has separate Development and Production tabs.
  </Accordion>

  <Accordion title="You want a third environment for staging">
    There are two. Since Development connectors are unlimited and unbilled, teams typically run staging against Development with a separate set of connectors and a shared Development key.
  </Accordion>
</AccordionGroup>
