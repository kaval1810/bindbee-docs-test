Creating links in the dashboard works while you're onboarding customers one at a time. Once connection is part of your product's own signup or setup flow, generate them programmatically.

<Info>
  **Before you start**

  - You know the integration slug and category - see [Look Up an Integration Slug](/how-to/setup/look-up-an-integration-slug).
  - You're using the API key for the environment the connector should live in - the environment is fixed at creation.
</Info>

## Steps

<Steps>
  <Step title="Build the link token payload">
    ```json
    {
      "end_user_data": {
        "org_name": "Acme Corp.",
        "origin_id": "064e1cd7-49ad-4e6d-8005-7e4c92fe9675"
      },
      "category": "HRIS",
      "integration": "bamboohr"
    }
    ```

    | Field | Purpose |
    | --- | --- |
    | `org_name` | The customer's organisation name, shown in the dashboard. Required |
    | `origin_id` | **Your** identifier for this customer. Required |
    | `email` | The end user's email. Optional |
    | `category` | `HRIS`, `ATS`, or `LMS`. Required |
    | `integration` | The integration slug. Required |

    **Result:** A payload identifying who is connecting and to what.
  </Step>

  <Step title="Set origin_id to something you can resolve">
    This is the field that makes programmatic creation worth doing. Every webhook payload returns it as `connector.origin_id`, so an incoming sync or error event resolves to your customer record with no mapping table.

    Use your own stable internal identifier - a customer or tenant ID, not an email or company name that can change.

    **Result:** Events you can route without a lookup.
  </Step>

  <Step title="Create the link and deliver it">
    Post the payload to the link token endpoint with your API key. Create it from your backend - the key must never reach the browser.

    <CodeGroup>

    ```bash cURL
    curl --request POST \
      --url 'https://api.bindbee.dev/api/embedded/v1/link/create-link-token' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "end_user_data": {
          "org_name": "Acme Corp.",
          "origin_id": "064e1cd7-49ad-4e6d-8005-7e4c92fe9675"
        },
        "category": "HRIS",
        "integration": "bamboohr"
      }'
    ```

    ```python Python
    import os, requests

    resp = requests.post(
        "https://api.bindbee.dev/api/embedded/v1/link/create-link-token",
        headers={"Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}"},
        json={
            "end_user_data": {
                "org_name": "Acme Corp.",
                "origin_id": "064e1cd7-49ad-4e6d-8005-7e4c92fe9675",
            },
            "category": "HRIS",
            "integration": "bamboohr",
        },
        timeout=30,
    )
    resp.raise_for_status()
    link_token = resp.json()["link_token"]
    ```

    </CodeGroup>

    The response carries a single field:

    ```json
    { "link_token": "..." }
    ```

    Present it to the customer - redirect to it, or embed it in your own onboarding flow. See [Create Link Token](/sdk/create-link-token) for the full schema.

    **Result:** The customer authorises without you sending a link by hand.
  </Step>

  <Step title="Wait for the connector via webhook">
    Connector creation completes when the customer finishes authorising, which may be minutes or days later. Don't poll.

    Subscribe to sync events so you learn when the connection is live and has data - see [Choose Webhook Events](/webhooks/events). Match the incoming `origin_id` to your customer record.

    **Result:** Your system learns about the connection when it's actually usable.
  </Step>

  <Step title="Store the connector token">
    Fetch the connector by the `origin_id` you set, and read `connector_token` from it.

    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/connectors?origin_id=064e1cd7-49ad-4e6d-8005-7e4c92fe9675&is_active=true' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>'
    ```

    Store it against your customer. It's what you pass as `X-Connector-Token` on every subsequent call - see [Authenticate a Request](/how-to/setup/authenticate-a-request).

    <Note>
      There is no `temporary_token` in this flow. That exchange belongs to the
      embedded SDK, where `onSuccess` hands your frontend a short-lived token to
      swap for a `connector_token` - see
      [Embed the Connection Flow](/how-to/connections/embed-the-connection-flow).
      With a hosted link you read the token from the connector instead.
    </Note>

    **Result:** You can read and write for that customer.
  </Step>
</Steps>

## Letting the customer choose the integration

`integration` is required, so the platform is decided before the link exists - there is no flow where the end user picks it. The same applies to the embedded component, where `category` and `integration` are fixed when the token is created.

If your customers use different systems, collect that choice in your own UI first and generate the matching link. Render the options from the lookup endpoint, which is already filtered to what your organization can actually connect - see [Look Up an Integration Slug](/how-to/setup/look-up-an-integration-slug).

## If this didn't work

<AccordionGroup>
  <Accordion title="The integration slug is rejected">
    Check hyphens versus underscores, and that the slug matches the category. Use the lookup endpoint rather than a hard-coded list - see [Look Up an Integration Slug](/how-to/setup/look-up-an-integration-slug).
  </Accordion>

  <Accordion title="The connector was created in the wrong environment">
    The environment comes from the API key used to create the link. It can be switched without the customer reconnecting - see [Move a Connector Between Environments](/how-to/setup/move-a-connector-between-environments).
  </Accordion>

  <Accordion title="Connectors are created but never complete">
    Customers opened the link and abandoned it. Incomplete connectors persist and inflate connector counts - filter to **Active Connectors** when reviewing, and follow up or delete them.
  </Accordion>

  <Accordion title="You generated two links for the same customer">
    Two completed links produce two connectors, both billed in Production. To fix a broken connection, relink the existing connector rather than issuing a new link - see [Update Credentials After an Auth Failure](/how-to/connections/update-credentials).

    Check for an existing connector by `origin_id` before generating.
  </Accordion>

  <Accordion title="You need to generate links in bulk">
    Generate per customer rather than in one batch - each link is specific to one end user, and links generated far in advance are more likely to be stale by the time they're opened.
  </Accordion>
</AccordionGroup>
