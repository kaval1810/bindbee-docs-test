---
title: "Map Custom Fields"
description: "Surface a value from the raw upstream payload as a named field on a unified model — validated before you save it, so it doesn't fail silently in production."
---

A custom field is a saved JMESPath expression that plucks a value out of data Bindbee already synced. No extra fetch, no extra latency.

<Info>
  Concepts — fields vs mappings, org vs connector scope, why it works this way —
  are in [Custom Fields: The Mental Model](/explanation/custom-fields-mental-model).
  This page is the procedure.
</Info>

## Before you start

Confirm the value is actually in the synced payload. If it isn't, no mapping can produce it.

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "include_raw_data=true" \
  --data-urlencode "page_size=1"
```

Not there? You need [passthrough](/how-to/use-passthrough) instead.

## The procedure

<Steps>
  <Step title="Discover">
    Get the valid `category`, `model` and `integration_slug` values.
  </Step>
  <Step title="Inspect the raw payload">
    See exactly what your JMESPath will run against.
  </Step>
  <Step title="Validate the expression">
    Dry-run it against real connector data — nothing is persisted.
  </Step>
  <Step title="Create the field">
    Declare it on a `(category, model)` pair.
  </Step>
  <Step title="Create a mapping">
    Attach it to an integration (org-wide) or one connector.
  </Step>
  <Step title="Verify and read">
    Confirm the effective configuration, then request it back.
  </Step>
</Steps>

---

## Step 1 — Discover valid targets

```bash
curl "https://api.bindbee.dev/api/v1/lookup/models" \
  -H "Authorization: Bearer $BINDBEE_API_KEY"

curl "https://api.bindbee.dev/api/v1/lookup/integrations" \
  -H "Authorization: Bearer $BINDBEE_API_KEY"
```

Use the exact values these return. Guessed model names are rejected.

## Step 2 — Inspect the raw payload

```bash
curl -G "https://api.bindbee.dev/api/v1/custom-fields/raw-data" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  --data-urlencode "connector_token=$CONNECTOR_TOKEN" \
  --data-urlencode "model=employee"
```

Read the structure carefully — this is the document your expression targets.

<Warning>
  Inspect payloads from **more than one employee**. Optional fields, empty
  arrays and absent objects are exactly where positional expressions break, and a
  single sample won't show you.
</Warning>

## Step 3 — Write and validate the expression

Bindbee uses [JMESPath](https://jmespath.org/).

| Goal | Expression |
| --- | --- |
| Top-level field | `employeeNumber` |
| Nested | `customFields.guardianMobile` |
| Field with awkward characters | `"custom_1234"` |
| Filter an array | `contacts[?type=='emergency'].phone \| [0]` |
| First element (fragile) | `contacts[0].phone` |
| First non-null of several | `[primaryPhone, mobilePhone, homePhone] \| [?@] \| [0]` |

<Warning>
  Avoid positional indexing like `contacts[0]`. Vendors do not promise array
  order. When it is wrong it doesn't error — it silently returns the wrong
  person's phone number, which is far worse than a failure.
</Warning>

Validate before saving. The preview endpoint dry-runs against real data and persists nothing:

```bash
curl -X POST "https://api.bindbee.dev/api/v1/custom-fields/preview" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "connector_token": "'"$CONNECTOR_TOKEN"'",
    "model": "employee",
    "json_path": "contacts[?type=='\''emergency'\''].phone | [0]"
  }'
```

<Tip>
  This step is optional and skipping it is the main cause of `INVALID_JSON_PATH`
  appearing in production responses. It costs one request.
</Tip>

## Step 4 — Create the custom field

```bash
curl -X POST "https://api.bindbee.dev/api/v1/custom-fields" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "category": "HRIS",
    "model": "employee",
    "name": "guardian_mobile",
    "description": "Emergency contact mobile number"
  }'
```

Declaring the field creates the *name*. It does not yet return anything anywhere.

<Tip>
  Name fields the way your product thinks about them, not the way the vendor
  does. `guardian_mobile` stays stable while the underlying vendor path varies
  per integration — that stability is the whole benefit.
</Tip>

## Step 5 — Create a mapping

Scope determines reach.

<Tabs>
  <Tab title="Organization-scoped">
    Applies to every connector of that integration in your org. Start here.

    ```bash
    curl -X POST "https://api.bindbee.dev/api/v1/custom-fields/mapping" \
      -H "Authorization: Bearer $BINDBEE_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "custom_field_id": "0192cc01-...",
        "integration_slug": "bamboohr",
        "json_path": "customFields.guardianMobile"
      }'
    ```
  </Tab>
  <Tab title="Connector-scoped">
    Applies to one connector and **overrides** the org-level mapping for it.
    Use for customers whose HRIS is configured unusually.

    ```bash
    curl -X POST "https://api.bindbee.dev/api/v1/custom-fields/mapping" \
      -H "Authorization: Bearer $BINDBEE_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "custom_field_id": "0192cc01-...",
        "connector_token": "'"$CONNECTOR_TOKEN"'",
        "json_path": "legacy_fields.emergency_no"
      }'
    ```
  </Tab>
</Tabs>

<Warning>
  A custom field needs a mapping **per integration**. BambooHR and Workday store
  the same concept in entirely different places. One mapping covers one
  integration — not all of them.
</Warning>

## Step 6 — Verify the effective configuration

```bash
curl -G "https://api.bindbee.dev/api/v1/custom-fields/configuration" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  --data-urlencode "connector_token=$CONNECTOR_TOKEN"
```

This shows which mapping is winning per connector and which fields remain unmapped — the fastest way to catch "I declared the field but never mapped it for this integration".

## Step 7 — Read it back

Opt in with `include_custom_fields=true`:

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "include_custom_fields=true"
```

```json
{
  "id": "01931edf-04b6-7391-8a5c-93ac4b395316",
  "first_name": "Jane",
  "work_email": "jane@acme.com",
  "custom_fields": {
    "guardian_mobile": "+1-555-0148"
  }
}
```

Read from `custom_fields`, never the root — that namespace is what keeps your fields safe from future unified-schema additions.

<Warning>
  Mapping changes take effect on the **next read**, not the next sync — the
  expression re-runs against already-stored data. Changing a mapping is instant
  and requires no resync.
</Warning>

## Do it in the dashboard instead

Everything above is available as a visual flow under **Custom Fields** in the dashboard, including interactive payload exploration. It creates identical configuration, tagged `source: "DASHBOARD"` rather than `"API"`.

Use the dashboard for exploration and one-offs; use the API when configuration should be reproducible across environments. See [Dashboard Configuration](/custom-fields/dashboard).

<Warning>
  If you manage custom fields as code, dashboard-created fields are drift. Pick
  one source of truth and check the other for surprises.
</Warning>

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `INVALID_JSON_PATH` | Expression doesn't parse or resolve | Preview it (Step 3) |
| Field absent from response | `include_custom_fields=true` missing | Add the parameter |
| Field present but `null` | No mapping for this integration, or expression matches nothing | Check the configuration endpoint |
| Works on one customer, not another | Their HRIS is configured differently | Add a connector-scoped override |
| Was populated, now null | Customer renamed the field upstream | Re-inspect `raw_data` and remap |
| Wrong value returned | Positional array indexing | Use a filtered expression |

<Tip>
  Monitor for custom fields that were populated and stopped. This failure is
  completely silent — nothing errors, the value simply becomes `null`.
</Tip>
