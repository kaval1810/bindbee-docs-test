title: "Create an Employee Payroll Run"
sidebarTitle: "Create a Payroll Run"
description: "Write earnings, deductions, and taxes for an employee into the customer's payroll system."
---

This is the write behind benefits deduction workflows: an ICHRA allowance, an HSA contribution, or a voluntary benefit premium reaching payroll as a deduction line.

It is also the write with the least tolerance for error. Payroll runs affect what people are paid.

<Info>
  **Before you start**

  - You've confirmed the integration supports this write - see [Check Which Writes an Integration Supports](/how-to/writing-data-back/check-write-support).
  - You have the deduction or earning codes defined in the customer's payroll system.
</Info>

## Steps

<Steps>
  <Step title="Fetch the schema">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs/meta/post' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'x-connector-token: <CONNECTOR_TOKEN>'
    ```

    Expect array-typed fields for earnings, deductions, and taxes, each with its own `required` array under `items`. Expect `integration_params` to be required - payroll writes almost always need a platform-specific reference such as a pay statement type.

    **Result:** The contract for this integration.
  </Step>

  <Step title="Source the codes from the customer's configuration">
    Deduction and earning codes are defined per customer in their payroll system. A code that works for one customer on a platform will not work for another.

    <Warning>
      There is no reliable automatic mapping from a benefit plan to a payroll deduction code. The relationship is customer-specific configuration, and getting it wrong posts a deduction against the wrong plan - which surfaces as a payroll discrepancy, not an API error.

      Confirm the mapping with the customer explicitly and store it against the connector. Treat it as configuration you own, not something to infer.
    </Warning>

    **Result:** Codes that exist in this customer's payroll configuration.
  </Step>

  <Step title="Build the arrays">
    ```json
    {
      "employee": "019f618e-c850-716d-a510-74639514abf6",
      "earnings": [
        { "earning_code": "REG", "amount": 4500 }
      ],
      "deductions": [
        { "deduction_code": "HSA_EE", "employee_deduction": 150 }
      ],
      "integration_params": {
        "pay_statement_type_id": "<PLATFORM_VALUE>"
      }
    }
    ```

    Use the field names from the schema. Send amounts in the currency and precision the schema specifies - some platforms expect minor units.

    **Result:** A body matching the contract.
  </Step>

  <Step title="Send with an idempotency key">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/hris/v1/employee-payroll-runs' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'x-connector-token: <CONNECTOR_TOKEN>' \
      --header 'x-idempotency-key: <UNIQUE_KEY>' \
      --header 'Content-Type: application/json' \
      --data @payroll-run.json
    ```

    <Warning>
      Derive the key from the employee and the pay period - something like `payroll-{employee_id}-{period_end}`. A duplicate payroll write can double a deduction, and the person affected finds out on payday.
    </Warning>

    **Result:** The payroll data is written.
  </Step>

  <Step title="Verify against the pay period">
    Read the run back and confirm it landed in the intended pay period - see [Get Employee Payroll Runs](/hris/employee-payroll-runs/get-employee-payroll-runs).

    Payroll systems close periods. A write submitted after close may be rejected, or silently applied to the next open period, which is worse.

    **Result:** Confirmation the amounts are in the right period.
  </Step>
</Steps>

## Timing matters more than on other writes

Payroll runs on a cycle with a cut-off. Deduction changes need to arrive before the customer's processing deadline, which is theirs and not visible through the API.

Where a change misses the cut-off, the correction is usually a catch-up adjustment in the following period rather than a retroactive edit. Design for that rather than assuming a write can be undone.

## If this didn't work

<AccordionGroup>
  <Accordion title="A deduction code is rejected">
    The code doesn't exist in this customer's configuration, or isn't valid for this employee's pay group. Confirm it against their payroll setup rather than reusing a code from another customer.
  </Accordion>

  <Accordion title="The write succeeded but the amount is wrong">
    Check the precision the schema expects - a value sent in dollars where minor units were expected is off by a factor of 100 and will pass validation.
  </Accordion>

  <Accordion title="The write was rejected because the period is closed">
    Expected after the customer's cut-off. Queue the change for the next open period and reconcile as an adjustment.
  </Accordion>

  <Accordion title="A deduction was applied twice">
    A retry without a consistent idempotency key, or the same logical change submitted through two paths. Correct it in the payroll system and fix the key derivation.
  </Accordion>

  <Accordion title="You need to map plan years to payroll periods">
    Payroll runs carry payment dates, not plan years. Assigning a deduction to the right plan year means cross-referencing the payment date against the benefit's coverage period from the benefits models - see [Read Benefits Data](/how-to/reading-data/read-benefits-data).
  </Accordion>
</AccordionGroup>
