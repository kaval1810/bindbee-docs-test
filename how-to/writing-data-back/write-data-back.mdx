Reads are uniform. Writes are not: every HRIS demands a different set of required fields, different enum values, and different integration-specific parameters.

Bindbee's answer is the **Meta API**: ask what this integration requires *before* you build the request body.

**You will build:** a schema-driven write that works across connectors without per-vendor branching.

---

## The write workflow

<Steps>
  <Step title="Call the Meta endpoint">
    Get the JSON Schema for this operation on this connector.
  </Step>
  <Step title="Read required fields, enums and integration params">
    Everything the source system will insist on is described in the response.
  </Step>
  <Step title="Build a conforming request body">
    Validate locally if you like - the response is JSON Schema compatible.
  </Step>
  <Step title="POST to the write endpoint">
    Same headers as any other request.
  </Step>
</Steps>

<Warning>
  Skipping the Meta call is the most common cause of write failures. A body that
  works for BambooHR will be rejected by ADP, and the missing field is usually an
  `integration_params` value you cannot guess.
</Warning>

## What you can write

| Operation | Write endpoint | Meta endpoint |
| --- | --- | --- |
| Create Employee | `POST /api/hris/v1/employees` | `GET /api/hris/v1/employees/meta/post` |
| Create Time Off | `POST /api/hris/v1/time-off` | `GET /api/hris/v1/time-off/meta/post` |
| Create Timesheet Entry | `POST /api/hris/v1/timesheet-entry` | `GET /api/hris/v1/timesheet-entry/meta/post` |
| Create Employee Payroll Run | `POST /api/hris/v1/employee-payroll-runs` | `GET /api/hris/v1/employee-payroll-runs/meta/post` |

ATS supports writes across candidates, applications, jobs, offers, activities, attachments and more - see the [ATS API Reference](/ats/candidate/create-candidate).

<Note>
  Write support varies by integration. An operation can be supported for a
  connector even when its Meta schema is not yet implemented - see
  [Handling 501](#when-a-meta-schema-is-not-available) below.
</Note>

## Step 1 - Ask what this connector needs

```bash
curl "https://api.bindbee.dev/api/hris/v1/time-off/meta/post" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN"
```

```json
{
  "type": "object",
  "properties": {
    "employee": {
      "type": "string",
      "description": "The Bindbee ID of the employee requesting time off.",
      "isRequired": true
    },
    "start_time": {
      "type": "string",
      "format": "date-time",
      "isRequired": true
    },
    "end_time": {
      "type": "string",
      "format": "date-time",
      "isRequired": true
    },
    "request_type": {
      "type": "string",
      "isRequired": true,
      "enum": ["VACATION", "SICK", "PERSONAL"],
      "enumInformation": [
        { "value": "VACATION", "description": "Paid vacation" },
        { "value": "SICK", "description": "Sick leave" },
        { "value": "PERSONAL", "description": "Personal day" }
      ]
    },
    "integration_params": {
      "type": "object",
      "isRequired": true,
      "properties": {
        "policy_id": { "type": "string", "isRequired": true }
      },
      "required": ["policy_id"]
    },
    "additional_attributes": {
      "type": "object",
      "isRequired": false
    }
  },
  "required": ["employee", "start_time", "end_time", "request_type"]
}
```

Read it like this:

| Keyword | Means |
| --- | --- |
| `required` (array) | Every mandatory field at this level |
| `isRequired` (boolean) | Whether this one field is mandatory |
| `enum` | The only accepted values |
| `enumInformation` | Human-readable meaning of each enum value - render these in your UI |
| `format` | Extra constraint, e.g. `email`, `date-time`, `uuid` |
| `integration_params` | **Validated** fields the source system demands |
| `additional_attributes` | **Free-form** passthrough of vendor-specific values |

<Warning>
  `integration_params` and `additional_attributes` are not interchangeable.
  `integration_params` has a defined schema and is validated - often required.
  `additional_attributes` is unvalidated and forwarded as-is. Putting a required
  integration parameter in `additional_attributes` will silently fail to apply.
</Warning>

Full reference: [Meta APIs for write operations](/meta-apis-for-write-operations).

## Step 2 - Build the body from the schema

Do not hardcode the shape. Drive it from the response:

```python
import requests, os

BASE = "https://api.bindbee.dev"

def headers(connector_token):
    return {
        "Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}",
        "X-Connector-Token": connector_token,
        "Content-Type": "application/json",
    }

def get_meta(connector_token, path):
    resp = requests.get(f"{BASE}{path}", headers=headers(connector_token))
    if resp.status_code == 501:
        raise MetaUnavailable(resp.json().get("detail"))
    resp.raise_for_status()
    return resp.json()

def required_fields(schema):
    """Every required field, including nested integration_params."""
    out = list(schema.get("required", []))
    params = schema.get("properties", {}).get("integration_params", {})
    out += [f"integration_params.{f}" for f in params.get("required", [])]
    return out

meta = get_meta(CONNECTOR_TOKEN, "/api/hris/v1/time-off/meta/post")
print(required_fields(meta))
# ['employee', 'start_time', 'end_time', 'request_type', 'integration_params.policy_id']
```

<Tip>
  If you render a form for your users, generate it from the Meta response. Use
  `enum` for the options, `enumInformation[].description` for the labels, and
  `description` for help text. The form stays correct as connectors change.
</Tip>

## Step 3 - Submit the write

```bash
curl -X POST "https://api.bindbee.dev/api/hris/v1/time-off" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "employee": "01931edf-04b6-7391-8a5c-93ac4b395316",
    "start_time": "2026-08-10T00:00:00Z",
    "end_time": "2026-08-14T00:00:00Z",
    "request_type": "VACATION",
    "integration_params": {
      "policy_id": "pol_4417"
    },
    "additional_attributes": {
      "internal_note": "Approved by manager in our app"
    }
  }'
```

### Creating an employee

`POST /api/hris/v1/employees` follows the same pattern. Two Meta endpoints exist for it:

| Endpoint | Returns |
| --- | --- |
| `GET /api/hris/v1/employees/meta/post` | The JSON Schema for the request body |
| `GET /api/hris/v1/employees/create/meta` | Integration-specific creation metadata |

Call the schema endpoint first and build from it exactly as above.

## Step 4 - Confirm the write landed

<Warning>
  A `2xx` from Bindbee means the source system accepted the request. It does
  **not** mean the record is readable from Bindbee's unified API yet - that
  requires a sync.
</Warning>

Two ways to confirm:

- **Wait for the next sync**, then read the record back. This is the correct behaviour to build around.
- **Trigger a resync** when a user is watching and expects immediate feedback: `POST /api/embedded/v1/connectors/resync`. Do not do this on a timer - see [Force a resync](/how-to/sync-control/force-a-resync).

Write the record optimistically in your own UI, and let the sync reconcile it.

## When a Meta schema is not available

If Bindbee has not implemented the Meta schema for that integration and operation, the Meta endpoint returns:

```http
501 Not Implemented
```

```json
{
  "detail": "Meta API is not implemented for Time Off in bamboohr. You can request this feature by contacting support@bindbee.dev."
}
```

This does **not** necessarily mean the write is unsupported - only that the schema is not published. Options:

1. Attempt the write with the documented unified fields and read the error.
2. Contact `support@bindbee.dev` to request the schema.
3. Use [passthrough](/how-to/writing-data-back/make-a-passthrough-request) to call the vendor endpoint directly.

Handle `501` explicitly rather than treating it as a generic failure:

```python
try:
    meta = get_meta(connector_token, "/api/hris/v1/time-off/meta/post")
    body = build_from_schema(meta, user_input)
except MetaUnavailable:
    body = build_minimal_body(user_input)   # documented unified fields only
    log.warning("meta schema unavailable; falling back")
```

## Error handling

| Status | Meaning | Action |
| --- | --- | --- |
| `400` / `422` | Body failed validation | Re-read the Meta schema; check `integration_params` |
| `401` | Bad API key | [Authenticate](/how-to/setup/authenticate-a-request) |
| `403` | Missing/invalid connector token | Add `X-Connector-Token` |
| `429` | Rate limited | Back off using `Retry-After` |
| `501` | Meta not implemented | See above |

<Warning>
  **Writes are not idempotent.** Bindbee does not deduplicate a repeated create.
  Retrying a timed-out `POST` can create a duplicate in your customer's HRIS.
  Record your own request key before submitting, and reconcile on the next sync
  rather than blind-retrying.
</Warning>

Full guidance: [Handle errors](/how-to/setup/handle-api-errors).
