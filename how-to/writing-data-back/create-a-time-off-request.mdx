<Info>
  **Before you start**

  - You've confirmed the integration supports this write - see [Check write support](/explanation/how-meta-apis-work).
  - You have the Bindbee `id` of the employee the request is for.
</Info>

## Steps

<Steps>
  <Step title="Fetch the schema">
    ```bash
    curl --request GET \
      --url 'https://api.bindbee.dev/api/hris/v1/time-off/meta/post' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>'
    ```

    Pay attention to the leave-type enum and to any required `integration_params`. Both vary by platform - see [Fetch a schema](/explanation/how-meta-apis-work).

    **Result:** The exact contract for this integration.
  </Step>

  <Step title="Resolve the employee">
    Use the Bindbee employee `id`, not the employee number or the source system's identifier. If you're starting from an upstream identifier, resolve it first with `remote_id` - see [Filtering](/how-to/reading-data/filter-and-narrow-a-collection).

    **Result:** A valid employee reference.
  </Step>

  <Step title="Send the request with an idempotency key">
    ```bash
    curl --request POST \
      --url 'https://api.bindbee.dev/api/hris/v1/time-off' \
      --header 'Authorization: Bearer <BINDBEE_API_KEY>' \
      --header 'X-Connector-Token: <CONNECTOR_TOKEN>' \
      --header 'X-Idempotency-Key: <UNIQUE_KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "employee": "019f618e-c850-716d-a510-74639514abf6",
        "request_type": "VACATION",
        "start_time": "2026-09-01T00:00:00Z",
        "end_time": "2026-09-05T00:00:00Z",
        "units": "DAYS",
        "amount": 5
      }'
    ```

    Use field names and enum values from the schema rather than the example above.

    <Warning>
      Always send `X-Idempotency-Key`. Writes create real records in the customer's HRIS, and a retried request without a key creates a duplicate leave request - which someone then has to find and cancel manually.

      Derive the key from your own request identity, not a random value, so a retry of the same logical request reuses the same key.
    </Warning>

    **Result:** The request is created in the source system.
  </Step>

  <Step title="Confirm it landed">
    Read it back rather than trusting the response alone - see [Get Time Off](/hris/time-off/get-time-off-list).

    The record won't appear in Bindbee's synced data until the next sync. To confirm sooner, [force a resync](/explanation/how-syncing-works).

    **Result:** Verified in the customer's system.
  </Step>
</Steps>

## What the write does and doesn't decide

A created request enters the source system's own workflow. It is not automatically approved - most platforms place it in a pending state for a manager, and the approval status is theirs to set, not yours.

Balances are also the source system's. Bindbee submits the request; whether it's permitted against the employee's accrued balance is enforced upstream, and a request exceeding the balance is typically rejected there rather than by Bindbee.

## If this didn't work

<AccordionGroup>
  <Accordion title="The leave type is rejected">
    Leave types are platform-specific and often customer-specific - a customer can define their own categories. Use a value from the schema's `enum`, and read `enumInformation` for what each means rather than matching on the name.

    If the customer's own category isn't in the enum, it may need supplying through `integration_params` or `additional_attributes`.
  </Accordion>

  <Accordion title="Dates are rejected or land wrong">
    Send ISO 8601 with an explicit timezone. Where a platform works in whole days, a timestamp with a time component can shift the request by a day across timezone boundaries - check whether the schema expects a date or a datetime.
  </Accordion>

  <Accordion title="The write succeeds but nothing appears in Bindbee">
    Expected until the next sync. Reads serve synced data, so a record created seconds ago won't be there yet.
  </Accordion>

  <Accordion title="You created duplicates during a retry">
    An idempotency key prevents this. To clean up, cancel the duplicates in the source system - Bindbee doesn't own the record once created.
  </Accordion>

  <Accordion title="The employee reference is rejected">
    Confirm you're sending the Bindbee `id`, and that the employee belongs to this connector. IDs are per connector; an ID from another customer's connector won't resolve.
  </Accordion>
</AccordionGroup>
