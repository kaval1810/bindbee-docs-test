Bindbee uses **two** credentials. Almost every day-one problem is a request carrying the wrong one, or only one of the two.

## The rule in one table

| Endpoint kind | `Authorization` | `X-Connector-Token` |
| --- | --- | --- |
| Organization-scoped — connectors, integrations, lookups, custom field definitions | Required | — |
| Customer data — employees, benefits, payroll, candidates, courses | Required | **Required** |
| Link token creation, token exchange | Required | — |
| Resync a connector | Required | Required |

<Info>
  **`Authorization` says who *you* are. `X-Connector-Token` says *whose data* you
  want.** Reading a customer's employees needs both.
</Info>

---

## Step 1 — Pick the right environment

| Environment | Key | Reads |
| --- | --- | --- |
| Development | `dev_api_key` | Development connectors only |
| Production | `prod_api_key` | Production connectors only |

They are not interchangeable in either direction. Using a Development key against a Production connector fails; it does not fall back.

<Warning>
  The key you use when creating a `link_token` decides which environment the
  resulting connector lives in — permanently. Connectors cannot be moved between
  environments.
</Warning>

---

## Step 2 — Get your API key

Go to [app.bindbee.dev/settings/keys](https://app.bindbee.dev/settings/keys) and copy the key for the environment you want.

<img
  src="https://images.unifyx.dev/documentation_images/api_keys.png"
  alt="API Keys"
  className="block"
/>

Store it as a server-side secret — environment variable or secret manager.

<Warning>
  Never ship an API key to a browser, mobile app, or any client you don't
  control. It grants access to every connector in that environment. The only
  value intended for the frontend is the short-lived `link_token`.
</Warning>

## Step 3 — Send the API key

Bearer token in the `Authorization` header. The `Bearer ` prefix — capital B, one space — is required.

```http
Authorization: Bearer YOUR_BINDBEE_API_KEY
```

Verify it with a request that needs nothing else:

<CodeGroup>

```bash cURL
curl "https://api.bindbee.dev/api/v1/lookup/integrations" \
  -H "Authorization: Bearer $BINDBEE_API_KEY"
```

```python Python
import os, requests

resp = requests.get(
    "https://api.bindbee.dev/api/v1/lookup/integrations",
    headers={"Authorization": f"Bearer {os.environ['BINDBEE_API_KEY']}"},
)
resp.raise_for_status()
```

```javascript Node
const res = await fetch("https://api.bindbee.dev/api/v1/lookup/integrations", {
  headers: { Authorization: `Bearer ${process.env.BINDBEE_API_KEY}` },
});
if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);
```

</CodeGroup>

A `200` confirms the key. Do this before debugging anything else — it isolates "bad key" from "bad request".

## Step 4 — Get a connector token

The `connector_token` identifies one customer's connection. Three ways to obtain it:

<Tabs>
  <Tab title="From the API">
    ```bash
    curl "https://api.bindbee.dev/api/hris/v1/connectors" \
      -H "Authorization: Bearer $BINDBEE_API_KEY"
    ```

    ```json
    {
      "items": [
        {
          "id": "018b18ef-c487-703c-afd9-0ca478ccd9d6",
          "integration_slug": "bamboohr",
          "origin_id": "tenant_9f2c1b40",
          "connector_token": "jk23h4jk23hk4j2h3kj4h23kjh4k23jh4k2j3h4",
          "status": "COMPLETE"
        }
      ]
    }
    ```

    Match on `origin_id` — your own customer ID.
  </Tab>
  <Tab title="From the link flow">
    After a customer links via Bindbee Embed, exchange the `temporary_token`:

    ```bash
    curl "https://api.bindbee.dev/api/embedded/v1/connectors/connector_token/$TEMPORARY_TOKEN" \
      -H "Authorization: Bearer $BINDBEE_API_KEY"
    ```

    ```json
    {
      "connector_token": "jk23h4jk23hk4j2h3kj4h23kjh4k23jh4k2j3h4",
      "connector_id": "123e4567-e89b-12d3-a456-426614174000"
    }
    ```

    This is a **server-side** call — it requires your API key.
  </Tab>
  <Tab title="From the dashboard">
    Open the connector and read the token from the **Overview** section.

    <img
      src="https://images.unifyx.dev/documentation_images/connector.png"
      alt="Connector Token"
      className="block"
    />

    Useful for manual testing. Don't build a workflow on copy-paste.
  </Tab>
</Tabs>

<Tip>
  Store the token against your customer record when you first receive it, rather
  than looking it up on every request. Encrypt it at rest — it is a credential.
</Tip>

## Step 5 — Send both headers

```http
Authorization: Bearer YOUR_BINDBEE_API_KEY
X-Connector-Token: END_USER_CONNECTOR_TOKEN
```

<CodeGroup>

```bash cURL
curl "https://api.bindbee.dev/api/hris/v1/employees?page_size=10" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN"
```

```python Python
import os, requests

class BindbeeClient:
    def __init__(self, base_url="https://api.bindbee.dev"):
        self.base_url = base_url
        self.api_key = os.environ["BINDBEE_API_KEY"]
        self.session = requests.Session()

    def get(self, path, connector_token=None, **params):
        headers = {"Authorization": f"Bearer {self.api_key}"}
        if connector_token:
            headers["X-Connector-Token"] = connector_token
        resp = self.session.get(
            f"{self.base_url}{path}", headers=headers, params=params, timeout=30
        )
        resp.raise_for_status()
        return resp.json()

client = BindbeeClient()
client.get("/api/hris/v1/employees", connector_token=token, page_size=10)
```

```javascript Node
class BindbeeClient {
  constructor(baseUrl = "https://api.bindbee.dev") {
    this.baseUrl = baseUrl;
    this.apiKey = process.env.BINDBEE_API_KEY;
  }

  async get(path, { connectorToken, ...params } = {}) {
    const headers = { Authorization: `Bearer ${this.apiKey}` };
    if (connectorToken) headers["X-Connector-Token"] = connectorToken;

    const qs = new URLSearchParams(params);
    const res = await fetch(`${this.baseUrl}${path}?${qs}`, { headers });
    if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);
    return res.json();
  }
}
```

</CodeGroup>

<Tip>
  Make the connector token a parameter of your client, not a constructor
  argument. You will call the same endpoints for many customers, and a client
  bound to one token invites cross-tenant bugs.
</Tip>

## Step 6 — Pick the right region

| Region | Base URL |
| --- | --- |
| Default | `https://api.bindbee.dev` |
| EU | `https://api-eu.bindbee.dev` |

Use the same region everywhere for a given customer — backend calls, the SDK's `serverUrl`, and the token exchange. A connector created in one region is not visible from the other.

## Troubleshooting

| Status | Cause | Fix |
| --- | --- | --- |
| `401` | Missing `Bearer ` prefix | `Authorization: Bearer <key>` — not the bare key |
| `401` | Wrong environment key | Development key ↛ Production data |
| `401` | Key regenerated | Copy the current key from settings |
| `401` | Whitespace in the key | Trim; a trailing newline from `cat`/copy is common |
| `403` | `X-Connector-Token` missing | Add it for any customer-data endpoint |
| `403` | Token belongs to another environment | Match key and connector environment |
| `404` on connector lookup | Wrong category path | `/api/hris/…` vs `/api/ats/…` vs `/api/lms/…` |
| `429` | Rate limited | 200/min per connector — [Rate Limits](/api-reference/basics/rate-limits) |
| Empty `items`, `200` | Auth is fine; sync hasn't run | [How syncing works](/explanation/how-syncing-works) |

### Isolate the layer

When something fails, work outward:

```bash
# 1. Is the key valid?              → expects 200
curl -i "https://api.bindbee.dev/api/v1/lookup/integrations" \
  -H "Authorization: Bearer $BINDBEE_API_KEY"

# 2. Does the connector exist?      → expects the connector in items[]
curl -i "https://api.bindbee.dev/api/hris/v1/connectors" \
  -H "Authorization: Bearer $BINDBEE_API_KEY"

# 3. Does the data call work?       → expects 200
curl -i "https://api.bindbee.dev/api/hris/v1/employees?page_size=1" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN"
```

Whichever step fails first is where the problem is.

<Warning>
  Redact `Authorization` and `X-Connector-Token` in request logging and error
  reporting. `curl -i` output pasted into a ticket is a real and common source of
  credential leaks.
</Warning>
