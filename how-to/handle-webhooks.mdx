Polling every connector on a timer is the default way teams start, and the first thing that stops scaling. This tutorial replaces it.

**You will build:** a signature-verified webhook receiver that triggers an incremental read.

---

## Step 1 - Decide whether you need them

Answer these before writing any code:

| If… | Then |
| --- | --- |
| You show HR data in a UI on demand | You may not need webhooks at all - read on request |
| You mirror data into your own database | Use `connector_data_modified` + `modified_after` |
| You act on employee joins/leaves (provisioning, enrolment) | Use `employee_data_changed` |
| You show connection health to your customer | Use the three `connector_sync_*` events |
| You need sub-24-hour freshness | Webhooks won't help - that is a **sync frequency** question, not a delivery one |

<Warning>
  Webhooks tell you *when a sync produced changes*. They do not make data fresher.
  If your customer needs hourly data, the sync schedule has to change - see
  [Data freshness](/explanation/data-freshness).
</Warning>

Full comparison: [Webhooks vs Polling](/explanation/webhooks-vs-polling).

## Step 2 - Understand the events

| Event | Fires when | `data` contains |
| --- | --- | --- |
| `connector_sync_started` | A sync begins | Connector sync status object |
| `connector_synced` | A sync completes successfully | Connector sync status object |
| `connector_sync_error` | A sync fails | Status object, plus a top-level `error` |
| `employee_data_changed` | Employees created/updated | Array of employee IDs |
| `connector_data_modified` | Any model created/updated | Object of `model → [ids]` |

Every payload includes `webhook`, `connector` and `sync` objects. `connector.origin_id` is your own customer ID - that is your routing key.

```json
{
  "webhook": { "webhook_id": "...", "url": "...", "event": "connector_data_modified" },
  "connector": {
    "id": "018f99e2-ed3a-7f4c-ae97-83d619bdf95c",
    "integration_slug": "breathehr",
    "categories": ["HRIS"],
    "origin_id": "tenant_9f2c1b40",
    "connector_status": "COMPLETE"
  },
  "data": {
    "hris_bank_info": ["0190d9d8-cf5b-7ce4-b60f-1fd95c04adee"],
    "hris_employment": ["0190d9d9-023d-7259-97e1-b38682dec062"]
  },
  "sync": { "sync_id": "019f146e-...", "sync_type": "AUTOMATED", "sync_name": "#13" }
}
```

<Note>
  The payload gives you **IDs, not records**. It is a change *notification*, not a
  change *feed*. You still fetch the data from the API.
</Note>

Full payload reference: [Webhooks](/webhooks/overview).

## Step 3 - Stand up an endpoint

Requirements, all of which matter:

- Public HTTPS URL accepting `POST`
- Responds within **10 seconds** - Bindbee times out after that
- Returns `2xx` on success; anything else is retried
- Keeps the **raw request body** available for signature verification

<Warning>
  Do the work asynchronously. Acknowledge the request, then process on a queue.
  A handler that fetches employees inline will blow the 10-second budget on any
  reasonably sized customer and get retried.
</Warning>

## Step 4 - Verify the signature

Every request carries `X-Bindbee-Webhook-Signature`: a base64url-encoded HMAC-SHA256 of the **raw body**, keyed with your organization's signature key from [app.bindbee.dev/webhooks](https://app.bindbee.dev/webhooks).

<CodeGroup>

```python Python (Flask)
import base64, hashlib, hmac, os
from flask import Flask, request, abort

app = Flask(__name__)
SIGNATURE_KEY = os.environ["BINDBEE_WEBHOOK_SIGNATURE_KEY"]

def is_valid(raw_body: bytes, received_signature: str) -> bool:
    digest = hmac.new(
        SIGNATURE_KEY.encode("utf-8"), raw_body, hashlib.sha256
    ).digest()
    expected = base64.urlsafe_b64encode(digest).decode()
    return hmac.compare_digest(expected, received_signature)

@app.post("/webhooks/bindbee")
def receive():
    signature = request.headers.get("X-Bindbee-Webhook-Signature")
    if not signature or not is_valid(request.get_data(), signature):
        abort(401)

    enqueue(request.get_json())      # process off the request path
    return "", 200                   # acknowledge fast
```

```javascript Node (Express)
const crypto = require("crypto");
const express = require("express");

const app = express();
const SIGNATURE_KEY = process.env.BINDBEE_WEBHOOK_SIGNATURE_KEY;

// Capture the raw body - re-serializing the parsed JSON will not match
app.use(
  express.json({
    verify: (req, _res, buf) => {
      req.rawBody = buf.toString("utf-8");
    },
  }),
);

function isValid(rawBody, receivedSignature) {
  const expected = crypto
    .createHmac("sha256", SIGNATURE_KEY)
    .update(rawBody)
    .digest("base64")
    .replace(/\+/g, "-")
    .replace(/\//g, "_");

  const a = Buffer.from(expected, "utf-8");
  const b = Buffer.from(receivedSignature, "utf-8");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

app.post("/webhooks/bindbee", (req, res) => {
  const signature = req.headers["x-bindbee-webhook-signature"];
  if (!signature || !isValid(req.rawBody, signature)) {
    return res.sendStatus(401);
  }

  enqueue(req.body);
  res.sendStatus(200);
});
```

</CodeGroup>

<Warning>
  Verify against the **raw bytes** you received. `JSON.stringify(req.body)` or
  `json.dumps(payload)` will reorder keys and change whitespace, and the HMAC will
  never match. This is the single most common cause of "signature mismatch".
</Warning>

More detail and failure modes: [Validate webhook signatures](/how-to/validate-webhook-signatures).

## Step 5 - Register the webhook

In the dashboard, go to **Configure → Webhooks → New webhook**:

1. **Destination URL** - your endpoint. Use **Test URL** to confirm reachability.
2. **Webhook Name** - e.g. `prod-employee-changes`.
3. **Webhook Type** - `Production` or `Development`.
4. **Events** - tick only what you handle.

<Warning>
  Webhook type is environment-scoped. A **Production** webhook never fires for
  Development connectors, and vice versa. Register both if you test in
  Development.
</Warning>

Step-by-step with screenshots: [Webhooks](/webhooks/overview).

## Step 6 - Process the event

The handler's job is: route by `origin_id`, then fetch what changed.

```python
CONNECTOR_EVENTS = {
    "connector_sync_started", "connector_synced", "connector_sync_error",
}

def handle(payload):
    event    = payload["webhook"]["event"]
    tenant   = payload["connector"]["origin_id"]
    sync_id  = payload["sync"]["sync_id"]

    if already_processed(sync_id, event):     # idempotency guard
        return

    if event in CONNECTOR_EVENTS:
        update_connection_health(tenant, payload)
        if event == "connector_sync_error":
            alert(tenant, payload["error"]["message"])

    elif event == "employee_data_changed":
        # data is a flat list of employee IDs
        fetch_and_upsert_employees(tenant, ids=payload["data"])

    elif event == "connector_data_modified":
        # data is {model_name: [ids]}
        for model, ids in payload["data"].items():
            fetch_and_upsert(tenant, model, ids)

    mark_processed(sync_id, event)
```

Fetch the changed records by ID rather than re-importing:

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "ids=0190d9d8-ac9b-76cb-a5ee-df70994e6f3d"
```

<Tip>
  A simpler and very robust alternative: ignore the ID lists entirely, and on
  `connector_synced` run a `modified_after` read using your stored watermark.
  Slightly more traffic, far less state to get wrong.
</Tip>

## Step 7 - Make it idempotent

Bindbee retries up to **4 times within 60 seconds** on network failures and any non-`2xx` response. You will receive duplicates.

| Property | Value |
| --- | --- |
| Max retries | 4 |
| Retry window | 60 seconds |
| Timeout per attempt | 10 seconds |
| Retry triggers | Network/protocol failures and all non-`2xx` responses |

Two rules make duplicates harmless:

1. **Deduplicate** on `sync.sync_id` + `webhook.event`.
2. **Upsert, never insert** - key on the record `id`.

<Warning>
  Retries stop after 4 attempts inside a 60-second window. If your endpoint is
  down for longer than that, those events are gone. Keep a scheduled
  `modified_after` reconciliation running as a safety net - daily is usually
  enough.
</Warning>

---

## Step 8 - Verify

1. Trigger a sync: `POST /api/embedded/v1/connectors/resync` with the connector token.
2. Watch delivery attempts and responses under [Logs → Webhooks](https://app.bindbee.dev/logs/webhooks).
3. Confirm you received `connector_sync_started` → `connector_synced`.
4. Replay the same payload deliberately and confirm nothing double-writes.
