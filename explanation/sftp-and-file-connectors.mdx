Not every HR system offers a usable API. Some expose one that omits the models customers need; some charge for API access; some have none at all. For these, the integration works by the customer's system delivering a file on a schedule, and Bindbee reading it.

The mechanics are different enough from an API connector that several behaviours look like faults until you know why.

## A file is a snapshot, not a change feed

An API connector can ask a question: what changed since yesterday? A file cannot be asked anything. It arrives, it contains whatever it contains, and that is the entire available information.

So each delivery is treated as a complete statement of truth at the moment it was produced. Bindbee reads the file, compares it against what it holds, and reconciles. There are no change events, no deltas, and no way to distinguish a field that was edited from one that was always that way.

## Absence is a signal

This is the behaviour that surprises people. In an API connector, a record you do not ask about is simply not mentioned. In a file connector, a record that is not in the file is a statement that it should not be there.

When an employee present in previous deliveries stops appearing, Bindbee infers they are no longer active and marks the record accordingly rather than leaving it as it was. It does not delete the record.

<Warning>
A truncated, filtered, or partially-generated file will therefore mark large numbers of employees inactive at once. If a customer changes their export configuration, restricts it to one division, or delivers a file that failed partway through generation, the effect on your data is indistinguishable from a mass termination.
</Warning>

Because the source file rarely carries a termination date for someone who has simply stopped being listed, the end date on these records is inferred rather than reported.

## Cadence belongs to the customer

An API connector syncs on Bindbee's schedule. A file connector syncs on the customer's - data is only as fresh as the last delivery, and Bindbee cannot request a new one.

If the customer's export runs weekly, forcing a resync re-reads the same file and changes nothing. A delivery that silently stops looks like data that has frozen: no error, no failed sync, just a connector whose records stop moving.

The practical monitoring signal is delivery recency rather than sync success. A connector can be healthy and current in every respect while consuming a file that is three weeks old.

## Coverage is narrower and fixed

A file contains the columns the customer's export was configured to produce. Models and fields outside that configuration are not merely unpopulated - they are unobtainable, and no permission change or scope adjustment will surface them.

Widening coverage means the customer changing their export configuration, which is a request to their HR or IT team rather than a setting either of you can adjust.

## Why it works this way

Treating absence as meaningful is a choice with a real failure mode, and the alternative has a worse one.

If absence were ignored - records simply persisting until something explicitly said otherwise - then terminations would never propagate at all for these integrations. Most HR exports list current employees and drop leavers; there is no termination row to read. An integration that could not detect departures would leave former employees looking active indefinitely, which in a benefits or provisioning context means people retaining access and coverage they should have lost.

Inferring departure from absence catches the common case correctly at the cost of misreading a broken file as a mass exit. That trade favours the failure that is loud and recoverable over the one that is silent and compliance-relevant - a sudden wave of inactive employees is noticed within hours, whereas a leaver who never became inactive may never be noticed at all.

The snapshot model itself is not a design preference. It is what the transport allows. A file has no mechanism for expressing change, so completeness is the only contract available.

## What this means for you

- **Monitor delivery recency, not sync success.** A file connector can be entirely healthy and weeks stale.
- **Treat a large simultaneous status change as suspect.** Real terminations are rarely synchronised; broken exports always are.
- **Forcing a resync does not fetch new data.** It re-reads the existing file.
- **Coverage gaps are export-configuration problems**, resolved by the customer's HR or IT team.
- **Inferred end dates are approximations.** Do not use them where a legally accurate termination date is required.
