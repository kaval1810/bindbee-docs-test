Something did not work. Before you can fix it you need to know whose failure it was - **yours, Bindbee's, or the source system's.** Those three arrive through different channels and look nothing like each other.

## Three origins, three channels

| Origin | How it reaches you | Where the detail is |
| --- | --- | --- |
| **Your request was wrong** | A `4xx` on the response | `detail` in the response body |
| **The source system refused** | Not on your response at all - it happens during a sync | Connector logs, sync-status webhook |
| **Nothing failed** | `200`, well-formed, data absent | Nowhere - it is scope or permissions |

The middle row is the one that catches people. **A source-system failure does not surface on the request you just made.**

Bindbee holds a synced copy, so an upstream refusal happened in the background - possibly hours earlier - and your read succeeds against whatever was last stored.

The third row has no error to look up at all - see [Scope & permissions](/explanation/scope-and-permissions) for how to tell those apart.

## What a Bindbee error body looks like

Errors Bindbee returns to you carry a `detail` field in one of two shapes: a string for most failures, an array of per-field objects for validation errors.

That is the whole documented surface - see [Handle API Errors](/how-to/setup/handle-api-errors).

## Upstream failures keep the source system's own answer

When Bindbee's request to the HRIS fails, the record of it preserves the source system's response rather than a Bindbee interpretation of it - the upstream status, the endpoint being called, and the response body unmodified.

That body is the thing to read first. It contains the HR system's own error format, whatever that is: BambooHR returns a structured problem document, Dayforce its own process-result codes inside a `403`, Workday SOAP faults.

**None of these are normalised, and that is the point.** The upstream message frequently names the exact permission or field at fault, which a translated message would lose.

<Warning>
An upstream `403` almost always means the authorising credentials lack a permission - not that Bindbee is unauthorised. **The fix is with your customer's HRIS administrator, not with your API keys.**
</Warning>

## Write failures are source-shaped

Reads mostly fail for structural reasons - credentials, permissions, coverage. **Writes fail for business reasons, and those belong entirely to the source system.**

A time-off request rejected for insufficient balance, a hire rejected because a tenant requires a custom field, a payroll entry rejected because the period is closed - none are conditions Bindbee can evaluate in advance.

It submits the write and reports what came back.

So write error handling cannot be fully generic. You can handle the transport uniformly, but the messages that tell your user what to do are shaped by whichever system they run.

## Logs and issues

Not every failure surfaces on a response. A sync that fails partway through happens in the background, and you find out from the connector's logs or a sync-status webhook.

**Logs** hold the per-request record: which endpoint, which status, what came back. This is where you answer "why is this connector not returning benefits" when nothing in your own application errored.

**Issues** are the layer above. Where a log entry is one request and its response, an issue is a failure Bindbee raised against a connector with a likely cause attached - carrying the evidence, so you and support read the same thing. See [Issues](/platform/issues).

<Warning>
Issues are a Dashboard surface. **There is no issues endpoint in the API**, so anything your own monitoring must act on has to come from sync-status webhooks or the connector's `status` - see [Connector lifecycle](/explanation/connector-lifecycle).
</Warning>

## Two rate limits

They protect different things, and only one of them is about you.

**Bindbee's limit** is 200 requests per minute per connector, and it is what a `429` from Bindbee refers to. It is generous relative to normal application traffic.

**The source system's limits** are usually far tighter, and they constrain how fast Bindbee can *sync* rather than how fast you can read. Most HR systems permit a small number of requests per minute per tenant.

That second one is **the main reason sync cadence is measured in hours rather than minutes**, and it is not something either of you can configure away.

## Why it works this way

Passing upstream errors through unmodified is a deliberate refusal to be helpful in a way that would hurt.

The tempting alternative is normalisation - map every source system's failure into one Bindbee taxonomy so your code handles a single shape. That works for the coarse cases and destroys the fine ones.

HR systems return errors naming specific fields, permission objects and tenant configuration. Collapsing *"the Workday integration system user lacks Get_Workers permission on this security group"* into `PERMISSION_DENIED` throws away **the one sentence that tells the administrator what to change.**

The trade is that your error handling has to be layered. Handle the envelope generically - retry, log, alert on status. Surface the upstream body to whoever can act on it, which is usually a human at the customer rather than your code.

## What this means for you

- **Read the upstream response body first** when a failure came from the source system. It usually names the fix.
- **Route upstream `403`s to the customer's HRIS administrator**, not to your own credentials.
- **Do not expect source-system failures on your own responses.** They happen during syncs; watch logs and sync-status webhooks.
- **Do not build generic user-facing messages for write failures.** The useful detail is source-specific.
- **A successful response with missing data is not an error case** - it is a scope or permissions question.
