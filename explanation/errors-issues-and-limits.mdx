Something did not work. Before you can fix it you need to know whose failure it was - **yours, Bindbee's, or the source system's.** Those three arrive through different channels and look nothing like each other.

## Three origins, three channels

| Origin | How it reaches you | Where the detail is |
| --- | --- | --- |
| **Your request was wrong** | A `4xx` on the response | `detail` in the response body |
| **The source system refused** | Not on your response at all - it happens during a sync | Connector logs, sync-status webhook |
| **Nothing failed** | `200`, well-formed, data absent | Nowhere - it is scope or permissions |

The middle row is the one that catches people. **A source-system failure does not surface on the request you just made.**

Bindbee holds a synced copy, so an upstream refusal happened in the background - possibly hours earlier - and your read succeeds against whatever was last stored.

The third row has no error to look up at all - see [Scope & permissions](/explanation/scope-and-permissions) for how to tell those apart.

## Classify the status

Errors fall into three groups: fix the request, back off and retry, or act on the connection. Treating them uniformly - retrying everything, or failing on everything - causes the two most common integration problems.

| Status | Meaning | Retry? |
| --- | --- | --- |
| `401` | Missing, malformed, or wrong-environment API key | No - fix credentials |
| `403` | Valid credentials without access to this resource | No - see below |
| `404` | Resource doesn't exist for this connector | No |
| `422` | Validation failed - an invalid query or path parameter, or a write body the schema rejects | No - the body names the field |
| `429` | Rate limit exceeded | Yes, after `Retry-After` |
| `5xx` | Server-side | Yes, with backoff |

Retrying a `4xx` other than `429` will never succeed and consumes the connector's rate limit while failing.

<Note>
  `422` is not a write-only code. A bad query parameter on a read returns `422`,
  not `400` - so a filter value the API rejects lands in the same branch as a
  malformed write body.
</Note>

## Read the response body, not just the status

Every error Bindbee returns carries a `detail` field, and **its type depends on the status.** On `401`, `403`, `404` and `429` it is a string:

```json
{ "detail": "Rate limit exceeded" }
```

On `422` it is an array, one entry per rejected field - here, a `page_size` above the maximum of 200:

```json
{
  "detail": [
    {
      "loc": ["query", "page_size"],
      "msg": "Input should be less than or equal to 200",
      "type": "less_than_equal"
    }
  ]
}
```

`loc` is the path to the offending field and `msg` says what was expected - together they usually identify the fault without any further digging.

<Warning>
  The same key holds two different types. Code that treats `detail` as a string
  - logging it, matching on it, lower-casing it - works against every other
  status and then throws on the first `422`. Branch on the status before
  touching `detail`.
</Warning>

## Handle 429 using the headers

Wait `Retry-After` seconds, then resume. Don't retry immediately, and don't use a fixed delay - the header is authoritative.

Better still, watch `X-RateLimit-Remaining` on successful responses and slow down before you hit zero. Throttling proactively is cheaper than recovering. Every response carries it, not just the failures - see [Rate Limits](/api-reference/basics/rate-limits) for all four headers and what each one holds.

## The two causes of 403

A `403` means the credentials are valid but don't permit this resource. Two very different situations produce it:

- **A connector token used against the wrong API category** - an HRIS connector called on `/api/ats/v1/*`. That's a bug in your code.
- **A model whose writes are disabled for that integration** - see [Check write support](/explanation/how-meta-apis-work).

Neither is retryable, and neither is a source-system permission problem - those surface as sync failures or empty results rather than `403`. See [Permission errors](/how-to/troubleshooting/resolve-a-permission-error).

## Back off exponentially on 5xx

Retry with exponential backoff and jitter, capped at a few attempts. Jitter matters when many connectors fail together - without it, every client retries in lockstep.

```python Python
import random, time, requests

RETRY_ON = {429, 500, 502, 503, 504}

def request_with_retry(method, url, *, max_attempts=4, timeout=30, **kwargs):
    for attempt in range(max_attempts):
        # Without a timeout a hung connection never reaches the retry logic
        resp = requests.request(method, url, timeout=timeout, **kwargs)
        if resp.status_code not in RETRY_ON:
            return resp
        if attempt == max_attempts - 1:
            resp.raise_for_status()

        # 429 tells you how long to wait; 5xx does not, so back off
        retry_after = resp.headers.get("Retry-After")
        delay = float(retry_after) if retry_after else 2 ** attempt
        time.sleep(delay + random.uniform(0, 0.5))   # jitter
```

<Warning>
  Retrying a write is only safe with an idempotency key. A `5xx` can be returned
  after the record was already created upstream, so a retry without
  `X-Idempotency-Key` creates a duplicate in the customer's HRIS. Send the same
  key on the retry that you sent on the original request - see
  [Employee](/how-to/writing-data-back/create-an-employee).
</Warning>

Capture status, response body, `X-RateLimit-Remaining`, the connector ID, and the endpoint. A `403` without the endpoint is nearly undiagnosable later.

## An empty result is not an error

The failure mode that costs most is a `200` with no records. Permission gaps, out-of-scope models, and stalled syncs all present this way, and code that only branches on status treats it as "the customer has no employees".

Where a zero count is implausible, check sync status rather than assuming absence - see [Missing records](/how-to/troubleshooting/trace-a-missing-record).

## Upstream failures keep the source system's own answer

When Bindbee's request to the HRIS fails, the record of it preserves the source system's response rather than a Bindbee interpretation of it - the upstream status, the endpoint being called, and the response body unmodified.

That body is the thing to read first. It contains the HR system's own error format, whatever that is: BambooHR returns a structured problem document, Dayforce its own process-result codes inside a `403`, Workday SOAP faults.

**None of these are normalised, and that is the point.** The upstream message frequently names the exact permission or field at fault, which a translated message would lose.

<Warning>
An upstream `403` almost always means the authorising credentials lack a permission - not that Bindbee is unauthorised. **The fix is with your customer's HRIS administrator, not with your API keys.**
</Warning>

## Write failures are source-shaped

Reads mostly fail for structural reasons - credentials, permissions, coverage. **Writes fail for business reasons, and those belong entirely to the source system.**

A time-off request rejected for insufficient balance, a hire rejected because a tenant requires a custom field, a payroll entry rejected because the period is closed - none are conditions Bindbee can evaluate in advance.

It submits the write and reports what came back.

So write error handling cannot be fully generic. You can handle the transport uniformly, but the messages that tell your user what to do are shaped by whichever system they run.

## Logs and issues

Not every failure surfaces on a response. A sync that fails partway through happens in the background, and you find out from the connector's logs or a sync-status webhook.

**Logs** hold the per-request record: which endpoint, which status, what came back. This is where you answer "why is this connector not returning benefits" when nothing in your own application errored - see [Logs](/how-to/troubleshooting/logs).

**Issues** are the layer above. Where a log entry is one request and its response, an issue is a failure Bindbee raised against a connector with a likely cause attached - carrying the evidence, so you and support read the same thing. See [Platform](/platform/overview).

<Warning>
Issues are a Dashboard surface. **There is no issues endpoint in the API**, so anything your own monitoring must act on has to come from sync-status webhooks or the connector's `status` - see [How connections work](/explanation/magic-link).
</Warning>

## Two rate limits

They protect different things, and only one of them is about you.

**Bindbee's limit** is [200 requests per minute per connector](/api-reference/basics/rate-limits) - counted against the connector token, not the API key - and it is what a `429` from Bindbee refers to. Each end user has an independent budget, so parallelising across customers is fine; hammering one customer's connector is what trips it.

**The source system's limits** are usually far tighter, and they constrain how fast Bindbee can *sync* rather than how fast you can read. Most HR systems permit a small number of requests per minute per tenant.

That second one is **the main reason sync cadence is measured in hours rather than minutes**, and it is not something either of you can configure away.

## Why it works this way

Passing upstream errors through unmodified is a deliberate refusal to be helpful in a way that would hurt.

The tempting alternative is normalisation - map every source system's failure into one Bindbee taxonomy so your code handles a single shape. That works for the coarse cases and destroys the fine ones.

HR systems return errors naming specific fields, permission objects and tenant configuration. Collapsing *"the Workday integration system user lacks Get_Workers permission on this security group"* into `PERMISSION_DENIED` throws away **the one sentence that tells the administrator what to change.**

The trade is that your error handling has to be layered. Handle the envelope generically - retry, log, alert on status. Surface the upstream body to whoever can act on it, which is usually a human at the customer rather than your code.

## What this means for you

- **Branch on status before touching `detail`.** It is a string on most errors and an array on `422`.
- **Read the upstream response body first** when a failure came from the source system. It usually names the fix.
- **Route upstream `403`s to the customer's HRIS administrator**, not to your own credentials.
- **Do not expect source-system failures on your own responses.** They happen during syncs; watch logs and sync-status webhooks.
- **Never retry a write without an idempotency key.**
- **Do not build generic user-facing messages for write failures.** The useful detail is source-specific.
- **A successful response with missing data is not an error case** - it is a scope or permissions question.

## If this didn't work

<AccordionGroup>
  <Accordion title="401 with a key you're sure is correct">
    Environment mismatch - a Development key against a Production connector returns `401` rather than a clearer error. See [Authentication](/api-reference/basics/authentication).

    Also check the header includes the `Bearer ` prefix.
  </Accordion>

  <Accordion title="429 despite low request volume">
    The limit is per connector. Several of your services calling the same connector share one budget, and a page walk at `page_size=50` uses four times the requests of one at 200.
  </Accordion>

  <Accordion title="Intermittent 5xx on one integration only">
    May reflect the source system rather than Bindbee. Capture the connector ID and timestamps and report it - the pattern across connectors on the same integration is what identifies it.
  </Accordion>

  <Accordion title="422 on a write that matches the schema">
    The schema is the structural contract; the source system enforces rules beyond it - codes that must exist in their configuration, closed periods, approval states. See [Fetch a schema](/explanation/how-meta-apis-work).
  </Accordion>
</AccordionGroup>
