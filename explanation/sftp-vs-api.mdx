## Two ways in

Not every HR and payroll system offers a usable API. Many enterprise systems - particularly in benefits administration and payroll - exchange data by **scheduled file feed** over SFTP instead.

Bindbee supports both, and normalizes both into the same unified models. The `integration_slug` tells you which you have:

```
bamboohr          API connector
adp               API connector
adp_sftp          SFTP connector
paylocity         API connector
paylocity_sftp    SFTP connector
```

Connectors whose slug ends in `_sftp` - and file-export variants like `workday_raas` and `paychex_flock` - are file-based. The full list is on the [Integrations](/integrations) page.

<Info>
  **Your read code does not change.** `GET /api/hris/v1/employees` returns the
  same unified shape either way. This page is about the differences that show up
  around the edges.
</Info>

## How they differ

| | API connector | SFTP connector |
| --- | --- | --- |
| How data arrives | Bindbee calls the vendor's API | The customer's system drops a file on a schedule |
| Who controls timing | Bindbee's sync schedule | The **customer's** file export schedule |
| Freshness ceiling | The sync schedule | The file schedule - often daily or weekly |
| Field availability | What the API exposes | **What the file contains** |
| Write support | Often available | Generally not |
| Setup | Customer authorizes | Customer's HR/IT configures a recurring export |
| Failure mode | Auth errors, API errors | File missing, late, or malformed |
| `raw_data` | Vendor API payload | Parsed file row |

## The three that actually bite

### 1. Freshness is not yours to control

With an API connector, Bindbee decides when to fetch. With SFTP, Bindbee can only process what has been delivered.

<Warning>
  If the customer's payroll team exports weekly, the data is weekly-fresh no
  matter what Bindbee's sync schedule is. Triggering a resync does not produce a
  new file. There is nothing on Bindbee's side, or yours, that improves it -
  only the customer changing their export schedule.
</Warning>

This is the most common misunderstanding: a resync on an SFTP connector re-processes the most recent file. It does not fetch anything new.

### 2. Field coverage is narrower and fixed by the file

An API connector can generally return any field the endpoint exposes. An SFTP connector can only return **columns present in the file**.

If the customer's export template has 40 columns, those 40 columns are the ceiling. Fields outside them are `null` - not because of a mapping gap, but because the data was never delivered.

Practical consequences:

- Expect more `null` fields than on the API equivalent of the same vendor.
- Deeply relational models - benefits enrolments, dependents, payroll line items - are often thinner or absent, because flat files struggle to represent them.
- The fix, when there is one, is the customer adding columns to their export, not a Bindbee change.

<Tip>
  Before diagnosing a `null` on an SFTP connector as a bug, check
  `include_raw_data=true`. On an SFTP connector, `raw_data` reflects the file
  row - if the value isn't there, it wasn't in the file.
</Tip>

### 3. Writes generally aren't available

File feeds are typically one-directional: the customer's system exports to Bindbee. Creating an employee or a time-off request over SFTP is not usually supported.

If your product depends on writes, check write support per connector before promising it to a customer on an SFTP integration.

## Choosing, when there's a choice

Several vendors appear in both forms - ADP, Paylocity, Paycom, Rippling. When a customer could use either:

| Prefer API when | Prefer SFTP when |
| --- | --- |
| You need richer field coverage | The customer's IT won't approve API credentials |
| You need write-back | Their API tier costs extra or isn't licensed |
| You want Bindbee-controlled sync timing | They already run an export for another vendor |
| You need relational models (benefits, dependents) | Volume is very large and batch is genuinely simpler |

<Warning>
  The choice is usually made by the customer's IT and procurement, not by you.
  Design your product to work correctly on the narrower SFTP profile, and treat
  richer API coverage as an enhancement - not the other way round.
</Warning>

## Building for both

1. **Detect the connector type** from the `integration_slug` suffix and store it with the connection.
2. **Set freshness expectations per type.** "Updated daily by your HR team's export" reads very differently from "synced every 24 hours".
3. **Feature-flag writes** on connector type.
4. **Never hard-fail on a missing field.** Degrade the UI; a required field that is structurally absent on SFTP will otherwise break the whole page.
5. **Explain resync honestly.** A "Sync now" button on an SFTP connector should say it re-processes the latest file, not that it fetches new data.
6. **Escalate coverage gaps to the customer, not to Bindbee.** Missing columns are an export-template conversation with their HR/IT team.

## Field parity, connector by connector

Exact field and model availability differs per connector and per customer file template. Check [Integrations & Coverage](/integrations) for what a specific integration supports, and confirm the customer's actual export template during onboarding - two customers on the same SFTP connector can deliver different columns.
