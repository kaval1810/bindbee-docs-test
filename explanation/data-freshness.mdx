## How fresh is the data?

Bindbee data reflects the **last successful sync** - once every 24 hours by default in Production. Need sub-daily freshness? Sync frequency is adjustable - contact `support@bindbee.dev` or your account manager.

<Warning>
  Webhooks tell you promptly *that a sync happened* - they don't make the sync
  itself more frequent. On a daily schedule, you learn about changes
  promptly, but still up to a day after they occurred in the HRIS.
</Warning>

Total staleness adds up the sync schedule, the sync's own duration (`avg_sync_duration` on the connector), the source system's lag in exposing a change, and any ingest delay on your side.

## Checking how stale you are

Every connector reports its own timing:

| Field | Use it for |
| --- | --- |
| `last_sync_start_time` | "Last updated *X* ago" in your UI |
| `next_sync_start_time` | "Next update in *Y*" |
| `avg_sync_duration` | Estimating how long a triggered sync will take |

<Tip>
  Showing data age ("synced 6 hours ago") heads off most freshness-related
  support tickets.
</Tip>

`modified_at` on a record is when **Bindbee** wrote it, not when the HRIS changed it. See [Field semantics](/explanation/field-semantics).

## Recommended pattern

`connector_synced` webhook → read with `modified_after=<watermark>` → upsert by `id` → save the new watermark. Add a daily reconciliation sweep with the same logic to catch anything missed while your endpoint was down.

| Requirement | Strategy |
| --- | --- |
| Display on demand in a UI | Read through on request; cache briefly; show data age |
| Mirror into your own database | Webhook + `modified_after` read + upsert |
| React to joiners/leavers | `employee_data_changed` webhook → fetch by ID |
| Nightly batch (payroll, billing) | Scheduled `modified_after` sweep; no webhooks needed |
| Sub-hourly freshness | Talk to Bindbee about sync frequency - no client-side pattern fixes this |

## Avoid

- **Short-timer polling.** Calling `/employees` every few minutes can't outrun a 24-hour sync - it just burns rate limit.
- **Resyncing on a schedule.** Trigger resyncs on user intent, not a cron. See [Force a resync](/how-to/force-a-resync).
- **Treating `modified_at` as a business timestamp.** It's a write time, not a change time.
- **Assuming a webhook means something changed.** A sync can rewrite unchanged records too - diff before acting on anything expensive.
- **Gating onboarding on rows existing.** Gate on `sync_status` instead - an empty directory mid-sync looks identical to a genuinely empty one.

## Caching

Invalidate on `connector_synced`, not on a timer - it's both fresher and cheaper. Cache the employee directory until the next sync; cache connector status for only 1-5 minutes since it changes independently of syncs.
