An employee your customer classifies as "Active PT" arrives with a status of active. A pay period they call "Semi-Monthly (2nd/16th)" arrives as semi-monthly. A benefit plan type they have named for their broker arrives as other.

Nothing was lost, exactly. It was set aside.

## What an enum is doing

A unified enum is a fixed set of values that every source system's local vocabulary maps into. It exists so your code can branch on a known set rather than on strings it has never seen.

Source vocabularies are unbounded. Customers define their own statuses, pay period names, benefit types, and employment classifications, and they do so to encode information their business cares about - division, contract type, shift pattern, broker. None of that is expressible in a fixed set, and all of it arrives at the mapping.

So the enum is a projection. Values with a clear equivalent map to it. Values without one land on a fallback.

## `OTHER` and `UNKNOWN` are different

They look interchangeable and are not.

**`OTHER`** means the source provided a value and it did not correspond to any unified value. The information exists; the unified field could not represent it. This is a mapping outcome.

**`UNKNOWN`** means the source did not provide a usable value at all - the field was absent, empty, or unset. This is an absence.

The distinction is diagnostically useful. A field returning `OTHER` across a customer's population means they use a vocabulary the mapping does not cover, and the original is available. A field returning `UNKNOWN` means the data is not being populated at source, which is a permissions or configuration question.

<Info>
A high proportion of `OTHER` on one integration is worth investigating rather than accepting. It often means a mapping gap that affects every customer on that system, not just the one that reported it.
</Info>

## The original is always in raw data

Whatever the source system sent survives unmodified alongside the normalised value.

This is the recovery path when the enum is insufficient. If the local vocabulary carries meaning your application needs - full-time versus part-time encoded in the status, contract type encoded in employment classification - read it from the payload and promote it into a custom field so it arrives as a stable field rather than something your code digs for.

What you should not do is branch on the raw string directly. That is integration-specific handling, and it will break when a customer edits their vocabulary.

## Enums can gain values

The fixed set is fixed at a point in time, not permanently. Values are added as coverage broadens and as source systems introduce concepts the model does not yet carry.

Code that treats the enum as exhaustive - a switch with no default, an exception on an unrecognised value - will break when a value is added. Handling the unrecognised case gracefully costs little and removes an entire class of future failure.

## Why it works this way

The alternative is to pass source strings through untouched, and it fails on its own terms.

Your code would then handle "Active", "ACTIVE", "Active FT", "A", and "Currently Employed" as five separate cases, all meaning employed, varying by integration and by customer within an integration. Every new customer would be a potential new string. That is precisely the per-integration branching a unified API exists to remove, and it moves the mapping work from Bindbee to you without making it easier.

Mapping to a fixed set means one comparison works everywhere. The cost is that nuance below the enum's resolution disappears from the unified field, which is why the fallback values exist and why raw data is retained rather than discarded. The design accepts that the projection will sometimes be too coarse, and makes the loss recoverable instead of pretending it does not happen.

`OTHER` and `UNKNOWN` are kept separate for the same reason. Collapsing them into one value would be simpler and would hide the difference between "we could not represent this" and "there was nothing to represent" - two problems with entirely different fixes.

## What this means for you

- **Handle unrecognised enum values gracefully.** The set can grow.
- **Treat `OTHER` as a signal**, particularly if it clusters on one integration.
- **`UNKNOWN` points at source configuration or permissions**, not at a mapping gap.
- **Promote local vocabulary into a custom field** if you need it. Do not branch on raw strings.
- **Do not infer from an enum what it cannot carry.** Part-time status is not reliably in an employment status field.
