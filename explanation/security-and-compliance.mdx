## What flows through Bindbee

Bindbee handles HR data, which means it routinely carries personal and sensitive information:

| Data | Appears in | Sensitivity |
| --- | --- | --- |
| Names, work contact details | `Employee` | Personal |
| Home address, personal phone/email | `Employee`, `Dependent` | Personal |
| Date of birth | `Employee`, `Dependent` | Personal |
| `ssn` | `Employee`, `Dependent` | Highly sensitive |
| Bank account details | `BankInfo` | Highly sensitive |
| Compensation, pay detail | `Compensation`, `EmployeePayrollRun` | Highly sensitive |
| Benefits enrolment, dependents | Benefits models | Health-adjacent - HIPAA relevance |
| `gender`, `ethnicity`, `marital_status`, `tobacco_use` | `Employee` | Special category under GDPR |
| EEOC data | ATS `EEOC` | Special category |

<Warning>
  Request only the models you need. Reading and storing `ssn` or `BankInfo`
  because they're available materially expands your compliance obligations and
  your breach exposure. Scope by model and by field.
</Warning>

## Credential model

Three distinct secrets, with different blast radii:

| Secret | Scope | If leaked |
| --- | --- | --- |
| **API key** | Your whole organization, one environment | Every connector in that environment is exposed |
| **`connector_token`** | One customer's connection | That customer's data is exposed |
| **Webhook signature key** | Your organization | Attackers can forge webhook payloads |

Rules that follow:

- **All three are server-side secrets.** None may reach a browser, mobile app, or any client you don't control.
- **`link_token` is the only value intended for the frontend.** It is short-lived and scoped to one link session. The `temporary_token` → `connector_token` exchange must happen on your server.
- **Encrypt `connector_token` at rest.** You are storing one per customer; treat the table as a credential store.
- **Keep all three out of logs**, error trackers and support tickets. Redact `Authorization` and `X-Connector-Token` headers in whatever request logging you run.

Rotate keys at [app.bindbee.dev/settings/keys](https://app.bindbee.dev/settings/keys).

<Warning>
  Regenerating a Production API key invalidates the previous key **immediately**.
  Update every dependent service before rotating, or you will take an outage.
</Warning>

## Environment isolation

Development and Production are fully separate:

- Development keys cannot read Production data, and vice versa
- Connectors and data never move between them
- Webhooks are environment-scoped - a Production webhook never fires for a Development connector

<Warning>
  Development keys are shareable within your team by design. Production keys are
  not. Never point a Development key at real customer data, and never test with
  a Production key.
</Warning>

The environment is decided at link time by which key created the `link_token`. There is no way to move a connector afterwards.

## Regions

Bindbee runs regional deployments:

| Region | API base URL |
| --- | --- |
| Default | `https://api.bindbee.dev` |
| EU | `https://api-eu.bindbee.dev` |

The frontend SDKs take the same value via `serverUrl`.

<Warning>
  Region is a data-residency decision. If you have EU customers with residency
  requirements, use the EU endpoint consistently - in your backend, in your
  `serverUrl`, and in your token exchange. Mixing regions for one customer
  produces connectors you cannot see from the other region.
</Warning>

## Webhook security

Anyone who learns your endpoint URL can POST to it. `X-Bindbee-Webhook-Signature` is what makes payloads trustworthy: a base64url HMAC-SHA256 of the raw body, keyed with your organization's signature key.

Non-negotiable:

1. **Verify every request.** Reject with `401` when the signature is absent or wrong.
2. **Verify against raw bytes.** Re-serializing parsed JSON changes key order and whitespace; the HMAC will not match.
3. **Compare in constant time.** `hmac.compare_digest` / `crypto.timingSafeEqual`, never `==`.
4. **Regenerate the key** if it is ever exposed.

See [Validate webhook signatures](/how-to/validate-webhook-signatures).

## Transport

All API traffic is HTTPS. Do not disable certificate verification in any client - not in tests, not "temporarily". Requests carry credentials and personal data in every call.

## Raw data and custom fields

Two flags widen your exposure and should be used deliberately:

| Flag | Effect |
| --- | --- |
| `include_raw_data=true` | Returns the full upstream payload - often far more personal data than the unified model |
| `include_custom_fields=true` | Returns your mapped fields |

<Warning>
  `raw_data` frequently contains fields Bindbee's unified model deliberately
  omits. If you log responses or persist them wholesale, enabling
  `include_raw_data` can silently pull sensitive attributes into your logs and
  database. Use it for interactive debugging; avoid it in bulk pipelines.
</Warning>

## Shared responsibility

| Bindbee | You |
| --- | --- |
| Securing the platform and stored data | Securing your API keys and connector tokens |
| Encrypting vendor credentials | Encrypting connector tokens in your database |
| Signing webhook deliveries | Verifying signatures |
| Environment and region isolation | Using the right key and region |
| Certifications and audits | Your own compliance posture, DPAs, and end-customer notices |
| | Access control within your product |
| | Data minimization - reading only what you need |
| | Retention and deletion in your own systems |

<Warning>
  Deleting a connector in Bindbee does not delete data you have already copied
  into your own systems. If your customer exercises a deletion right, your
  retention policy has to handle your copy.
</Warning>

## Offboarding a customer

When a customer leaves:

1. `DELETE /api/{category}/v1/connectors/{connector_id}/delete`
2. Delete the stored `connector_token` from your database
3. Apply your own retention policy to the mirrored data
4. Confirm the connector shows `is_active: false`

## Answering a security review

Evaluators typically ask for:

- **Certifications and reports** → [trust.bindbee.dev](https://trust.bindbee.dev)
- **Subprocessors and data flow** → Trust Center
- **Data residency** → regional endpoints, above
- **Credential handling** → this page, plus your own key management
- **Deletion path** → connector delete, above

<Tip>
  Point evaluators at the Trust Center rather than restating certification
  details in your own materials. It stays current; a copied claim goes stale and
  becomes a liability.
</Tip>
