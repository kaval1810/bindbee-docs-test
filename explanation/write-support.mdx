title: "Write support"
description: "What it means for a model to support writes, and why support differs by category and by integration."
---

Reading is close to uniform: if a model exists for a category, most integrations return something.

**Writing is not.** Write support is sparse, uneven, and distributed in a way that runs against most people's expectations.

## The shape of it today

| Category | Creates | What accepts them |
| --- | --- | --- |
| **ATS** | 17 endpoints, 16 models | Candidates, applications, jobs, offers, interviews, scorecards, departments, offices, tags and more |
| **HRIS** | 4 | Employee, employee payroll run, time off, timesheet entry |
| **LMS** | 0 | Read-only |

Attachments account for the seventeenth endpoint: they can be created standalone or against a candidate.

The asymmetry surprises people who assume HRIS, being the largest category, is the most capable. **The constraint is not Bindbee's** - it reflects what source systems permit.

HR systems are systems of record for compensation, employment and personal data, and most expose narrow, heavily-validated write surfaces or none at all. Recruiting systems are built around external tools pushing data in, so their write APIs are correspondingly open.

## Two layers of support

An endpoint existing does not mean the write works for your customer.

**The endpoint layer** is what Bindbee's API exposes. This is uniform: if create candidate exists, it exists for every ATS connector.

**The integration layer** is whether the underlying system accepts it. This varies, and an integration that supports reading candidates may not support creating them.

<Warning>
Do not infer write capability from read capability, or from the endpoint being documented. Confirm per integration before committing to a workflow that depends on it.
</Warning>

## Creates, not updates

The write surface is creates. There is no general facility for updating or deleting a record through the unified models.

This is a larger constraint than it first appears. Correcting a mistyped hire, updating a title, cancelling a submitted time-off request - none are operations the unified write API performs.

Where they are possible at all, they go through passthrough, against that integration's own API.

The API surface confirms it. **Exactly one `PATCH` exists in the whole API**, and it is on a custom field mapping - Bindbee configuration, not customer data. There is no `PUT` anywhere, and no `PATCH` on any unified HRIS, ATS or LMS model.

## What a failed write leaves behind

A rejected write leaves nothing in Bindbee. **It may not leave nothing in the source system.**

Some creates are multi-step upstream: a person record, then an employment, then a compensation entry. A failure partway through can leave **a partial record in the customer's HR system** - visible in their UI, which Bindbee did not create and will not clean up.

So a failed write is not automatically safe to retry - retrying may produce a duplicate rather than completing the original.

Where a create fails ambiguously, check the source system's state before retrying.

## Reads and writes are not the same path

A successful write does not immediately appear in your reads. The record was created in the source system; Bindbee learns about it on the next sync.

Reading back straight away finds nothing, and **that absence means nothing**. Trust the write response, or force a resync if the record must appear promptly.

## Why it works this way

The narrowness is inherited rather than chosen, and expanding it is bounded by what source systems allow.

**Reading is forgiving.** A request that returns the wrong thing produces a bad response, and nothing changes.

Writing is not. A malformed create in a payroll system produces a real employee who will be paid, or a time-off request that consumes real entitlement. Source systems reflect that asymmetry: read APIs are broad, write APIs are narrow, heavily validated and often restricted to named integration partners.

Model-by-model expansion follows. Each write requires understanding one system's validation rules, required-field configuration and failure modes well enough not to corrupt a system of record - and **that work does not generalise across models**, so support arrives incrementally.

Passthrough exists as the pressure valve. When the unified write surface does not cover an operation, the escape hatch is available - with the trade-off of integration-specific code.

## What this means for you

- **Confirm write support per integration** before designing a workflow around it.
- **Plan for creates only.** Updates and deletions go through passthrough, if at all.
- **Do not retry a failed write blindly.** Check the source system's state first.
- **Do not read back immediately to confirm.** Trust the write response.
- **Expect the surface to grow**, model by model rather than in bulk.
