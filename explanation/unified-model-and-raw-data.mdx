title: "The Unified Model and Raw Data"
description: "What normalization actually promises, what it necessarily gives up, and why every record carries the original payload alongside the normalized one."
---

The unified model is a translation, and every translation loses something. Knowing what it keeps and what it drops is what lets you decide when to reach past it — and when reaching past it is a mistake.

## What "unified" promises

One thing, precisely: **the shape of a response does not depend on which system produced it.**

```http
GET /api/hris/v1/employees
```

returns the same field names, the same types, and the same relation structure whether the connector is BambooHR, Workday, or an SFTP feed. Your parsing code is written once.

That is the entire guarantee. It is narrower than it first sounds, and three things people expect from it are not included:

| Not promised | Why |
| --- | --- |
| The same *fields populated* on every connector | Systems differ in what they expose. Shape is stable; occupancy is not. |
| The same *values* for the same concept | An enum only normalizes where vendor values map cleanly. Where they don't, the original passes through. |
| Every field the source system has | The unified model carries what is common across systems, not the union of everything any system offers. |

The third is the one worth sitting with. A unified model that carried every vendor's every field would have thousands of columns and no stability — the thing you adopted it for. It is deliberately a **common denominator**, and the escape hatches below exist because a common denominator is not always enough.

## What normalization does to a record

<Steps>
  <Step title="Maps fields">
    Vendor field names become Bindbee field names. A vendor field with no unified
    counterpart is not mapped.
  </Step>
  <Step title="Coerces enums, or passes them through">
    Vendor values are mapped into Bindbee's enums where they match. Where they
    don't, the original string is returned unchanged rather than being dropped or
    forced into the nearest bucket.
  </Step>
  <Step title="Rewrites relations as Bindbee IDs">
    `manager`, `company`, `employment` and similar fields hold Bindbee UUIDs, not
    the source system's identifiers. This is what makes relations traversable
    across connectors.
  </Step>
  <Step title="Nulls what wasn't returned">
    A field the vendor did not send becomes `null`. `null` means *unknown*, not
    zero and not empty.
  </Step>
</Steps>

The second step is the one that surprises people, and it is a deliberate choice about which failure mode is worse. Forcing `"Garden Leave"` into `INACTIVE` would give you a clean enum and a wrong answer. Passing it through gives you a messy enum and a true one. Bindbee picks true. See [Field semantics](/explanation/field-semantics) for how to write code that survives it.

## Why `raw_data` exists

Every record can carry the original payload the source system returned, before any of the above happened.

```bash
curl -G "https://api.bindbee.dev/api/hris/v1/employees" \
  -H "Authorization: Bearer $BINDBEE_API_KEY" \
  -H "X-Connector-Token: $CONNECTOR_TOKEN" \
  --data-urlencode "include_raw_data=true" \
  --data-urlencode "page_size=1"
```

It has two legitimate jobs:

- **Diagnosis.** When a unified field is `null`, `raw_data` tells you whether the value never arrived or arrived and wasn't mapped. Those have completely different fixes, and nothing else distinguishes them.
- **Discovery.** When you need a value the unified model doesn't carry, this is where you find its path before mapping it as a custom field.

<Warning>
  `raw_data` is not an API surface. Its shape is the vendor's, so it varies by
  system, and it can change when the vendor changes their API — which is exactly
  the coupling the unified model removes. Reading production logic straight out
  of `raw_data` re-introduces per-vendor code, silently, in a place your type
  system won't catch.
</Warning>

The right move is to *find* the value in `raw_data` and then *read* it through a custom field, so there is one mapping in one place rather than vendor-shaped conditionals scattered through your codebase.

## The three ways past the model

They are not interchangeable. Each gives up something different.

| | Custom fields | Passthrough | Meta API |
| --- | --- | --- | --- |
| **For** | A value that exists in synced data but has no unified field | A vendor capability Bindbee does not model at all | Discovering what a specific system requires on writes |
| **Reads from** | Bindbee's normalized store | The vendor's API, live | The vendor's schema |
| **Response shape** | Unified, plus your named field | The vendor's | The vendor's |
| **Costs you** | Almost nothing — one mapping | Per-vendor code, vendor rate limits, vendor latency | Nothing; writes require it |
| **Freshness** | As fresh as the last sync | Live | n/a |

Custom fields are a **view over data Bindbee already synced**, not an extra fetch — which is why they cost so little and why they are exactly as stale as everything else. Reach for passthrough only when the value genuinely is not in the sync at all, and know that each use is a small piece of the integration work you adopted Bindbee to avoid.

## What this means when you build

1. **Key on `id`, not `remote_id`.** `id` is Bindbee's and stable; `remote_id` is the vendor's and only unique within one connector.
2. **Treat every non-identity field as nullable.** Shape stability is not occupancy stability.
3. **Never write an exhaustive switch over an enum.** Handle the unrecognized case explicitly.
4. **Use `raw_data` to investigate, custom fields to depend.** If a value ends up in your product, it should arrive through a mapping.
5. **Count your passthrough calls.** A growing number is a signal that the unified model is missing something worth asking for.
