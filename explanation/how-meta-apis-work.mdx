Reading is symmetrical: every integration returns the same employee shape. **Writing is not.**

What a source system requires to create an employee differs by system - and within a system, by tenant, because customers configure their own mandatory fields.

A fixed request schema cannot express that. So for writes, Bindbee tells you what the schema is at the moment you ask, for the connector you are asking about.

## Ask before you write

A meta endpoint returns the request schema for a create operation on a specific connector: which fields exist, which are required, and where the value set is constrained, what the permitted values are.

That last part matters more than it sounds. Many required fields are not free text but **references into the customer's own configuration** - a location identifier, a pay group, an employment type defined in their tenant.

You cannot know those values in advance, and they differ between two customers on the same system.

The response is an envelope - `success`, `data` and `error` - with the schema itself inside `data`, so unwrap before you validate against it.

<Info>
The practical pattern is to fetch the schema, render a form or validate against it, then submit. Hardcoding a request body that worked for one customer is the most common way to build a write integration that breaks on the second.
</Info>

Five operations have one:

| Operation | Endpoint |
| --- | --- |
| Create employee | `/hris/v1/employees/meta/post` |
| Create employee payroll run | `/hris/v1/employee-payroll-runs/meta/post` |
| Create time off | `/hris/v1/time-off/meta/post` |
| Create timesheet entry | `/hris/v1/timesheet-entry/meta/post` |
| Create candidate | `/ats/v1/candidates/create/meta` |

<Warning>
**A meta endpoint existing does not mean a schema exists for your connector.** Where the schema has not been published for that integration and model, the request returns `501 Not Implemented` - which means *unknown*, not *unsupported*. The write itself may still work.

Handle `501` as its own branch rather than folding it into a general error path - see [Meta APIs](/meta-apis-for-write-operations#meta-api-not-implemented-for-an-integration).
</Warning>

## Where there is no meta endpoint

Most write operations do not have one. The ATS creates in particular are largely uncovered - of the seventeen ATS create endpoints, only create candidate has a schema.

For those the request shape comes from the API reference, and the per-tenant variation a schema would have told you has to be discovered by attempting the write and reading the failure. Unsatisfying, and the current state.

## Integration-specific parameters

Some writes need values that exist in one source system and nowhere else - a pay adjustment code, a system-specific flag governing how the record is processed.

These travel in a dedicated parameters object rather than joining the unified body. The separation is deliberate: unified fields stay portable, and the escape hatch is visibly an escape hatch.

Code passing integration-specific parameters knows which integration it is talking to, and the request should show that.

## Why it works this way

Publishing one fixed schema per model would be simpler to document and simpler to code against, and it would be wrong for a substantial share of customers.

The alternative is the intersection - require only what every integration requires, and hope the rest are optional. They are not.

A tenant that has made cost centre mandatory rejects a create that omits it, and no schema design on Bindbee's side changes that. You would learn the requirement from a `400`, which is what runtime discovery exists to avoid.

The other option is the union - accept every field any system might want. That produces a schema too large to be useful, and no signal about what the customer in front of you actually requires.

**Asking the connector puts the answer where the truth is.** The cost is an extra call and a more dynamic integration than a static schema would need.

In return, a write built against the schema works for tenants configured in ways you never anticipated - which is most of them.

## What this means for you

- **Fetch the schema per connector**, not once per integration. Requirements vary by tenant.
- **Render forms from the schema** rather than hardcoding fields.
- **Do not reuse a working request body across customers** without checking it against their schema.
- **Keep integration-specific parameters out of the unified body.** They belong in the dedicated object.
- **Treat `501` as unknown, not unsupported.** The write may still succeed.
- **Where no meta endpoint exists**, expect to discover requirements from failures, and log them.
